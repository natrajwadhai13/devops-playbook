<a id="app-service-overview"></a>

## 1. Azure App Service Overview

Azure App Service is a **PaaS platform** for hosting web applications and APIs without managing the underlying VM operating system.

Azure manages much of the infrastructure, OS platform and runtime environment, while you focus mainly on the application and configuration.

**Flow:** `Developer → App Service → Runtime → Application → Users`

### Common Use Cases

- Web applications
- REST APIs
- Backend services
- Mobile backends
- Business applications
- Enterprise web applications
- CI/CD-based application deployments

### App Service vs VM

| Feature | Azure VM | App Service |
|---|---|---|
| Service Model | IaaS | PaaS |
| OS Management | Customer | Azure |
| OS Patching | Customer | Azure |
| Runtime Management | Customer | Platform-supported |
| SSH/RDP | Yes | Limited/platform-dependent |
| Scaling | VM/VMSS | App Service scaling |
| Deployment Slots | No | Yes |
| Best For | OS-level control | Managed web/API hosting |

<a id="app-service-plan"></a>

## 3. App Service Plan

An **App Service Plan** defines the compute resources used by App Service applications.

It determines important characteristics such as:

- Pricing tier
- CPU/memory capacity
- Number of instances
- Scaling capabilities
- Available platform features

### Important Concept

Multiple Web Apps can run on the same App Service Plan.

**Flow:** `App Service Plan → Compute Resources → Web App 1 + Web App 2 + Web App 3`

### App Service Plan vs Web App

| Component | Purpose |
|---|---|
| App Service Plan | Provides compute resources |
| Web App | Runs the application |
| Deployment Slot | Separate deployment environment for the Web App |

### Important Interview Point

If multiple applications share the same App Service Plan, they share the underlying compute capacity of that plan.

Therefore, one application consuming excessive resources can affect other applications on the same plan.

<a id="app-service-scaling"></a>

## 5. App Service Scaling

App Service supports two major scaling approaches.

| Scaling Type | Meaning | Example |
|---|---|---|
| Vertical Scaling | Increase resources/tier | Basic → Standard → Premium |
| Horizontal Scaling | Increase application instances | 2 → 4 → 8 instances |

### Vertical Scaling

Increase the App Service Plan tier/resources.

**Example:** `Smaller Tier → Larger Tier`

Use when the application needs more:

- CPU
- Memory
- Network capacity
- Platform features

### Horizontal Scaling

Increase the number of instances.

**Flow:** `Traffic Increase → More Instances → More Application Capacity`

### Autoscaling

Autoscaling automatically adjusts instance count based on configured rules and metrics.

Typical signals can include:

- CPU
- Memory
- HTTP/request-related metrics
- Schedule
- Other supported metrics

---

<a id="app-service-autoscaling"></a>

## 6. Autoscaling

Example:

```text
Minimum = 2
Default = 2
Maximum = 10
```

Possible policy:

`High Load → Scale Out → More Instances`

`Low Load → Scale In → Fewer Instances`

### Important Autoscaling Concepts

| Setting | Purpose |
|---|---|
| Minimum | Lowest number of instances |
| Maximum | Highest allowed instances |
| Default | Normal capacity |
| Scale Out | Add instances |
| Scale In | Remove instances |
| Rule | Condition triggering scaling |
| Cooldown | Avoid rapid repeated scaling |

### Production Flow

`Metric → Threshold → Autoscale Rule → Instance Count → Application Capacity`

Do not rely only on CPU if CPU does not represent actual application load.

<a id="deployment-slots"></a>

## 7. Deployment Slots

Deployment Slots provide separate environments for an App Service application.

Common example:

```text
Production
Staging
Testing
```

Instead of deploying directly to production:

`Build → Staging Slot → Test → Validate → Swap → Production`

### Benefits

- Safer deployments
- Testing before production
- Easy rollback
- Reduced downtime
- Blue-Green deployment approach

---

<a id="slot-swap"></a>

## 8. Slot Swap

A slot swap exchanges the application versions/configuration between slots according to App Service slot behavior.

Typical deployment:

`Production v1 + Staging v2 → Validate Staging → Swap → Production v2`

### Rollback

If problems occur:

`Production v2 → Swap Back → Production v1`

This makes slots useful for controlled production releases.

### Important Interview Point

Deployment Slots are available only in supported App Service pricing tiers. Always verify the selected tier before designing the deployment strategy.

---

<a id="slot-settings"></a>

## 9. Slot Configuration

Not every application setting should move between slots.

Examples of settings that may need to remain slot-specific:

- Database connection strings
- API endpoints
- Environment-specific configuration
- Secrets
- External service configuration

Use **Deployment Slot Setting** for configuration that must stay with a specific slot.

### Example

```text
Staging → Staging Database
Production → Production Database
```

During a swap, these slot-specific settings remain associated with their respective slot.

### Production Principle

`Application Code → Swap`

`Environment-specific Configuration → Keep with Slot`

<a id="custom-domain"></a>

## 10. Custom Domain

By default, App Service provides an Azure-hosted hostname.

Example:

```text
myapp.azurewebsites.net
```

You can map a custom domain:

```text
www.example.com
```

### Basic Flow

`User → DNS → Custom Domain → App Service → Web App`

### DNS Configuration

Depending on the domain setup, common records include:

| Record | Purpose |
|---|---|
| CNAME | Maps hostname to App Service hostname |
| A Record | Maps domain to IP where appropriate |
| TXT | Domain ownership/verification |

The exact DNS configuration depends on the hostname and Azure setup.

### Production Considerations

- Verify domain ownership.
- Configure correct DNS records.
- Enable HTTPS.
- Avoid exposing application only through HTTP.
- Configure redirect to HTTPS where appropriate.

<a id="ssl-tls"></a>

## 11. SSL/TLS

App Service supports HTTPS/TLS for secure application traffic.

**Flow:** `Client → HTTPS/TLS → App Service → Web App`

### Why SSL/TLS?

- Encrypts traffic
- Protects credentials
- Protects API communication
- Prevents traffic interception
- Provides application trust through certificates

### Certificate Options

Depending on the App Service setup, certificates can be:

- App Service managed certificate
- Uploaded certificate
- Certificate integrated through supported Azure services

### Production Checklist

- Custom domain configured
- Certificate configured
- HTTPS enabled
- Certificate validity monitored
- HTTP-to-HTTPS redirect configured where appropriate
- TLS configuration reviewed

### Certificate Rotation

`Certificate Expiry Monitoring → New Certificate → Configure → Validate → Remove Old Certificate`

<a id="app-settings"></a>

## 12. Application Settings

Application Settings provide environment-specific configuration to the Web App.

Examples:

```text
ENVIRONMENT=production
API_URL=https://api.example.com
LOG_LEVEL=INFO
```

Application settings are exposed to the application as environment variables according to the runtime/platform.

### Best Practice

Do not store secrets directly in source code.

Preferred:

`App Service → Managed Identity → Key Vault → Secret`

Detailed Key Vault and Identity concepts should remain in the dedicated security module.

<a id="managed-identity"></a>

## 13. Managed Identity

Managed Identity allows an App Service application to authenticate to supported Azure resources without storing credentials in application code.

Example:

`Web App → Managed Identity → Microsoft Entra ID → Key Vault`

Common use cases:

- Key Vault
- Azure Storage
- Azure SQL
- Other Azure services supporting Microsoft Entra authentication

### Benefits

- No hardcoded credentials
- Reduced secret management
- Centralized access control
- Azure RBAC integration

<a id="azure-devops-app-service"></a>

## 15. Azure DevOps → App Service

Typical Azure DevOps pipeline:

`Azure Repos/Git → Azure Pipeline → Build → Test → Artifact → App Service Staging → Approval → Slot Swap`

Example conceptual YAML:

```yaml
trigger:
- main

pool:
  vmImage: ubuntu-latest

steps:
- script: |
    echo "Build application"
    echo "Run tests"
  displayName: Build and Test

- task: AzureWebApp@1
  inputs:
    azureSubscription: 'Azure-Service-Connection'
    appType: 'webApp'
    appName: 'my-web-app'
    package: '$(System.DefaultWorkingDirectory)/**/*.zip'
```

For production, use:

`Build → Test → Scan → Deploy Staging → Smoke Test → Approval → Production`

## 17. App Service Deployment Strategies

| Strategy | Idea | Use |
|---|---|---|
| Direct Deployment | Deploy directly to production | Simple applications |

<a id="app-service-troubleshooting"></a>

## 20. App Service Troubleshooting

### Standard Method

`Alert → Scope → App Service Plan → Web App → Configuration → Deployment → Network → Logs → Metrics → Root Cause → Fix → Verify`

### HTTP 500

Check:

`Application → Runtime → Configuration → Dependencies → Application Logs → Stack Trace`

Possible causes:

- Application exception
- Incorrect configuration
- Missing dependency
- Runtime mismatch
- Database/API failure

### HTTP 502/503

Check:

`App Service → Instance Health → Application Startup → Resource Usage → Deployment → Dependencies`

Possible causes:

- Application not starting
- Resource exhaustion
- Startup timeout
- Dependency failure
- Platform/application issue

### Deployment Failed

Check:

`Pipeline → Authentication → Build Artifact → App Service Configuration → Runtime → Deployment Logs`

### Slot Swap Problem

Check:

`Source Slot → Target Slot → Slot Settings → Application Startup → Configuration → Health → Logs`

### Custom Domain Not Working

Check:

`DNS → Domain Verification → DNS Record → App Service Domain Binding → Certificate → HTTPS`

### SSL Certificate Problem

Check:

`Certificate Validity → Domain Binding → Certificate Configuration → TLS → HTTPS Request`

<a id="app-service-hands-on"></a>

## 22. Hands-on: Create App Service

Create Resource Group:

```bash
az group create \
  --name my-rg \
  --location eastus
```

Create App Service Plan:

```bash
az appservice plan create \
  --name my-app-plan \
  --resource-group my-rg \
  --location eastus \
  --sku B1 \
  --is-linux
```

Create Web App:

```bash
az webapp create \
  --resource-group my-rg \
  --plan my-app-plan \
  --name my-unique-web-app
```

Get default URL:

```bash
az webapp show \
  --resource-group my-rg \
  --name my-unique-web-app \
  --query defaultHostName \
  --output tsv
```

### Configure Application Setting

```bash
az webapp config appsettings set \
  --resource-group my-rg \
  --name my-unique-web-app \
  --settings ENVIRONMENT=production
```

### Enable HTTPS Only

```bash
az webapp update \
  --resource-group my-rg \
  --name my-unique-web-app \
  --https-only true
```

**Hands-on flow:** `Resource Group → App Service Plan → Web App → Configuration → HTTPS → Deploy → Verify`

<a id="app-service-slots-hands-on"></a>

## 23. Hands-on: Deployment Slot

Create staging slot:

```bash
az webapp deployment slot create \
  --resource-group my-rg \
  --name my-unique-web-app \
  --slot staging
```

List slots:

```bash
az webapp deployment slot list \
  --resource-group my-rg \
  --name my-unique-web-app \
  --output table
```

Swap staging to production:

```bash
az webapp deployment slot swap \
  --resource-group my-rg \
  --name my-unique-web-app \
  --slot staging \
  --target-slot production
```

**Deployment flow:** `Build → Staging → Test → Approval → Swap → Production`

<a id="app-service-interview"></a>

## 24. Interview Questions

### Q1. What is Azure App Service?

Azure App Service is a PaaS service for hosting web applications and APIs without managing the underlying server infrastructure.

### Q2. What is an App Service Plan?

It provides the compute resources and pricing tier used by one or more App Service applications.

### Q3. Can multiple Web Apps use one App Service Plan?

Yes. Multiple Web Apps can share the compute resources of an App Service Plan.

### Q4. What is a Deployment Slot?

A Deployment Slot is a separate environment for an App Service application that can be used for testing and controlled production deployments.

### Q5. What is slot swap?

It promotes the application/configuration from one slot to another, commonly staging to production.

### Q6. How do you achieve zero/minimal downtime deployment?

`Build → Staging Slot → Test → Validate → Swap → Monitor`

### Q7. Vertical vs horizontal scaling in App Service?

**Vertical:** Move to a higher App Service Plan tier.

**Horizontal:** Increase the number of application instances.

### Q8. How do you configure a custom domain?

Configure the appropriate DNS record, verify domain ownership, add the custom domain binding in App Service and configure HTTPS/TLS.

### Q9. How do you secure secrets in App Service?

Prefer Managed Identity with Azure Key Vault rather than storing secrets in source code or pipeline files.

### Q10. How would you design App Service CI/CD?

`Git → CI → Build → Test → Scan → Artifact → Staging Slot → Smoke Test → Approval → Swap → Monitor`

### Q11. App Service is returning 503. What will you check?

`Instance Health → Resource Usage → Application Startup → Configuration → Dependencies → Deployment → Logs`

### Q12. Production deployment succeeded but application is failing. What will you do?

Check application logs and health, compare with the previous version, validate configuration/dependencies and use the deployment slot to **swap back/rollback** if required.

<a id="app-service-scenarios"></a>

## 25. Production Scenarios

### Scenario 1: Need zero/minimal downtime deployment

**Solution:**

`Build → Staging Slot → Deploy → Smoke Test → Approval → Swap → Monitor`

If the new release fails:

`Production → Swap Back → Previous Version`

---

### Scenario 2: Application requires more capacity

**Check:** `CPU → Memory → Response Time → Traffic → Instance Count`

If the application needs more resources:

`Vertical Scaling → Larger App Service Plan`

If more instances are required:

`Horizontal Scaling → More Instances`

If traffic varies:

`Autoscaling → Dynamic Instance Count`

---

### Scenario 3: Custom domain works but HTTPS fails

**Check:**

`DNS → Domain Binding → Certificate → Certificate Validity → HTTPS → TLS`

---

### Scenario 4: Application works in staging but fails after swap

**Check:**

`Slot Settings → Environment Variables → Connection Strings → Secrets → External Dependencies → Logs`

Likely issue: environment-specific configuration was not correctly separated.

---

### Scenario 5: Pipeline successfully deploys but application does not start

**Check:**

`Artifact → Runtime Version → Startup Command → Application Logs → Environment Variables → Dependencies`

<a id="app-service-best-practices"></a>

## 26. Best Practices

- Use App Service Plan according to workload requirements.
- Avoid unnecessarily sharing critical applications on the same plan.
- Use Deployment Slots for production releases where supported.
- Test in staging before swapping.
- Keep environment-specific settings slot-specific.
- Use HTTPS for production.
- Use Managed Identity for Azure resource access.
- Store secrets in Key Vault.
- Use CI/CD instead of manual production deployments.
- Enable Application Insights/Azure Monitor.
- Configure health checks and alerts.
- Use autoscaling for variable workloads.
- Monitor App Service Plan resource consumption.
- Keep runtime versions supported and updated.
- Use rollback/swap-back strategy.
- Apply least-privilege RBAC.

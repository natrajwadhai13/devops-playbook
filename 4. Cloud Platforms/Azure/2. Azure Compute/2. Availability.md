<a id="availability-overview"></a>

## 1. Azure VM Availability Overview

Production applications should avoid depending on a single VM.

If one VM fails, the application should continue serving users through another instance.

### Availability Options

| Feature | Main Purpose | Failure Protection | Scaling |
|---|---|---|---|
| Availability Set | Protect VMs from planned/unplanned hardware issues within a datacenter | Fault/Update Domains | No |
| Availability Zone | Protect against datacenter/zone failure | Zone-level | No |
| VM Scale Set | Manage multiple VM instances | Instance-level + scaling | Yes |
| Autoscaling | Automatically adjust capacity | Load-based capacity | Yes |

**Basic HA flow:** `Users → Load Balancer → Multiple VM Instances → Application`

<a id="availability-sets"></a>

## 2. Availability Sets

An Availability Set is a logical grouping of VMs that helps protect applications from localized hardware failures and planned maintenance.

Azure distributes VMs across:

- Fault Domains
- Update Domains

### Fault Domain

A Fault Domain represents a group of VMs that share common physical infrastructure.

If that physical infrastructure fails, VMs in the same fault domain may be affected.

### Update Domain

An Update Domain represents a group of VMs that may be restarted together during planned maintenance.

Azure spreads VMs across update domains so that not all VMs are unavailable at the same time.

### Architecture

`Application → Availability Set → Fault Domains + Update Domains → Multiple VMs`

### Example

```text id="7t0qk9"
VM1 → Fault Domain 1
VM2 → Fault Domain 2
VM3 → Fault Domain 3
```

The exact number and behavior depend on the Azure platform and configuration.

### Important Point

Availability Sets **do not protect against an entire Azure datacenter/zone failure**.

For stronger datacenter-level resiliency, use **Availability Zones**.

<a id="availability-zones"></a>

## 3. Availability Zones

Availability Zones are physically separate locations within an Azure region.

Each zone has independent:

- Power
- Cooling
- Networking
- Physical infrastructure

A failure in one zone should not automatically affect workloads running in another zone.

### Architecture

`Azure Region → Zone 1 + Zone 2 + Zone 3 → Application Instances`

### Example

| Zone | Application |
|---|---|
| Zone 1 | VM / VMSS Instance |
| Zone 2 | VM / VMSS Instance |
| Zone 3 | VM / VMSS Instance |

### Zone-Redundant Architecture

`Users → Load Balancer → Zone 1 VM + Zone 2 VM + Zone 3 VM`

### When to Use

Use Availability Zones when the application requires protection from **zone-level infrastructure failures**.

Typical production workloads:

- Critical web applications
- Application servers
- Databases supporting zone architecture
- High-availability services

---

<a id="availability-set-vs-zone"></a>

## 4. Availability Set vs Availability Zone

| Feature | Availability Set | Availability Zone |
|---|---|---|
| Scope | Within Azure region/datacenter infrastructure | Separate physical zones |
| Protection | Fault + planned maintenance distribution | Zone-level failure |
| Fault Domains | Yes | Not the main mechanism |
| Update Domains | Yes | Not the main mechanism |
| Datacenter/Zone Failure | Limited protection | Designed for zone failure |
| Typical Use | VM HA within a datacenter | Stronger regional HA |
| Architecture | Multiple VMs in Availability Set | VMs distributed across zones |

### Interview Answer

**Availability Set** protects VMs from localized hardware failures and planned maintenance by distributing them across fault and update domains.

**Availability Zone** provides stronger isolation by placing workloads in physically separate zones within an Azure region.

<a id="vmss"></a>

## 5. Virtual Machine Scale Sets (VMSS)

Azure Virtual Machine Scale Sets allow you to create and manage a group of load-balanced VMs.

VMSS provides:

- Multiple VM instances
- Centralized management
- Autoscaling
- Load balancing integration
- Consistent VM configuration
- Rolling upgrades
- Instance management

### Architecture

`Users → Load Balancer → VMSS → VM1 + VM2 + VM3 → Application`

### Why VMSS?

Instead of manually creating:

`VM1 + VM2 + VM3 + VM4`

VMSS manages the instances as a group.

### Common Use Cases

- Web applications
- Application servers
- Microservice workloads requiring VMs
- High-traffic applications
- Batch processing
- Horizontally scalable workloads

## 6. VMSS Important Components

|---|---|

| Instance | Individual VM inside VMSS |
| Image | Base OS/template |
| VM Size | CPU/RAM/network capacity |
| Instance Count | Number of VM instances |
| Load Balancer | Distributes incoming traffic |
| Autoscale | Changes instance count automatically |

| Health Monitoring | Helps determine instance health |

### VMSS Flow

`Image → VMSS → Instance Count → Load Balancer → Application → Autoscale`

<a id="create-vmss"></a>

## 7. Create VMSS

Example Azure CLI:

```bash id="3f9f6j"
az vmss create \
  --resource-group my-rg \
  --name my-vmss \
  --image Ubuntu2404 \
  --instance-count 2 \
  --vm-sku Standard_D2s_v5 \
  --admin-username azureuser \
  --generate-ssh-keys
```

Check VMSS:

```bash id="y3t8tc"
az vmss show \
  --resource-group my-rg \
  --name my-vmss \
  --output table
```

List instances:

```bash id="o6t2e5"
az vmss list-instances \
  --resource-group my-rg \
  --name my-vmss \
  --output table
```

<a id="vmss-scaling"></a>

## 8. VMSS Scaling

VMSS supports horizontal scaling.

Example:

```text id="b48n4d"
2 Instances → 4 Instances → 6 Instances
```

When demand decreases:

```text id="5g7vwp"
6 Instances → 4 Instances → 2 Instances
```

### Manual Scaling

```bash id="kqv7qk"
az vmss scale \
  --resource-group my-rg \
  --name my-vmss \
  --new-capacity 4
```

### Check Capacity

```bash id="8kq6v2"
az vmss show \
  --resource-group my-rg \
  --name my-vmss \
  --query sku.capacity
```

<a id="autoscaling"></a>

## 9. Autoscaling

Autoscaling automatically adjusts the number of VM instances based on workload conditions.

### Basic Concept

`Low Load → Fewer Instances`

`High Load → More Instances`

### Typical Metrics

- CPU percentage
- Memory, when supported through appropriate monitoring/custom metrics
- Queue length
- Request count
- Custom metrics
- Schedule/time-based requirements

### Autoscaling Flow

`Metric → Threshold → Scale Rule → VMSS Instance Count → Application Capacity`

---

<a id="autoscale-rules"></a>

## 10. Autoscale Rules

Example:

```text id="0y2z6q"
CPU > 70% → Scale Out
CPU < 30% → Scale In
```

### Scale-Out

Adds VM instances.

`High Traffic → CPU High → Scale Out → More Instances`

### Scale-In

Removes VM instances.

`Low Traffic → CPU Low → Scale In → Fewer Instances`

### Important Concepts

| Setting | Purpose |
|---|---|
| Minimum | Lowest allowed instance count |
| Maximum | Highest allowed instance count |
| Default | Normal starting capacity |
| Scale-out rule | Adds instances |
| Scale-in rule | Removes instances |
| Cooldown | Prevents rapid repeated scaling |
| Evaluation period | Determines how metrics are evaluated |

### Example Policy

```text id="5cl8s6"
Minimum = 2
Default = 2
Maximum = 10

CPU > 70% → Add instances
CPU < 30% → Remove instances
```

---

<a id="autoscaling-cli"></a>

## 11. Configure Autoscaling

Create autoscale setting:

```bash id="prn3id"
az monitor autoscale create \
  --resource-group my-rg \
  --resource my-vmss \
  --resource-type Microsoft.Compute/virtualMachineScaleSets \
  --name vmss-autoscale \
  --min-count 2 \
  --max-count 10 \
  --count 2
```

Add scale-out rule:

```bash id="0y0c8v"
az monitor autoscale rule create \
  --resource-group my-rg \
  --autoscale-name vmss-autoscale \
  --condition "Percentage CPU > 70 avg 5m" \
  --scale out 1
```

Add scale-in rule:

```bash id="b6f6hj"
az monitor autoscale rule create \
  --resource-group my-rg \
  --autoscale-name vmss-autoscale \
  --condition "Percentage CPU < 30 avg 5m" \
  --scale in 1
```

Check configuration:

```bash id="5x1f4p"
az monitor autoscale show \
  --resource-group my-rg \
  --name vmss-autoscale
```

<a id="autoscaling-best-practice"></a>

## 12. Autoscaling Best Practices

### Do

- Define minimum and maximum capacity.
- Keep at least enough instances for HA.
- Use realistic thresholds.
- Use cooldown periods.
- Monitor scaling events.
- Test scale-out and scale-in.
- Use health probes.
- Combine autoscaling with load balancing.
- Consider scheduled scaling for predictable workloads.

### Avoid

- Minimum instance count = 1 for critical applications.
- Extremely sensitive thresholds.
- Continuous scale-out/scale-in.
- Scaling without monitoring.
- Using CPU as the only metric when CPU does not represent actual application load.

### Production Flow

`Traffic → Load → Metric → Autoscale Rule → VMSS → More/Fewer Instances → Load Balancer → Application`

<a id="vmss-upgrade"></a>

## 13. VMSS Upgrade & Instance Management

VMSS can manage application/OS changes across instances.

Common approaches include:

- Rolling updates
- Manual upgrades
- Automatic upgrades
- Image-based updates

### Rolling Update Concept

`Old Instances → Update Batch → Health Check → Next Batch → All Instances Updated`

The goal is to avoid taking the entire application offline during updates.

### Production Considerations

- Maintain minimum healthy capacity.
- Validate new image/configuration.
- Monitor application health.
- Use health probes.
- Roll back when required.

---

<a id="vmss-health"></a>

## 14. VMSS Health & Load Balancing

VMSS commonly works with a load balancer.

**Flow:** `Client → Load Balancer → Health Probe → Healthy VMSS Instance → Application`

If an instance becomes unhealthy, traffic should not be sent to that unhealthy instance when the health configuration is correctly implemented.

### Health Checks

Check:

- VM instance state
- Health probe
- Application port
- Application process
- NSG
- Backend pool
- Load balancer configuration

<a id="vmss-zones"></a>

## 15. VMSS with Availability Zones

For stronger production resiliency, VMSS can be deployed across Availability Zones where supported by the selected architecture/SKU.

### Architecture

`Users → Load Balancer → Zone 1 VMSS + Zone 2 VMSS + Zone 3 VMSS → Application`

This provides both:

- Horizontal scaling
- Zone-level resiliency

### Production Goal

`HA + Scaling → Multi-Zone VMSS + Load Balancer + Autoscaling`

## 16. Production Architecture Patterns

### Pattern 1: Availability Set

`Users → Load Balancer → Availability Set → VM1 + VM2 → Application`

**Use:** VM-level HA within the supported infrastructure boundary.

### Pattern 2: Availability Zone

`Users → Load Balancer → Zone 1 VM + Zone 2 VM + Zone 3 VM`

**Use:** Zone-level resiliency.

### Pattern 3: VMSS

`Users → Load Balancer → VMSS → Multiple VM Instances`

**Use:** Centralized VM management and horizontal scaling.

### Pattern 4: Production HA + Autoscaling

`Users → Load Balancer → Multi-Zone VMSS → Autoscale → Application`

**Use:** High availability + dynamic capacity.

<a id="availability-troubleshooting"></a>

## 18. Troubleshooting

### VMSS Instances Not Scaling

`Alert → Autoscale Setting → Metric → Threshold → Rule → Current Capacity → Maximum Limit → Activity Log`

Check:

- Autoscale enabled
- Correct resource selected
- Metric available
- Threshold reached
- Minimum/maximum limits
- Scaling rule
- Cooldown
- Activity Log

### Scale-Out Happened but Application Still Slow

`Traffic → Load Balancer → Backend Health → VMSS → CPU/Memory → Application → Database`

Possible causes:

- Application bottleneck
- Database bottleneck
- Incorrect health probe
- Network bottleneck
- New instances not ready
- Slow application startup

### Instances Become Unhealthy

`Health Probe → NSG → Port → Service → Application → Logs`

### Continuous Scale-Out/Scale-In

This can happen when thresholds are too close or workload changes rapidly.

Example:

```text id="mg3i0h"
CPU > 60% → Scale Out
CPU < 55% → Scale In
```

A workload around 57–60% can repeatedly trigger scaling.

**Fix:** Use sensible thresholds and cooldown periods.

<a id="availability-interview"></a>

## 19. Interview Questions

### Q1. What is Availability Set?

Availability Set distributes VMs across fault domains and update domains to improve availability during localized failures and planned maintenance.

### Q2. What is Availability Zone?

Availability Zone is a physically separate location within an Azure region designed to provide isolation from zone-level infrastructure failures.

### Q3. Availability Set vs Availability Zone?

**Availability Set:** Fault Domain + Update Domain distribution.

**Availability Zone:** Physically separate zones within an Azure region.

### Q4. What is VMSS?

VM Scale Set manages a group of similar VMs as a single scalable resource.

### Q5. Why use VMSS?

For:

- Horizontal scaling
- Centralized VM management
- Load balancing
- Autoscaling
- Consistent configuration

### Q6. What is autoscaling?

Autoscaling automatically increases or decreases VM instances based on defined metrics, schedules or rules.

### Q7. What happens when CPU reaches the scale-out threshold?

The autoscale rule evaluates the configured condition and, when satisfied, increases the VMSS instance count within the configured limits.

### Q8. What are minimum, maximum and default instance counts?

| Setting | Meaning |
|---|---|
| Minimum | Lowest instance count |
| Maximum | Highest allowed instance count |
| Default | Normal starting capacity |

### Q9. Why use a cooldown period?

To prevent repeated scaling actions before the previous scaling action has had enough time to affect workload metrics.

### Q10. How would you design a highly available scalable VM application?

`Users → Load Balancer → Multi-Zone VMSS → Autoscaling → Application → Database`

### Q11. How do you troubleshoot VMSS autoscaling?

`Autoscale Configuration → Metric → Threshold → Rule → Capacity → Activity Log → Instance Health`

### Q12. Can VMSS and Availability Zones be used together?

Yes. VMSS can be designed across Availability Zones where supported, providing both horizontal scaling and zone-level resiliency.

<a id="availability-scenarios"></a>

## 20. Production Scenarios

### Scenario 1: One VM fails but application must continue

**Solution:**

Use multiple VM instances behind a load balancer.

`Users → Load Balancer → VM1 + VM2`

For stronger resiliency:

`Users → Load Balancer → Zone 1 + Zone 2 + Zone 3`

---

### Scenario 2: Traffic increases during business hours

**Solution:**

Use VMSS with autoscaling.

`Traffic Increase → CPU/Metric Increase → Scale Out → More VM Instances`

---

### Scenario 3: Traffic decreases at night

**Solution:**

Configure scale-in rules or scheduled scaling.

`Low Traffic → Scale-In Rule → Fewer Instances → Lower Cost`

---

### Scenario 4: Application must survive an Availability Zone failure

**Solution:**

Deploy application instances across multiple Availability Zones and use an appropriate load-balancing architecture.

`Users → Load Balancer → Zone 1 + Zone 2 + Zone 3`

---

### Scenario 5: VMSS keeps scaling continuously

**Check:**

`Metrics → Thresholds → Cooldown → Scale Rules → Application Load`

**Likely cause:** Scaling thresholds are too close or workload is unstable.

**Fix:** Adjust thresholds and cooldown periods and validate the scaling policy.

---

<a id="availability-best-practices"></a>

## 21. Best Practices

- Use Availability Zones for critical zone-resilient workloads where supported.
- Use Availability Sets when zone-level architecture is not required or available.
- Use VMSS for horizontally scalable VM workloads.
- Keep multiple instances for production applications.
- Use Load Balancer or appropriate traffic distribution.
- Configure health probes correctly.
- Define minimum and maximum autoscale limits.
- Use sensible scale-out and scale-in thresholds.
- Configure cooldown periods.
- Monitor autoscale events.
- Test scale-out and scale-in behavior.
- Use rolling updates for controlled VMSS changes.
- Keep application instances stateless where possible.
- Store persistent data outside individual VM instances.
- Combine HA, scaling and monitoring rather than depending on autoscaling alone.

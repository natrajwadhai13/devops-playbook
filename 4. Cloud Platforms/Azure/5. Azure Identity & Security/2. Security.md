## 2. Azure Key Vault

**Azure Key Vault** is a managed Azure service used to securely store and manage sensitive information such as:

- Secrets
- Encryption keys
- Certificates

Instead of storing sensitive values in:

```text
Source Code
Pipeline YAML
Application Configuration
Git Repository
Docker Image
```

store them in:

```text
Application → Managed Identity → Key Vault → Secret/Key/Certificate
```

### Common Use Cases

- Database passwords
- API keys
- Connection strings
- TLS/SSL certificates
- Encryption keys
- Application secrets
- CI/CD secrets

### Production Principle

> **Never hardcode secrets in source code or configuration files.**

---

<a id="3key-vault-components"></a>

## 3. Key Vault Components

Key Vault mainly manages three security objects.

| Object | Purpose | Example |
|---|---|---|
| Secret | Store sensitive values | DB password |
| Key | Cryptographic operations | Encryption/signing |
| Certificate | TLS/SSL certificate | HTTPS certificate |

### Simple Memory

```text
Secret      → Sensitive Value
Key         → Cryptography
Certificate → TLS/SSL Identity
```

<a id="4key-vault-authentication"></a>

## 4. Key Vault Authentication

Applications need an identity to access Key Vault.

Preferred approach:

```text
Application
     ↓
Managed Identity
     ↓
Microsoft Entra ID
     ↓
RBAC
     ↓
Key Vault
```

Other authentication mechanisms may include:

- Service Principal
- User identity
- Azure CLI login

### Production Recommendation

For Azure-hosted applications:

```text
Managed Identity + Microsoft Entra ID + RBAC
```

is preferred over storing client secrets inside applications.

<a id="5secrets"></a>

## 5. Secrets

A **Key Vault Secret** stores sensitive data as a value.

Examples:

```text
Database Password
API Token
Connection String
Third-Party Credential
Application Secret
```

### Example

Instead of:

```text
DB_PASSWORD=MyPassword123
```

store the password in Key Vault.

Application:

```text
Application → Managed Identity → Key Vault → DB Password
```

### Secret Versioning

When a secret is updated, Key Vault can maintain different versions.

```text
Secret
 ├── Version 1
 ├── Version 2
 └── Version 3
```

This helps during:

- Secret rotation
- Rollback
- Migration
- Troubleshooting

<a id="6secret-access-and-permissions"></a>

## 6. Secret Access and Permissions

Key Vault access should follow least privilege.

Example:

```text
Application Identity
        ↓
Key Vault RBAC
        ↓
Secret Reader Permission
        ↓
Specific Key Vault
```

Common Azure roles include:

- Key Vault Secrets User
- Key Vault Secrets Officer
- Key Vault Administrator
- Key Vault Reader

### Production Example

An application only needs to read secrets.

Give:

```text
Application Managed Identity
        ↓
Key Vault Secrets User
```

Do not give unnecessary administrative permissions.

## 7. Certificates

Azure Key Vault can securely store and manage certificates.

Certificates are commonly used for:

- HTTPS
- TLS
- Application authentication
- Client certificates
- Mutual TLS
- Service authentication

### Certificate Components

A certificate generally contains:

```text
Certificate
   ↓
Public Key
   +
Certificate Information
   +
Private Key
```

The private key must be protected.

### Production Flow

```text
Client
  ↓
HTTPS
  ↓
Application
  ↓
TLS Certificate
```

Key Vault can be used to centrally manage the certificate lifecycle.

<a id="8certificate-management"></a>

## 8. Certificate Management

Key Vault helps manage certificate lifecycle operations such as:

- Certificate creation
- Certificate import
- Certificate renewal
- Certificate expiration monitoring
- Certificate versions
- Certificate access control

### Certificate Lifecycle

```text
Create → Deploy → Monitor Expiry → Renew → Deploy New Version → Validate
```

### Production Problem

If an HTTPS certificate expires:

```text
Users
  ↓
HTTPS
  ↓
Certificate Expired
  ↓
TLS Error
```

Therefore certificate expiry monitoring is important.

<a id="9keys"></a>

## 9. Keys

Azure Key Vault supports cryptographic keys used for encryption and signing operations.

Common key types include:

- RSA
- EC

### Key Use Cases

- Encryption
- Decryption
- Digital signing
- Signature verification
- Data protection
- Customer-managed encryption

### Important Concept

A Key is different from a Secret.

```text
Secret → Application reads a sensitive value

Key → Cryptographic operation
```

For example:

```text
Application → Key Vault Key → Encrypt/Decrypt
```

The application does not necessarily need direct access to the raw key material.

---

<a id="10keys-vs-secrets-vs-certificates"></a>

## 10. Keys vs Secrets vs Certificates

| Feature | Secret | Key | Certificate |
|---|---|---|---|
| Main purpose | Store sensitive value | Cryptography | TLS/identity |
| Example | Password | Encryption key | HTTPS certificate |
| Application password | Yes | No | No |
| Encryption | No | Yes | Can support certificate-based security |
| HTTPS | No | Not directly | Yes |
| Rotation | Yes | Yes | Yes |
| Key Vault | Yes | Yes | Yes |

### Easy Memory

```text
Secret      = Password / Token
Key         = Encryption / Signing
Certificate = HTTPS / TLS
```

<a id="11secret-and-certificate-rotation"></a>

## 11. Secret and Certificate Rotation

**Rotation** means replacing an existing credential or security object with a new one before it becomes invalid or compromised.

### Secret Rotation

```text
Old Secret
    ↓
Generate New Secret
    ↓
Store New Secret
    ↓
Update Application
    ↓
Test
    ↓
Disable/Remove Old Secret
```

### Certificate Rotation

```text
Old Certificate
      ↓
Renew/New Certificate
      ↓
Store New Version
      ↓
Deploy
      ↓
Validate HTTPS
      ↓
Retire Old Certificate
```

### Why Rotation Is Important

- Reduce credential lifetime
- Reduce security exposure
- Prevent expired credentials
- Meet security/compliance requirements
- Recover from credential compromise

---

<a id="12key-rotation"></a>

## 12. Key Rotation

Cryptographic keys should also be rotated according to security requirements.

### Key Rotation Flow

```text
Current Key
    ↓
Create New Version
    ↓
Update Application/Encryption Configuration
    ↓
Validate
    ↓
Retire Old Version
```

### Important

Key rotation must be planned carefully when existing encrypted data depends on an older key version.

Always understand:

- Which applications use the key
- Which data was encrypted with the key
- Whether old versions must remain available
- How decryption will work after rotation

## 13. Automatic Rotation Architecture

A production rotation architecture can look like:

```text
Secret/Certificate
        ↓
Key Vault
        ↓
Rotation Policy / Automation
        ↓
New Version
        ↓
Application
        ↓
Validate
        ↓
Old Version Retired
```

### Production Example

```text
Application
    ↓
Managed Identity
    ↓
Key Vault
    ↓
Secret Version
    ↓
Database
```

When the secret changes:

```text
New Secret
    ↓
Key Vault
    ↓
Application retrieves updated value
    ↓
Application reconnects
    ↓
Validate
```

### Important Production Consideration

Applications should be designed to handle credential changes without requiring unnecessary downtime.

<a id="14conditional-access"></a>

## 14. Conditional Access

**Microsoft Entra Conditional Access** controls access based on conditions.

Instead of simply asking:

> Who is the user?

Conditional Access can evaluate:

> Who is the user, from where are they connecting, what device are they using, and what application are they accessing?

### Common Conditions

- User or group
- Location
- Device
- Application
- Risk
- Authentication method

### Example

```text
User
 ↓
Entra ID
 ↓
Conditional Access
 ↓
MFA Required
 ↓
Access Granted
```

<a id="15conditional-access-policies"></a>

## 15. Conditional Access Policies

A Conditional Access policy generally contains:

```text
Assignments
     ↓
Conditions
     ↓
Access Controls
     ↓
Policy Result
```

### Example Policy

Requirement:

> Require MFA for administrators.

Flow:

```text
Admin Login
    ↓
Conditional Access
    ↓
User = Admin
    ↓
MFA Required
    ↓
MFA Success
    ↓
Access Granted
```

### Common Policies

| Policy | Example |
|---|---|
| MFA | Require MFA for administrators |
| Location | Block access from restricted locations |
| Device | Require compliant device |
| Application | Apply controls to specific applications |
| Risk | Require MFA for risky sign-ins |
| Legacy Authentication | Block legacy authentication |

### Production Principle

Conditional Access should be designed carefully to avoid accidentally blocking legitimate administrative access.

## 21. Security Troubleshooting

### Troubleshooting Flow

`Access Issue → Identity → Authentication → Conditional Access → RBAC → Key Vault Permission → Network → Secret/Key/Certificate → Expiry → Logs → Root Cause → Fix → Verify`

### Scenario 1 — Application Cannot Read Secret

Check:

- Managed Identity enabled
- Correct identity
- Principal ID
- RBAC assignment
- Key Vault scope
- Secret name
- Secret version
- Key Vault firewall/network
- Private Endpoint/DNS if configured

### Scenario 2 — Secret Authentication Failed

Check:

- Secret value
- Secret version
- Secret expiry
- Application configuration
- Rotation status
- Application restart/reload requirement

### Scenario 3 — HTTPS Certificate Expired

Check:

```text
Certificate
    ↓
Expiry Date
    ↓
Renewal
    ↓
New Version
    ↓
Application Binding
    ↓
HTTPS Test
```

### Scenario 4 — Admin Cannot Login

Check:

- Entra ID user
- Conditional Access
- MFA
- Device compliance
- Location restrictions
- Sign-in risk
- Account status
- RBAC

<a id="23security-interview"></a>

## 23. Interview Questions

### Q1. What is Azure Key Vault?

**Answer:** Azure Key Vault is a managed service used to securely store and manage secrets, cryptographic keys, and certificates.

### Q2. What is the difference between a Secret and a Key?

**Answer:** A Secret stores sensitive values such as passwords and tokens. A Key is primarily used for cryptographic operations such as encryption, decryption, and signing.

### Q3. What is a certificate used for?

**Answer:** Certificates are commonly used for TLS/HTTPS, identity, and secure authentication.

### Q4. Why should secrets not be stored in Git?

**Answer:** Git repositories can expose credentials to unauthorized users and credentials can remain in commit history even after deletion. Secrets should be stored in a secure secret-management service such as Key Vault.

### Q5. How can an Azure application access Key Vault securely?

**Answer:** Use Managed Identity with Microsoft Entra ID and appropriate RBAC permissions.

### Q6. What is secret rotation?

**Answer:** Secret rotation is the process of replacing an existing credential with a new credential before expiry or compromise.

### Q7. Why is certificate rotation important?

**Answer:** It prevents certificate expiry, reduces security risk, and maintains uninterrupted TLS/HTTPS communication.

### Q8. What is Conditional Access?

**Answer:** Conditional Access is an Entra ID capability that applies access controls based on conditions such as user, location, device, application, and risk.

### Q9. How would you troubleshoot an application that cannot access Key Vault?

**Answer:**

`Managed Identity → Entra ID → RBAC → Key Vault Permission → Scope → Network → DNS → Firewall → Secret → Logs`

### Q10. How would you secure administrative access to Azure?

**Answer:** Use Microsoft Entra ID, Conditional Access, MFA, least-privilege RBAC, and controlled administrative access.

### Q11. What is the production approach for secrets?

**Answer:** Store secrets in Key Vault, use Managed Identity where possible, apply least-privilege RBAC, monitor access, and rotate credentials regularly.

### Q12. What happens if a certificate expires?

**Answer:** Applications using that certificate may fail TLS validation, causing HTTPS or service-to-service communication failures. Certificate expiry should therefore be monitored and renewal should be planned before expiration.

<a id="24security-best-practices"></a>

## 24. Best Practices

- Never hardcode secrets.
- Never commit credentials to Git.
- Use Azure Key Vault for secrets.
- Prefer Managed Identity for Azure workloads.
- Use RBAC with least privilege.
- Rotate secrets regularly.
- Rotate certificates before expiry.
- Rotate cryptographic keys according to security requirements.
- Monitor secret and certificate expiration.
- Protect Key Vault access.
- Use Conditional Access for administrative access.
- Require MFA where appropriate.
- Avoid excessive RBAC permissions.
- Separate development, staging, and production security resources.
- Audit identity and Key Vault access.
- Test credential rotation before production rollout.

### Production Security Principle

```text
No Hardcoded Secrets
        ↓
Key Vault
        ↓
Managed Identity
        ↓
Entra ID
        ↓
Least-Privilege RBAC
        ↓
Monitoring + Rotation
```

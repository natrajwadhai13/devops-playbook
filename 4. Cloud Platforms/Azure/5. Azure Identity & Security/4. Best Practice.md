## 2. Least Privilege

**Least Privilege** means giving a user, application, or service only the permissions required to perform its job.

### Basic Principle

```text
Identity → Minimum Required Permission → Required Resource
```

Do not give:

```text
Application → Owner → Subscription
```

when it only needs:

```text
Application → Reader → Specific Resource
```

### Example

An application needs to read blobs from Storage.

Instead of:

```text
Storage Account → Owner
```

use an appropriate data-plane role such as:

```text
Application Managed Identity
        ↓
Storage Blob Data Reader
        ↓
Required Storage Account
```

### RBAC Scope

Prefer the smallest practical scope:

```text
Management Group
      ↓
Subscription
      ↓
Resource Group
      ↓
Resource
```

### Production Example

If a deployment pipeline only needs to deploy resources in one Resource Group:

```text
CI/CD Identity
      ↓
Contributor
      ↓
Specific Resource Group
```

Avoid:

```text
CI/CD Identity
      ↓
Owner
      ↓
Entire Subscription
```

### Benefits

- Reduces security risk
- Limits accidental changes
- Limits blast radius
- Improves compliance
- Makes access easier to audit

### Interview Answer

> Least privilege means giving identities only the minimum permissions and scope required to perform their task. In Azure, I implement this using RBAC and assign the narrowest practical role and scope.

## 3. No Hardcoded Secrets

Never store sensitive credentials directly inside:

- Source code
- Git repositories
- Dockerfiles
- Container images
- Pipeline YAML
- Configuration files
- Scripts
- Public repositories

### Bad Practice

```text
id="bad-example"
DB_USER=admin
DB_PASSWORD=MyPassword123
API_KEY=xxxxxxxx
```

inside source code or configuration committed to Git.

### Recommended Approach

```text
Application
    ↓
Managed Identity
    ↓
Microsoft Entra ID
    ↓
Key Vault
    ↓
Secret
```

### Example

Instead of:

```text
Application → config file → database password
```

use:

```text
Application
    ↓
Managed Identity
    ↓
Key Vault
    ↓
Database Password
```

### CI/CD

Do not put credentials directly into pipeline YAML.

Bad:

```yaml
variables:
  PASSWORD: "MyPassword123"
```

Better:

```text
Pipeline
   ↓
Secure Secret Store
   ↓
Authentication
   ↓
Deployment
```

### If a Secret Is Exposed

Treat it as compromised.

Recommended flow:

```text
Secret Exposed
      ↓
Revoke / Disable
      ↓
Generate New Secret
      ↓
Update Secure Store
      ↓
Update Application
      ↓
Validate
      ↓
Review Exposure
```

### Important

Deleting a secret from the latest Git commit does **not necessarily remove it from Git history**.

Therefore, rotate the exposed credential immediately.

### Interview Answer

> I never hardcode passwords, API keys, tokens, or connection strings in source code or pipeline files. I use Key Vault or an appropriate secret-management solution and prefer Managed Identity for Azure-hosted workloads.

## 4. Managed Identity

**Managed Identity** allows Azure resources and applications to authenticate to supported Azure services without storing application credentials.

### Basic Flow

```text
Azure Application
      ↓
Managed Identity
      ↓
Microsoft Entra ID
      ↓
RBAC
      ↓
Azure Service
```

### Example

Application needs to access Key Vault:

```text
Application
     ↓
Managed Identity
     ↓
Entra ID
     ↓
RBAC
     ↓
Key Vault
```

No client secret needs to be stored inside the application.

### Common Use Cases

- VM → Key Vault
- App Service → Storage
- Function App → Key Vault
- Azure workload → Azure Storage
- Azure workload → Azure Database
- Azure automation → Azure resources

### System-Assigned Identity

Identity is tied to the Azure resource.

```text
Resource Created
      ↓
Identity Created
      ↓
RBAC Assignment
```

When the resource is deleted, its system-assigned identity is also deleted.

### User-Assigned Identity

Identity exists independently and can be associated with multiple resources.

```text
User-Assigned Identity
       ↓
 ┌─────┼─────┐
 ↓     ↓     ↓
 VM   App   Function
```

### Why Prefer Managed Identity?

Compared with storing Service Principal secrets:

```text
Client Secret
     ↓
Storage
     ↓
Rotation
     ↓
Expiration
     ↓
Potential Exposure
```

Managed Identity reduces the need for application-managed credentials.

### Production Principle

```text
Azure Workload
      ↓
Managed Identity
      ↓
Entra ID
      ↓
Least-Privilege RBAC
      ↓
Azure Service
```

### Interview Answer

> For Azure-hosted workloads, I prefer Managed Identity because Azure manages the identity credentials and the application does not need to store a client secret. I then assign only the required RBAC permissions.

## 5. Private Access

**Private Access** means keeping Azure services and workloads away from unnecessary public Internet exposure.

### Public Access

```text
Internet
   ↓
Public IP
   ↓
Azure Resource
```

This increases the attack surface.

### Private Access

```text
Application
     ↓
VNet
     ↓
Private Endpoint / Private IP
     ↓
Azure Service
```

### Common Azure Technologies

- Private Endpoint
- Private Link
- VNet integration
- Private IP
- Private DNS
- Network Security Groups
- Azure Firewall

### Example — Private Key Vault

Instead of:

```text
Application → Public Internet → Key Vault
```

use:

```text
Application
     ↓
VNet
     ↓
Private Endpoint
     ↓
Private IP
     ↓
Key Vault
```

### Example — Private Storage

```text
Application
     ↓
VNet
     ↓
Private Endpoint
     ↓
Storage Account
```

### Private DNS

Private connectivity often requires correct DNS resolution.

Example:

```text
Application
     ↓
DNS
     ↓
Private IP
     ↓
Private Endpoint
     ↓
Azure Service
```

If DNS is incorrect, the application may resolve the service to a public endpoint instead of the private endpoint.

### Production Principle

> Use private connectivity for sensitive Azure services whenever the architecture and service support it, and avoid unnecessary public exposure.

## 6. Production Security Architecture

A secure Azure workload can combine all four practices:

```text
Users
  ↓
Entra ID
  ↓
RBAC + Least Privilege
  ↓
Application
  ↓
Managed Identity
  ↓
Private Network
  ↓
Private Endpoint
  ↓
Key Vault / Storage / Database
```

### Complete Security Flow

```text
Identity
→ Least Privilege
→ Managed Identity
→ Private Access
→ Secure Service
→ Monitoring
```

### Example

```text
Application
     ↓
Managed Identity
     ↓
Entra ID
     ↓
Least-Privilege RBAC
     ↓
VNet
     ↓
Private Endpoint
     ↓
Key Vault
```

This avoids:

- Hardcoded credentials
- Unnecessary permissions
- Unnecessary public exposure

<a id="7security-checklist"></a>

## 7. Security Checklist

### Identity

- [ ] Use Microsoft Entra ID
- [ ] Use RBAC
- [ ] Apply least privilege
- [ ] Review access regularly
- [ ] Remove unused permissions

### Secrets

- [ ] No passwords in source code
- [ ] No API keys in Git
- [ ] No secrets in Dockerfiles
- [ ] No credentials in pipeline YAML
- [ ] Use Key Vault
- [ ] Rotate exposed credentials

### Managed Identity

- [ ] Use Managed Identity for Azure workloads where supported
- [ ] Avoid unnecessary Service Principal secrets
- [ ] Assign minimum RBAC permissions
- [ ] Use correct scope

### Network

- [ ] Avoid unnecessary public endpoints
- [ ] Use Private Endpoint where appropriate
- [ ] Configure Private DNS correctly
- [ ] Use NSG and Firewall controls
- [ ] Restrict network access

## 8. Production Scenarios

### Scenario 1 — Developer Requests Owner Access

**Problem:**

A developer requests:

```text
Owner → Subscription
```

**Approach:**

Understand what the developer actually needs.

If they only need to manage resources in one Resource Group:

```text
Developer
   ↓
Required RBAC Role
   ↓
Specific Resource Group
```

**Interview Answer:**

> I would not provide Owner access by default. I would identify the required operations and assign the minimum RBAC role at the narrowest practical scope.

---

### Scenario 2 — Password Found in Git

**Problem:**

A database password is committed to Git.

**Approach:**

```text
Credential Exposed
      ↓
Revoke / Rotate
      ↓
Store New Credential Securely
      ↓
Remove Secret from Code
      ↓
Check Git History
      ↓
Validate Application
```

The exposed credential should be considered compromised.

---

### Scenario 3 — Application Uses Client Secret

**Problem:**

An Azure application stores a Service Principal secret.

**Preferred Improvement:**

```text
Service Principal Secret
        ↓
Replace Where Supported
        ↓
Managed Identity
        ↓
Entra ID
        ↓
RBAC
```

---

### Scenario 4 — Storage Account Is Publicly Accessible

**Problem:**

A production Storage Account is exposed through a public endpoint unnecessarily.

**Approach:**

```text
Public Access
     ↓
Review Requirement
     ↓
Private Endpoint
     ↓
Private DNS
     ↓
Network Validation
     ↓
Restrict Public Access
```

---

### Scenario 5 — Application Cannot Access Private Endpoint

Check:

```text
Application
   ↓
VNet
   ↓
DNS
   ↓
Private Endpoint
   ↓
NSG / Firewall
   ↓
Azure Service
```

Typical causes:

- DNS resolution
- Private DNS zone
- VNet connectivity
- NSG rules
- Firewall rules
- Private Endpoint configuration
- RBAC/identity permissions

<a id="9security-best-practices-interview"></a>

## 9. Interview Questions

### Q1. What is the principle of least privilege?

**Answer:** Give an identity only the permissions required to perform its job, at the smallest practical scope.

### Q2. Why should secrets not be hardcoded?

**Answer:** Hardcoded secrets can be exposed through source code, Git history, logs, container images, or configuration files. They are difficult to control and rotate safely.

### Q3. How do you manage secrets in Azure?

**Answer:** I use Azure Key Vault and allow applications to access secrets using Managed Identity and least-privilege RBAC.

### Q4. Why use Managed Identity?

**Answer:** Managed Identity removes the need for applications to store and manage credentials when authenticating to supported Azure services.

### Q5. How do you secure Azure Storage or Key Vault?

**Answer:** I use identity-based access with least-privilege RBAC and prefer private connectivity using Private Endpoint where appropriate. I also restrict unnecessary public access.

### Q6. What is Private Endpoint?

**Answer:** A Private Endpoint provides a private IP address in a VNet for accessing supported Azure services through private connectivity.

### Q7. What would you do if a secret is accidentally committed to Git?

**Answer:**

> I would immediately consider the secret compromised, revoke or rotate it, update the application with the new credential through a secure mechanism, remove the secret from the codebase, review Git history and access logs, and verify the application.

### Q8. How would you secure an Azure application in production?

**Answer:**

> I would use Entra ID and least-privilege RBAC for identity, Managed Identity instead of application-managed credentials, Key Vault for secrets, and Private Endpoint/private networking for sensitive Azure services where supported. I would also monitor and regularly review access.

<a id="10security-best-practice-cheat-sheet"></a>

## 10. Security Best Practice Cheat Sheet

| Best Practice | Remember |
|---|---|
| Least Privilege | Minimum permission |
| No Hardcoded Secrets | Never store credentials in code |
| Managed Identity | Azure-managed authentication |
| Private Access | Avoid unnecessary public exposure |
| RBAC | Control authorization |
| Key Vault | Secure secret management |
| Private Endpoint | Private connectivity |
| Private DNS | Resolve private service endpoint |
| Secret Rotation | Replace exposed/expiring credentials |
| Access Review | Remove unnecessary permissions |

### Four Core Rules

```text
1. Least Privilege
   → Give minimum required access

2. No Hardcoded Secrets
   → Store secrets securely

3. Managed Identity
   → Avoid application-managed credentials

4. Private Access
   → Avoid unnecessary public exposure
```

### Production Memory Flow

```text
User/Application
→ Entra ID
→ Least-Privilege RBAC
→ Managed Identity
→ Private Network
→ Private Endpoint
→ Azure Service
```

### Final Interview Summary

> **The four key Azure security practices are least privilege, avoiding hardcoded secrets, using Managed Identity for Azure workloads, and using private access for sensitive services where supported. Together they reduce unauthorized access, credential exposure, and unnecessary network exposure.**

<a id="2microsoft-entra-id"></a>

## 2. Microsoft Entra ID

**Microsoft Entra ID** is Microsoft's cloud-based identity and access management service.

It manages:

- Users
- Groups
- Applications
- Service Principals
- Managed Identities
- Authentication
- Authorization

### Simple Flow

`User/Application → Entra ID → Authentication → Authorization → Azure Resource`

### Example

A developer logs in to Azure:

```bash
az login
```

Azure authenticates the user through Microsoft Entra ID.

After authentication, Azure checks whether the user has permission to perform the requested operation.

### Key Point

**Entra ID = Identity**

**RBAC = Permission**

<a id="3users"></a>

## 3. Users

A **User** represents an individual identity in Microsoft Entra ID.

Examples:

- Developer
- DevOps Engineer
- Administrator
- Application Owner

### User Authentication

A user can authenticate using:

- Password
- MFA
- Passwordless authentication
- Federated authentication
- Conditional Access policies

### Azure CLI

Login:

```bash
az login
```

List users:

```bash
az ad user list
```

Show a specific user:

```bash
az ad user show --id user@example.com
```

Create a user:

```bash
az ad user create \
  --display-name "DevOps User" \
  --user-principal-name devopsuser@example.com \
  --password "StrongPassword123!"
```

### Production Example

A DevOps engineer needs access to Azure resources.

Instead of sharing credentials:

`Engineer → Entra ID User → Group → RBAC Role → Azure Resource`

<a id="4groups"></a>

## 4. Groups

A **Group** is a collection of users or other supported identities used to simplify permission management.

Instead of assigning RBAC individually:

`User 1 → RBAC`

`User 2 → RBAC`

`User 3 → RBAC`

Use:

`Users → Entra Group → RBAC → Azure Resource`

### Types of Groups

Common group types:

- Security Group
- Microsoft 365 Group

For Azure RBAC, **Security Groups** are commonly used.

### Azure CLI

List groups:

```bash
az ad group list
```

Create a group:

```bash
az ad group create \
  --display-name DevOps-Team \
  --mail-nickname DevOps-Team
```

Add user to group:

```bash
az ad group member add \
  --group DevOps-Team \
  --member-id <USER_OBJECT_ID>
```

### Production Example

Create:

```text
DevOps-Team
```

Add:

```text
Developer
DevOps Engineer
Release Engineer
```

Assign RBAC once:

```text
DevOps-Team → Contributor → Resource Group
```

All group members inherit the permission.

<a id="5rbac"></a>

## 5. RBAC

**Azure Role-Based Access Control (RBAC)** controls what an identity can do on Azure resources.

RBAC answers:

> **Who can do what on which resource?**

### RBAC Model

`Security Principal + Role + Scope = Access`

### Security Principals

A security principal can be:

- User
- Group
- Service Principal
- Managed Identity

### Example

```text
DevOps-Team
      ↓
Contributor
      ↓
Resource Group
```

The group members can perform actions allowed by the Contributor role within that scope.

### Azure CLI

List role assignments:

```bash
az role assignment list
```

Assign a role:

```bash
az role assignment create \
  --assignee <USER_OR_OBJECT_ID> \
  --role Contributor \
  --scope /subscriptions/<SUBSCRIPTION_ID>/resourceGroups/<RESOURCE_GROUP>
```

Remove a role:

```bash
az role assignment delete \
  --assignee <USER_OR_OBJECT_ID> \
  --role Contributor \
  --scope /subscriptions/<SUBSCRIPTION_ID>/resourceGroups/<RESOURCE_GROUP>
```

---

<a id="6rbac-scope"></a>

## 6. RBAC Scope

RBAC can be assigned at different levels.

### Scope Hierarchy

`Management Group → Subscription → Resource Group → Resource`

Permissions assigned at a higher level can flow down to child resources.

### Example

```text
Subscription
    ↓
Resource Group
    ↓
VM
```

If a user receives Contributor at the Resource Group level, the permission applies to resources inside that Resource Group.

### Common Scope Examples

Subscription:

```text
/subscriptions/<subscription-id>
```

Resource Group:

```text
/subscriptions/<subscription-id>/resourceGroups/<rg-name>
```

Resource:

```text
/subscriptions/<subscription-id>/resourceGroups/<rg-name>/providers/Microsoft.Compute/virtualMachines/<vm-name>
```

### Production Best Practice

Prefer the **smallest required scope**.

`Subscription → broad access`

`Resource Group → controlled access`

`Resource → highly restricted access`

---

<a id="7common-rbac-roles"></a>

## 7. Common RBAC Roles

| Role | Typical Purpose |
|---|---|
| Owner | Full resource access including permission management |
| Contributor | Manage resources but cannot manage RBAC access |
| Reader | View resources only |
| User Access Administrator | Manage user access/RBAC |
| Virtual Machine Contributor | Manage VMs |
| Storage Blob Data Reader | Read blob data |
| Storage Blob Data Contributor | Read/write blob data |

### Important Interview Point

**Contributor cannot normally assign RBAC roles to other users.**

**Owner can manage resources and access.**

<a id="8service-principal"></a>

## 8. Service Principal

A **Service Principal** is an application identity used by applications, automation, scripts, and CI/CD pipelines to authenticate to Azure.

Instead of:

`Pipeline → Human User`

Use:

`Pipeline → Service Principal → Entra ID → Azure`

### Common Use Cases

- Azure DevOps pipelines
- GitLab CI/CD
- Terraform
- Automation scripts
- Deployment tools
- Infrastructure provisioning

### Example

Terraform needs to create Azure resources.

```text
Terraform
   ↓
Service Principal
   ↓
Microsoft Entra ID
   ↓
RBAC
   ↓
Azure Resources
```

### Create Service Principal

```bash
az ad sp create-for-rbac \
  --name my-terraform-sp \
  --role Contributor \
  --scopes /subscriptions/<SUBSCRIPTION_ID>
```

The command can return credentials such as:

- Client ID
- Client Secret
- Tenant ID
- Subscription information

**Client secrets must be protected and never committed to Git.**

<a id="9service-principal-authentication"></a>

## 9. Service Principal Authentication

A Service Principal can authenticate using different credential mechanisms.

Common approach:

```text
Client ID
+
Client Secret
+
Tenant ID
```

Example Azure CLI login:

```bash
az login \
  --service-principal \
  --username <CLIENT_ID> \
  --password <CLIENT_SECRET> \
  --tenant <TENANT_ID>
```

### Production Flow

```text
CI/CD Pipeline
      ↓
Secret Store
      ↓
Service Principal
      ↓
Microsoft Entra ID
      ↓
RBAC
      ↓
Azure Resource
```

### Important

Avoid storing credentials directly inside:

```text
.gitlab-ci.yml
pipeline.yml
terraform.tfvars
source code
```

<a id="10managed-identity"></a>

## 10. Managed Identity

**Managed Identity** provides an Azure-managed identity to an Azure resource.

It removes the need to manually manage credentials for supported Azure resources.

Example:

```text
Azure VM
   ↓
Managed Identity
   ↓
Microsoft Entra ID
   ↓
RBAC
   ↓
Azure Key Vault
```

The application can authenticate to Azure services without storing a client secret.

### Common Use Cases

- VM → Key Vault
- App Service → Storage
- Function App → Key Vault
- AKS → Azure services
- Automation → Azure resources

---

<a id="11managed-identity-types"></a>

## 11. Types of Managed Identity

There are two types.

### System-Assigned Managed Identity

Identity is created together with the Azure resource.

```text
VM Created
   ↓
Identity Created
   ↓
RBAC Assignment
```

If the resource is deleted, the identity is also deleted.

### User-Assigned Managed Identity

Identity is created separately.

```text
User-Assigned Identity
       ↓
 ┌─────┼─────┐
 ↓     ↓     ↓
 VM   App   Function
```

The same identity can be associated with multiple resources.

### Comparison

| Feature | System-Assigned | User-Assigned |
|---|---|---|
| Lifecycle | Resource lifecycle | Independent |
| Reusable | No | Yes |
| Multiple resources | No | Yes |
| Management | Simple | More flexible |
| Production use | Resource-specific identity | Shared/reusable identity |

---

<a id="12service-principal-vs-managed-identity"></a>

## 12. Service Principal vs Managed Identity

| Feature | Service Principal | Managed Identity |
|---|---|---|
| Identity type | Application identity | Azure-managed identity |
| Credential management | Usually required | Azure manages credentials |
| Client secret | Commonly used | Not required |
| Best use | External CI/CD and automation | Azure-hosted workloads |
| Security | Depends on secret handling | Better for Azure resources |
| Rotation | Credential rotation required | Azure-managed |

### Interview Answer

> A Service Principal is an application identity commonly used by CI/CD and automation. Managed Identity is an Azure-managed identity that allows Azure resources to authenticate without storing credentials. For Azure-hosted workloads, I prefer Managed Identity where supported.

## 14. Production Architecture

A typical Azure identity architecture:

```text
Human Users → Entra ID → Groups → RBAC → Azure Resources

CI/CD → Service Principal → Entra ID → RBAC → Azure Resources

Azure Workload → Managed Identity → Entra ID → RBAC → Azure Services
```

### Example

```text
Developer
   ↓
Entra ID
   ↓
DevOps Group
   ↓
RBAC
   ↓
Resource Group
   ↓
Azure Resources
```

For automation:

```text
GitLab CI/CD
   ↓
Service Principal
   ↓
Entra ID
   ↓
RBAC
   ↓
Azure
```

For Azure-hosted applications:

```text
App Service
   ↓
Managed Identity
   ↓
Entra ID
   ↓
RBAC
   ↓
Storage / Key Vault / Azure Services
```

<a id="21identity-troubleshooting"></a>

## 21. Identity Troubleshooting

### Troubleshooting Flow

`Authentication Failure → Identity → Tenant → Subscription → RBAC → Scope → Credentials → Token → Resource → Logs → Fix → Verify`

### Scenario 1 — User Cannot Access Resource

Check:

```bash
az role assignment list \
  --assignee <USER_OBJECT_ID> \
  --output table
```

Check:

- Correct user
- Correct subscription
- Correct resource group
- Correct RBAC role
- Correct scope
- Role assignment propagation

### Scenario 2 — Pipeline Authentication Failed

Check:

- Client ID
- Tenant ID
- Client secret/certificate
- Service Principal status
- Subscription
- RBAC permissions
- Secret expiration

### Scenario 3 — Application Cannot Access Azure Resource

Check:

- Managed Identity enabled
- Correct identity type
- Principal ID
- RBAC assignment
- RBAC scope
- Target resource
- Network/private endpoint if applicable

<a id="22identity-interview"></a>

## 22. Interview Questions

### Q1. What is Microsoft Entra ID?

**Answer:** Microsoft Entra ID is Microsoft's cloud identity and access management service used for authentication and identity management.

### Q2. What is RBAC?

**Answer:** RBAC controls which identity can perform which action on which Azure resource.

### Q3. What is a Service Principal?

**Answer:** A Service Principal is an application identity used by automation, applications, Terraform, and CI/CD pipelines to authenticate to Azure.

### Q4. What is Managed Identity?

**Answer:** Managed Identity provides an Azure-managed identity to Azure resources so applications can access Azure services without storing credentials.

### Q5. Service Principal vs Managed Identity?

**Answer:** Service Principals commonly require credential management, while Managed Identities are managed by Azure and are preferred for supported Azure-hosted workloads.

### Q6. What are RBAC scopes?

**Answer:** RBAC can be assigned at Management Group, Subscription, Resource Group, or Resource level.

### Q7. Why use Groups with RBAC?

**Answer:** Groups simplify permission management. Instead of assigning roles to individual users, we assign the role to the group.

### Q8. How would you troubleshoot an RBAC access issue?

**Answer:**

`User → Identity → Subscription → Role Assignment → Scope → Effective Permission → Resource → Verify`

### Q9. How would you secure a CI/CD pipeline accessing Azure?

**Answer:** Use a dedicated identity with minimum required RBAC permissions. Prefer workload identity or secure authentication mechanisms where supported, and never hardcode credentials in pipeline files.

### Q10. Why is Managed Identity preferred for Azure workloads?

**Answer:** It removes the need to store and manage application credentials manually and allows Azure to manage the identity credentials.

<a id="23identity-cheat-sheet"></a>

## 23. Identity Cheat Sheet

| Concept | Remember |
|---|---|
| Entra ID | Identity platform |
| User | Human identity |
| Group | Collection of identities |
| RBAC | Azure permissions |
| Service Principal | Application/automation identity |
| Managed Identity | Azure-managed application identity |
| System-Assigned | Identity tied to resource |
| User-Assigned | Reusable identity |
| RBAC Scope | Management Group → Subscription → RG → Resource |
| Least Scope | Give access at the lowest required level |

### Final Memory Flow

```text
Human → User → Group → RBAC → Azure Resource

CI/CD → Service Principal → Entra ID → RBAC → Azure

Azure Workload → Managed Identity → Entra ID → RBAC → Azure Service
```

### One-Line Interview Summary

> **Microsoft Entra ID manages identities, Groups organize users, RBAC controls Azure permissions, Service Principals provide application identities, and Managed Identities provide Azure-managed authentication without storing credentials.**

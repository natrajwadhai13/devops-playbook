## 11.1 Troubleshooting Method

### 🔹 Standard Production Flow

```text
Alert → Scope → Metrics → Logs → Network → Application → Root Cause → Fix → Verify → Prevent
```

### Step 1: Understand the Issue

Check:

- What is impacted?
- Which application/service?
- All users or selected users?
- Production only or all environments?
- When did the issue start?
- Was there any recent deployment/change?

### Step 2: Check Monitoring

Check:

- CPU
- Memory
- Disk
- Network
- Application response time
- Error rate
- Availability
- Pod health
- Node health

### Step 3: Check Logs

Common sources:

- Application logs
- VM logs
- Azure Activity Log
- AKS container logs
- Ingress logs
- Application Gateway logs
- Pipeline logs

### Step 4: Check Network

Verify:

- DNS
- NSG
- Route
- Port
- Load Balancer
- Application Gateway
- Firewall
- Private Endpoint
- Private DNS

### Step 5: Find Root Cause

Do not directly restart services.

First identify:

```text
Symptom → Evidence → Root Cause → Fix
```

### Step 6: Verify

After fixing:

- Test application
- Check logs
- Check metrics
- Verify dependencies
- Confirm user traffic
- Monitor for recurrence

### Step 7: Prevent

Add:

- Monitoring
- Alert
- Automation
- Capacity planning
- Health checks
- Documentation
- Permanent code/configuration fix

## 11.2 VM Troubleshooting

### 🔹 CPU High

Linux:

```bash
top
htop
uptime
ps aux --sort=-%cpu | head
```

Azure:

```bash
az vm get-instance-view \
  --resource-group <rg> \
  --name <vm>
```

Check:

- Which process consumes CPU?
- Application traffic increased?
- Infinite loop?
- Background job?
- Insufficient VM size?

### 🔹 Memory High

```bash
free -h
top
ps aux --sort=-%mem | head
```

Check:

- Memory leak
- Java heap
- Node.js process
- Too many processes
- Insufficient RAM

### 🔹 Disk Full

```bash
df -h
du -sh /*
du -sh /var/*
find /var -type f -size +500M
```

Check:

- Application logs
- Docker images
- Temporary files
- Core dumps
- Old backups

Production fix:

```text
Find large files → Verify → Clean/rotate → Increase disk if required → Monitor
```

### 🔹 Process Troubleshooting

```bash
ps -ef
pgrep -af <process>
systemctl status <service>
journalctl -u <service>
```

### 🔹 Service Down

```bash
systemctl status nginx
systemctl restart nginx
journalctl -u nginx --since "30 min ago"
```

Before restart check:

```bash
systemctl status nginx
journalctl -xe
ss -lntp
```

### 🔹 SSH Issue

Check:

```bash
systemctl status ssh
ss -lntp | grep 22
```

Azure checks:

- NSG
- Public IP
- Route
- VM running state
- Boot diagnostics
- Serial Console

### 🔹 RDP Issue

Check:

- VM running
- NSG port 3389
- Windows Firewall
- RDP service
- Route
- Public/private connectivity

### 🔹 Boot Issue

Azure tools:

```bash
az vm get-instance-view \
  --resource-group <rg> \
  --name <vm>
```

Check:

- Boot diagnostics
- Serial Console
- OS disk
- Recent configuration changes

## 11.3 Network Troubleshooting

### 🔹 DNS Issue

Linux:

```bash
nslookup example.com
dig example.com
cat /etc/resolv.conf
```

Windows:

```powershell
nslookup example.com
ipconfig /flushdns
```

Check:

- DNS server
- DNS record
- Private DNS Zone
- DNS resolution from correct network

### 🔹 Port Connectivity

Linux:

```bash
nc -vz <host> <port>
curl -v http://<host>:<port>
```

Windows:

```powershell
Test-NetConnection <host> -Port 443
```

Check:

```text
Client → DNS → Route → NSG → Firewall → Load Balancer → Application
```

### 🔹 NSG Issue

Check:

- Source
- Destination
- Port
- Protocol
- Priority
- Allow/Deny rule

Azure:

```bash
az network nsg rule list \
  --resource-group <rg> \
  --nsg-name <nsg>
```

### 🔹 Route Issue

Check:

- Route Table
- Next Hop
- UDR
- Peering
- VPN/ExpressRoute
- Firewall

### 🔹 Load Balancer Issue

Check:

- Backend pool
- Health probe
- NSG
- Application listening port
- Backend availability

### 🔹 Application Gateway Issue

Check backend health:

```bash
az network application-gateway show-backend-health \
  --resource-group <rg> \
  --name <appgw>
```

Check:

- Listener
- Backend pool
- Health probe
- HTTP settings
- Routing rule
- TLS certificate
- NSG

### 🔹 Private Endpoint Issue

Check:

- Private Endpoint connection
- Private IP
- Private DNS Zone
- VNet integration
- DNS resolution

Typical problem:

```text
Application → Private Endpoint → DNS resolves public IP
```

instead of:

```text
Application → Private Endpoint → Private IP
```

## 11.4 Application Troubleshooting

### 🔹 4xx Errors

**400 Bad Request**

Possible causes:

- Invalid request
- Missing parameter
- Invalid JSON

**401 Unauthorized**

Possible causes:

- Missing token
- Expired token
- Invalid authentication

**403 Forbidden**

Possible causes:

- Insufficient permissions
- RBAC issue
- Authorization failure

**404 Not Found**

Possible causes:

- Wrong URL
- Wrong route
- Ingress path issue
- Service endpoint missing

### 🔹 5xx Errors

**500 Internal Server Error**

Application-side failure.

Check:

```bash
application logs
database connectivity
dependency errors
```

**502 Bad Gateway**

Usually proxy/backend communication issue.

Check:

- Backend service
- Port
- Health probe
- Ingress
- Application Gateway
- Nginx

**503 Service Unavailable**

Possible causes:

- Backend unavailable
- No healthy pods
- Service has no endpoints
- Application overloaded

### 🔹 Timeout

Check:

- Application response time
- Network latency
- Load Balancer
- Application Gateway
- NSG
- Database
- External API
- Connection pool

### 🔹 SSL/TLS Issue

Check:

```bash
openssl s_client -connect example.com:443
```

Verify:

- Certificate expiry
- CN/SAN
- Certificate chain
- TLS version
- Listener configuration
- Secret/certificate rotation

### 🔹 Connection Refused

Usually means nothing is listening on the target port.

Check:

```bash
ss -lntp
netstat -lntp
curl -v http://localhost:<port>
```

### 🔹 Dependency Failure

Application may depend on:

- Database
- Redis
- Storage
- Queue
- External API
- Key Vault
- Service-to-service API

Check dependency health before changing application code.

<a id="115-aks-troubleshooting"></a>

## 11.5 AKS Troubleshooting

### 🔹 Pod Not Running

```bash
kubectl get pods -n <namespace>
kubectl describe pod <pod> -n <namespace>
kubectl logs <pod> -n <namespace>
```

Check:

- Events
- Image
- ConfigMap
- Secret
- Resource limits
- Probes
- Volume

### 🔹 Pending Pod

```bash
kubectl describe pod <pod> -n <namespace>
```

Common causes:

- Insufficient CPU/memory
- Node selector
- Taints
- Affinity
- PVC pending

### 🔹 CrashLoopBackOff

```bash
kubectl logs <pod> --previous -n <namespace>
kubectl describe pod <pod> -n <namespace>
```

Common causes:

- Application crash
- Wrong environment variable
- Database connection failure
- Secret missing
- Wrong command
- Liveness probe failure
- OOM

### 🔹 OOMKilled

Check:

```bash
kubectl describe pod <pod> -n <namespace>
kubectl top pod -n <namespace>
```

Possible cause:

```text
Memory usage > container memory limit
```

Fix:

- Optimize application
- Increase memory limit
- Investigate memory leak
- Configure appropriate requests/limits

### 🔹 ImagePullBackOff

Check:

```bash
kubectl describe pod <pod> -n <namespace>
```

Common causes:

- Wrong image name
- Wrong tag
- ACR authentication
- Image does not exist
- Network issue

Verify:

```bash
az acr repository list --name <acr>
```

### 🔹 Deployment Issue

```bash
kubectl get deployment -n <namespace>
kubectl rollout status deployment/<deployment> -n <namespace>
kubectl rollout history deployment/<deployment> -n <namespace>
```

Rollback:

```bash
kubectl rollout undo deployment/<deployment> -n <namespace>
```

### 🔹 Service Issue

```bash
kubectl get svc -n <namespace>
kubectl get endpoints -n <namespace>
```

If service has no endpoints:

- Selector mismatch
- Pods not Ready
- Wrong labels

### 🔹 Ingress Issue

```bash
kubectl get ingress -n <namespace>
kubectl describe ingress <ingress> -n <namespace>
```

Check:

- Host
- Path
- TLS
- Backend service
- Ingress controller
- DNS

### 🔹 AKS DNS Issue

```bash
kubectl get pods -n kube-system
kubectl exec -it <pod> -- nslookup <service>
```

Check:

- CoreDNS
- Service name
- Namespace
- Network policies

### 🔹 Storage Issue

```bash
kubectl get pv
kubectl get pvc -n <namespace>
kubectl describe pvc <pvc> -n <namespace>
```

Check:

- StorageClass
- Azure Disk
- Azure Files
- Permissions
- Availability Zone compatibility

### 🔹 Node Issue

```bash
kubectl get nodes
kubectl describe node <node>
kubectl top nodes
```

Check:

- CPU
- Memory
- Disk
- Conditions
- Taints
- Node readiness

### 🔹 Scaling Issue

```bash
kubectl get hpa -n <namespace>
kubectl describe hpa <hpa> -n <namespace>
kubectl get nodes
```

Check:

- CPU/memory metrics
- HPA configuration
- Resource requests
- Cluster Autoscaler
- Node capacity

## 11.6 Pipeline Troubleshooting

### 🔹 Build Failure

Check:

- Source code
- Dependency installation
- Build command
- Environment variables
- Runner/agent
- Artifact generation

### 🔹 Runner/Agent Issue

Check:

- Runner status
- Tags
- Executor
- Network connectivity
- Docker availability
- Required tools

### 🔹 Credential Failure

Common causes:

- Expired secret
- Wrong service connection
- Invalid token
- Permission removed
- Secret variable missing

Never print secrets in logs.

### 🔹 ACR Login Failure

Check:

```bash
az acr login --name <acr>
```

Verify:

- Service principal
- Managed Identity
- AcrPull/AcrPush permission
- Registry name
- Network access

### 🔹 Deployment Failure

Check:

```bash
kubectl get pods -n <namespace>
kubectl get deployment -n <namespace>
kubectl rollout status deployment/<deployment> -n <namespace>
```

Pipeline flow:

```text
GitLab → Build → Test → Docker Build → ACR Push → AKS Deploy → Verify
```

### 🔹 Rollback

Kubernetes:

```bash
kubectl rollout history deployment/<deployment>
kubectl rollout undo deployment/<deployment>
```

Helm:

```bash
helm history <release>
helm rollback <release> <revision>
```

## 11.7 Production Scenarios

### Scenario 1: Website Down

Check:

```text
DNS → Network → Load Balancer/App Gateway → Ingress → Service → Pod → Application
```

Commands:

```bash
kubectl get ingress
kubectl get svc
kubectl get pods
kubectl logs <pod>
```

### Scenario 2: VM CPU 100%

Check:

```bash
top
ps aux --sort=-%cpu | head
```

Then:

- Identify process
- Check application logs
- Check traffic
- Check recent deployment
- Restart only if required
- Fix root cause

### Scenario 3: API Returns 502

Check:

```text
Client → App Gateway/Ingress → Service → Pod → Application
```

Verify:

- Backend health
- Service endpoints
- Pod readiness
- Application port
- Health probe

### Scenario 4: Pods Crash After Deployment

Check:

```bash
kubectl rollout status deployment/<deployment>
kubectl get pods
kubectl describe pod <pod>
kubectl logs <pod> --previous
```

Likely causes:

- Bad image
- Configuration issue
- Secret missing
- Dependency failure
- Wrong environment variable

Rollback if required.

### Scenario 5: Pipeline Worked Yesterday but Fails Today

Check:

- Code changes
- Dependency changes
- Runner status
- Certificate expiry
- Token expiry
- Service connection
- ACR
- External dependency
- Agent image/tool version

### Scenario 6: Internal Works but Internet Does Not

Check:

- Public DNS
- Public IP
- Load Balancer
- Application Gateway
- NSG
- Firewall
- Route
- Backend health

## 11.8 RCA Method

### 🔹 RCA Format

```text
Incident
→ Impact
→ Detection
→ Timeline
→ Root Cause
→ Resolution
→ Validation
→ Prevention
→ Action Items
```

### Example

**Incident:** API unavailable for users.

**Impact:** Customers could not access checkout.

**Detection:** Monitoring generated 5xx alert.

**Root Cause:** Backend pods were OOMKilled because memory limit was too low.

**Resolution:** Increased appropriate memory limit and restarted affected pods.

**Validation:** API health and transaction flow verified.

**Prevention:**

- Proper resource sizing
- Memory monitoring
- OOM alerts
- Load testing
- Capacity planning

### 🔹 Good RCA

RCA should identify:

- Why it happened
- Why monitoring did not prevent it
- Why deployment/configuration allowed it
- How to prevent recurrence

Avoid:

> "Server was down."

Prefer:

> "Application pods were repeatedly OOMKilled because memory consumption exceeded the configured container limit."

<a id="119-interview-questions"></a>

## 11.9 Interview Questions

### Q1. How do you troubleshoot a production application?

**Answer:**

I first understand the impact and scope. Then I check monitoring metrics, application logs, network connectivity and dependencies. After collecting evidence, I identify the root cause, apply the safest fix, verify the application and document preventive actions.

### Q2. How do you troubleshoot high CPU on Linux?

```bash
top
ps aux --sort=-%cpu | head
```

I identify the process, check application logs and recent changes, validate traffic and then fix or scale the application based on the root cause.

### Q3. Difference between 502 and 503?

**502:** Gateway/proxy cannot get a valid response from backend.

**503:** Service/backend is unavailable or has no healthy backend.

### Q4. How do you troubleshoot CrashLoopBackOff?

```bash
kubectl describe pod <pod>
kubectl logs <pod> --previous
```

I check application crash, configuration, secrets, dependencies, commands and probes.

### Q5. How do you troubleshoot ImagePullBackOff?

I verify the image name/tag, confirm the image exists in ACR and check AKS authentication and permissions.

### Q6. How do you troubleshoot Pending pods?

I check pod events and verify CPU/memory availability, node selectors, affinity, taints/tolerations and PVC status.

### Q7. How do you troubleshoot AKS Service?

```bash
kubectl get svc
kubectl get endpoints
kubectl describe svc <service>
```

I verify selectors, pod labels, readiness and targetPort.

### Q8. How do you troubleshoot DNS?

I test DNS resolution using `nslookup` or `dig`, then verify DNS records, Private DNS, CoreDNS and network connectivity.

### Q9. What is your production troubleshooting approach?

> **Monitor → Logs → Metrics → Network → Application → Root Cause → Fix → Verify → Prevent**

### Q10. When do you rollback?

I rollback when a recent deployment is confirmed or strongly suspected to cause production impact and rollback is safer and faster than fixing forward.

<a id="1110-best-practices"></a>

## 11.10 Best Practices

- Always check monitoring before making changes.
- Do not restart blindly.
- Capture logs before restarting.
- Check recent deployments and configuration changes.
- Follow least-privilege access.
- Keep production changes documented.
- Use health probes.
- Configure alerts for critical resources.
- Maintain deployment rollback capability.
- Monitor CPU, memory, disk and application errors.
- Use centralized logging.
- Maintain RCA for major incidents.
- Automate repetitive recovery tasks.
- Test disaster recovery procedures.
- Use change management for production.
- Keep secrets out of source code and logs.

### 🔹 Production Golden Rule

```text
Evidence First → Fix Second → Prevention Third
```

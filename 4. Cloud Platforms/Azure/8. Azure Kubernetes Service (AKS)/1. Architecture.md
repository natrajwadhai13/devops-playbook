## 1. AKS Architecture Overview

**Azure Kubernetes Service (AKS)** is Azure's managed Kubernetes service.

In AKS, Azure manages the Kubernetes **control plane**, while you manage the **worker nodes/node pools**, workloads, configurations, and applications.

Basic architecture:

`User → Azure → AKS Control Plane → Node Pool → Worker Nodes → Pods → Application`

A typical production flow:

`Developer → Git → CI/CD → ACR → AKS Control Plane → Node Pool → Pods → Service/Ingress → Users`

### Main AKS Architecture Components

| Component | Purpose |
|---|---|
| Control Plane | Manages Kubernetes cluster |
| Node Pool | Group of similar worker nodes |
| System Node Pool | Runs critical Kubernetes system components |
| User Node Pool | Runs application workloads |
| VM Size | Defines CPU, memory, disk/network capabilities of nodes |
| Worker Node | Azure VM running Kubernetes components |
| Pod | Smallest Kubernetes workload unit |

### Key Memory

```text
Control Plane = Manages Cluster
Node Pool     = Group of Nodes
System Pool   = Kubernetes System Workloads
User Pool     = Application Workloads
VM Size       = CPU + Memory + Disk + Network Capacity
```

<a id="2-aks-control-plane"></a>

## 2. AKS Control Plane

The **control plane** is the management layer of Kubernetes.

It receives requests and maintains the desired state of the cluster.

In AKS, the control plane is **managed by Azure**.

You normally interact with it using:

- Azure Portal
- Azure CLI
- `kubectl`
- Kubernetes API
- CI/CD pipelines

Architecture:

`kubectl / CI-CD → Kubernetes API → Control Plane → Nodes → Pods`

### What Does the Control Plane Do?

The control plane:

- Accepts Kubernetes API requests
- Stores cluster state
- Schedules workloads
- Detects desired vs actual state
- Manages deployments
- Manages nodes
- Manages pods
- Handles scaling decisions
- Maintains Kubernetes objects

### Example

You run:

```bash
kubectl create deployment my-app --image=nginx
```

Flow:

`kubectl → API Server → Control Plane → Scheduler → Node → Pod`

The control plane determines **where and how the workload should run**.

---

<a id="3-aks-control-plane-components"></a>

## 3. AKS Control Plane Components

The Kubernetes control plane contains several important components.

### 3.1 API Server

The **API Server** is the main entry point to Kubernetes.

All Kubernetes API requests go through the API Server.

Examples:

```bash
kubectl get pods
kubectl get nodes
kubectl create deployment my-app --image=nginx
kubectl apply -f deployment.yaml
```

Flow:

`kubectl → API Server → Kubernetes Objects`

---

### 3.2 Scheduler

The **Scheduler** decides which worker node should run a new Pod.

It considers:

- Available CPU
- Available memory
- Resource requests
- Node selectors
- Affinity
- Taints
- Tolerations
- Other scheduling constraints

Example:

`New Pod → Scheduler → Suitable Node → Pod`

---

### 3.3 Controller Manager

Controllers continuously compare:

**Desired State vs Current State**

Example:

You define:

```yaml
replicas: 3
```

But only two Pods are running.

The controller detects:

```text
Desired = 3
Current = 2
```

It creates another Pod.

Flow:

`Desired State → Controller → Actual State`

---

### 3.4 etcd

`etcd` stores Kubernetes cluster state.

It contains information such as:

- Kubernetes objects
- Cluster configuration
- Desired state
- Metadata

Conceptually:

`API Server ↔ etcd`

In AKS, the control plane and its management are handled by Azure.

---

### Control Plane Memory

```text
API Server       → API Entry Point
Scheduler        → Selects Node
Controller       → Maintains Desired State
etcd             → Stores Cluster State
```

<a id="4-aks-node-pools"></a>

## 4. AKS Node Pools

A **node pool** is a group of Kubernetes worker nodes with the same configuration.

Each node in an AKS node pool is an Azure VM.

Example:

```text
AKS Cluster
│
├── System Node Pool
│   ├── Node 1
│   └── Node 2
│
└── User Node Pool
    ├── Node 1
    ├── Node 2
    └── Node 3
```

Node pools allow you to use different VM configurations for different workloads.

### Why Use Multiple Node Pools?

Different applications may have different requirements.

Example:

```text
System Workloads → Small/Medium Nodes
General Apps     → General Purpose Nodes
Memory Apps      → Memory Optimized Nodes
CPU Apps         → Compute Optimized Nodes
GPU Apps         → GPU Nodes
```

### Example Production Design

```text
AKS
├── System Pool
│   └── System components
│
├── Application Pool
│   └── Normal applications
│
└── High-Memory Pool
    └── Memory-intensive applications
```

<a id="5-system-node-pool"></a>

## 5. System Node Pool

The **system node pool** is intended for critical Kubernetes system workloads.

Examples include Kubernetes system components and cluster add-ons.

A system node pool is required for an AKS cluster.

### Purpose

System pools provide dedicated capacity for:

- Core Kubernetes components
- Cluster add-ons
- System-level workloads

### Production Recommendation

Keep system workloads separated from normal application workloads where practical.

Example:

```text
System Pool
├── Kubernetes system workloads
├── CoreDNS
└── Other system components

User Pool
├── Web application
├── API application
└── Background workers
```

This helps prevent application workloads from consuming all available resources needed by the cluster itself.

---

<a id="6-user-node-pool"></a>

## 6. User Node Pool

A **user node pool** is primarily intended for application workloads.

Examples:

- Java applications
- .NET applications
- Node.js applications
- Python applications
- Microservices
- Background workers

Example:

```text
User Pool
├── Web Pods
├── API Pods
├── Worker Pods
└── Microservice Pods
```

User pools can use different:

- VM sizes
- Node counts
- Autoscaling configurations
- Labels
- Taints
- Workload-specific configurations

---

<a id="7-system-vs-user-node-pools"></a>

## 7. System vs User Node Pools

| Feature | System Node Pool | User Node Pool |
|---|---|---|
| Main purpose | Kubernetes/system workloads | Application workloads |
| Required | Yes | Optional |
| Typical workloads | Core system components | Applications |
| VM size | Usually general-purpose | Based on workload |
| Scaling | Cluster dependent | Application dependent |
| Production usage | Dedicated system capacity | Application capacity |

### Simple Interview Answer

> **System node pools are used for critical Kubernetes system workloads, while user node pools are primarily used for application workloads. Separating them helps protect cluster system capacity from application resource consumption.**

<a id="8-aks-vm-sizes"></a>

## 8. AKS VM Sizes

Each AKS worker node runs on an Azure VM.

The VM size determines the node's available resources.

Important resources include:

- vCPU
- Memory
- Temporary disk
- Network performance
- Disk capabilities

Example:

```text
VM Size
   ↓
CPU + Memory + Network + Disk Capacity
   ↓
Node Capacity
   ↓
Pod Capacity
```

### Common VM Size Categories

| Category | Typical Usage |
|---|---|
| General Purpose | Normal applications |
| Compute Optimized | CPU-intensive applications |
| Memory Optimized | Memory-intensive applications |
| Storage Optimized | Storage-intensive workloads |
| GPU | AI/ML and GPU workloads |

### Example

A CPU-heavy application may require:

```text
Compute Optimized Node
```

A Java application with high memory requirements may need:

```text
Memory Optimized Node
```

---

<a id="9-choosing-vm-sizes"></a>

## 9. Choosing VM Sizes

Do not select VM sizes only based on CPU.

Consider:

- CPU utilization
- Memory utilization
- Pod resource requests
- Pod resource limits
- Network requirements
- Disk requirements
- Application workload
- Cost
- Scaling requirements

### Example

Suppose an application requires:

```text
CPU    = 2 vCPU
Memory = 8 GB
```

If many Pods run on the node, the node must have enough capacity for:

```text
Application Pods
+
Kubernetes System Pods
+
Operating System
+
Resource Overhead
```

### Production Approach

Start with a suitable VM size → monitor utilization → right-size → enable autoscaling.

Flow:

`Workload Requirements → VM Size → Node Pool → Monitor → Right Size → Autoscale`

## 10. AKS Cluster Architecture

A simplified AKS architecture:

```text
                    Users / Developers
                           │
                           ▼
                    Kubernetes API
                           │
                           ▼
                  ┌─────────────────┐
                  │  AKS Control    │
                  │     Plane       │
                  │                 │
                  │ API Server      │
                  │ Scheduler       │
                  │ Controllers     │
                  │ etcd            │
                  └────────┬────────┘
                           │
             ┌─────────────┴─────────────┐
             ▼                           ▼
      System Node Pool             User Node Pool
             │                           │
       ┌─────┴─────┐               ┌─────┴─────┐
       ▼           ▼               ▼           ▼
     Node        Node            Node        Node
       │           │               │           │
     Pods        Pods            Pods        Pods
```

Compact production flow:

`Users → AKS → Control Plane → Node Pool → Nodes → Pods`

<a id="11-aks-production-architecture"></a>

## 11. AKS Production Architecture

A production AKS environment commonly separates system and application capacity.

```text
Azure
│
└── AKS Cluster
    │
    ├── Managed Control Plane
    │
    ├── System Node Pool
    │   ├── System Node
    │   └── System Node
    │
    └── User Node Pools
        ├── Application Pool
        │   ├── Node
        │   └── Node
        │
        └── Specialized Pool
            ├── Node
            └── Node
```

### Example Production Design

```text
System Pool
→ Kubernetes system workloads

Application Pool
→ Web/API applications

Specialized Pool
→ CPU/Memory/GPU workloads
```

### Production Considerations

- Use multiple nodes for production workloads.
- Use appropriate VM sizes.
- Separate system and application workloads.
- Use multiple availability zones where supported and appropriate.
- Use autoscaling for variable workloads.
- Monitor CPU and memory.
- Define Pod resource requests and limits.
- Avoid running production applications only on a single node.
- Use dedicated node pools for specialized workloads when required.

## 12. AKS Hands-on

### 12.1 Check Azure CLI

```bash
az version
```

Login:

```bash
az login
```

Check subscription:

```bash
az account show
```

---

### 12.2 Create Resource Group

```bash
az group create \
  --name rg-aks-demo \
  --location centralindia
```

---

### 12.3 Create AKS Cluster

Example:

```bash
az aks create \
  --resource-group rg-aks-demo \
  --name aks-demo \
  --node-count 2 \
  --generate-ssh-keys
```

This creates an AKS cluster with worker nodes.

---

### 12.4 Get AKS Credentials

```bash
az aks get-credentials \
  --resource-group rg-aks-demo \
  --name aks-demo
```

Verify:

```bash
kubectl get nodes
```

---

### 12.5 View Node Pools

```bash
az aks nodepool list \
  --resource-group rg-aks-demo \
  --cluster-name aks-demo \
  --output table
```

---

### 12.6 View Kubernetes Nodes

```bash
kubectl get nodes -o wide
```

Check node details:

```bash
kubectl describe node <node-name>
```

---

### 12.7 Add User Node Pool

Example:

```bash
az aks nodepool add \
  --resource-group rg-aks-demo \
  --cluster-name aks-demo \
  --name userpool \
  --node-count 2
```

Verify:

```bash
az aks nodepool list \
  --resource-group rg-aks-demo \
  --cluster-name aks-demo \
  --output table
```

---

### 12.8 Scale Node Pool

```bash
az aks nodepool scale \
  --resource-group rg-aks-demo \
  --cluster-name aks-demo \
  --name userpool \
  --node-count 3
```

Verify:

```bash
kubectl get nodes
```

---

### 12.9 Check VM Size

```bash
az aks nodepool show \
  --resource-group rg-aks-demo \
  --cluster-name aks-demo \
  --name userpool \
  --query vmSize
```

<a id="13-aks-architecture-troubleshooting"></a>

## 13. AKS Architecture Troubleshooting

When an AKS workload has an issue, first determine whether the problem is related to:

```text
Control Plane
→ Node Pool
→ Node
→ Pod
→ Application
```

### Node Not Ready

Check:

```bash
kubectl get nodes
```

Then:

```bash
kubectl describe node <node-name>
```

Check:

- Node status
- Conditions
- CPU
- Memory
- Disk
- Network
- Events

---

### Pod Cannot Be Scheduled

Check:

```bash
kubectl get pods -o wide
```

Then:

```bash
kubectl describe pod <pod-name>
```

Look for:

- Insufficient CPU
- Insufficient memory
- Taints
- Node selectors
- Affinity rules
- Resource requests
- Node availability

Flow:

`Pod Pending → Describe Pod → Events → Scheduling Constraints → Node Capacity → Root Cause`

---

### Node Pool Capacity Problem

Check:

```bash
az aks nodepool list \
  --resource-group rg-aks-demo \
  --cluster-name aks-demo \
  --output table
```

Check:

- Node count
- VM size
- Autoscaling
- Resource utilization
- Workload distribution

<a id="14-production-scenarios"></a>

## 14. Production Scenarios

### Scenario 1: Application Pods Are Consuming System Resources

**What will you check?**

- Node pool design
- Pod resource requests
- Pod resource limits
- System node pool
- Node utilization

**Root Cause:**

Application workloads are consuming resources required by system workloads.

**Fix:**

Use dedicated user node pools and define proper resource requests/limits.

**Interview Answer:**

> I would separate system and application workloads using system and user node pools, define appropriate resource requests and limits, and monitor node utilization.

---

### Scenario 2: Pods Are Pending

**What will you check?**

```bash
kubectl get pods
kubectl describe pod <pod-name>
kubectl get nodes
kubectl describe node <node-name>
```

Check:

- CPU
- Memory
- Taints
- Tolerations
- Node selectors
- Affinity
- Available nodes

**Root Cause:**

The scheduler cannot find a node satisfying the Pod's requirements.

**Fix:**

Depending on the cause:

- Add/scale nodes
- Increase node capacity
- Correct resource requests
- Fix scheduling rules
- Add required tolerations

---

### Scenario 3: Node Pool Is Running at High CPU

**What will you check?**

```text
Node CPU → Pod CPU → Resource Requests → Node Pool Size → Scaling
```

**Fix:**

- Optimize application
- Right-size VM
- Add nodes
- Enable cluster autoscaling
- Distribute workloads

---

### Scenario 4: Different Applications Need Different VM Sizes

**Solution:**

Create separate user node pools.

Example:

```text
System Pool
→ General system workloads

Application Pool
→ Normal applications

Memory Pool
→ Memory-intensive applications
```

Use labels, taints, tolerations, and affinity to control workload placement.

<a id="15-interview-questions"></a>

## 15. Interview Questions

### Q1. What is AKS?

**Answer:**

> AKS is Azure's managed Kubernetes service. Azure manages the Kubernetes control plane, while customers manage workloads, node pools, applications, networking, security, and configurations.

---

### Q2. What is the AKS control plane?

**Answer:**

> The control plane is the management layer of Kubernetes. It includes components such as the API Server, Scheduler, Controllers, and etcd. In AKS, Azure manages the control plane.

---

### Q3. What is a node pool?

**Answer:**

> A node pool is a group of Kubernetes worker nodes with the same configuration. An AKS cluster can have multiple node pools with different VM sizes and workload purposes.

---

### Q4. What is a system node pool?

**Answer:**

> A system node pool is used for critical Kubernetes system workloads. It provides dedicated capacity for system components and cluster add-ons.

---

### Q5. What is a user node pool?

**Answer:**

> A user node pool is primarily used for application workloads. It allows us to separate application workloads from system workloads and use different VM sizes for different applications.

---

### Q6. Why use multiple node pools?

**Answer:**

> We use multiple node pools when workloads have different requirements. For example, normal applications may use general-purpose VMs while memory-intensive applications can use memory-optimized VMs.

---

### Q7. What is the difference between system and user node pools?

**Answer:**

> System pools are intended for critical Kubernetes system workloads, while user pools are intended primarily for application workloads.

---

### Q8. What determines the capacity of an AKS node?

**Answer:**

> The VM size determines the node's CPU, memory, network, and disk capabilities. Pod resource requests and system overhead also affect how much workload the node can run.

---

### Q9. How would you troubleshoot a Pod stuck in Pending state?

**Answer:**

> I would first run `kubectl describe pod` and check Events. Then I would check node availability, CPU and memory capacity, resource requests, taints, tolerations, node selectors, and affinity rules.

---

### Q10. Why should system and application workloads be separated?

**Answer:**

> Separation prevents application workloads from consuming all node resources and affecting critical Kubernetes system components. It also provides better workload isolation and operational control.

---

<a id="16-best-practices"></a>

## 16. Best Practices

### AKS Architecture

- Use system and user node pools appropriately.
- Use multiple nodes for production.
- Select VM sizes based on actual workload requirements.
- Avoid over-provisioning.
- Monitor CPU and memory.
- Define Pod resource requests and limits.
- Use multiple node pools for significantly different workloads.
- Use availability zones where appropriate.
- Enable autoscaling for variable workloads.
- Use labels, taints, tolerations, and affinity when workload placement requires control.
- Review node pool utilization regularly.
- Keep system capacity protected from application workloads.

### Production Architecture

```text
Managed Control Plane
        ↓
System Node Pool
        ↓
User Node Pool(s)
        ↓
Workload-Specific VM Sizes
        ↓
Pods
        ↓
Monitoring + Autoscaling
```

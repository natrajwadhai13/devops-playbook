<a id="1-aks-networking-overview"></a>

## 1. AKS Networking Overview

AKS networking allows Pods, Nodes, Services, Ingress, and external users to communicate with each other.

A typical request flow is:

`User → DNS → Ingress → Service → Pod`

Inside the cluster:

`Pod → Service → Pod`

External application access:

`Internet → Public IP → Ingress/Load Balancer → Service → Pod`

### Main AKS Networking Components

| Component | Purpose |
|---|---|
| Azure CNI | Integrates AKS networking with Azure VNet |
| Azure CNI Overlay | Uses Azure networking for nodes while Pod IPs are from an overlay network |
| Kubenet | Basic Kubernetes networking with node-based Azure networking |
| Service | Stable network endpoint for Pods |
| Ingress | HTTP/HTTPS routing into applications |
| DNS | Name resolution |
| Network Policy | Controls Pod-to-Pod traffic |

### Key Memory

```text
CNI       = Pod Networking
Service   = Stable Application Endpoint
Ingress   = HTTP/HTTPS Routing
DNS       = Name Resolution
Policy    = Pod Traffic Control
```

<a id="2-aks-network-models"></a>

## 2. AKS Network Models

AKS supports different networking approaches.

The two important models are:

- Azure CNI
- Kubenet

Azure CNI also supports an **overlay networking model**.

### Basic Difference

```text
Azure CNI
→ Pods can use Azure VNet networking

Azure CNI Overlay
→ Nodes use Azure VNet
→ Pods use separate overlay Pod CIDR

Kubenet
→ Pods use a separate Pod network
→ Azure networking is primarily associated with nodes
```

The correct networking model depends on:

- IP requirements
- VNet integration
- Existing network architecture
- Network security requirements
- Connectivity requirements
- Cluster size
- Azure service integration

<a id="3-azure-cni"></a>

## 3. Azure CNI

**Azure Container Networking Interface (Azure CNI)** integrates AKS networking with an Azure Virtual Network.

Pods receive IP addresses from the Azure networking environment according to the selected Azure CNI model.

Traditional Azure CNI architecture:

```text
Azure VNet
│
├── Node Subnet
│   ├── Node
│   └── Node
│
└── Pod IPs
    ├── Pod
    ├── Pod
    └── Pod
```

### Why Use Azure CNI?

Azure CNI is useful when Pods need strong integration with Azure networking.

Common reasons:

- Pod-to-Azure resource connectivity
- Integration with Azure networking
- Enterprise networking requirements
- Network security requirements
- Existing VNet architecture

### Important Consideration

Azure CNI requires careful IP planning.

You need enough address space for:

- Nodes
- Pods
- Other Azure resources

Example:

```text
VNet
→ AKS Subnet
→ Nodes
→ Pod IP Capacity
```

Poor IP planning can become a production problem.

---

<a id="4-azure-cni-overlay"></a>

## 4. Azure CNI Overlay

Azure CNI Overlay separates the **node network** and **Pod network**.

Nodes receive IP addresses from the Azure VNet.

Pods receive IP addresses from a separate Pod CIDR.

Conceptually:

```text
Azure VNet
│
└── Node Subnet
    ├── Node 1
    └── Node 2

Pod Overlay Network
├── Pod 1
├── Pod 2
├── Pod 3
└── Pod 4
```

### Why Use Overlay?

Overlay networking can significantly reduce Azure VNet IP consumption compared with assigning VNet IPs directly to every Pod.

It can be useful for:

- Large clusters
- Limited VNet address space
- High Pod density
- Enterprise AKS environments

### Memory

```text
Azure CNI
→ Azure VNet-based Pod networking

Azure CNI Overlay
→ Azure VNet for Nodes
→ Overlay network for Pods
```

---

<a id="5-kubenet"></a>

## 5. Kubenet

**Kubenet** is a basic Kubernetes networking model.

Nodes receive Azure VNet IP addresses, while Pods use a separate Pod address range.

Conceptually:

```text
Azure VNet
│
└── Node Subnet
    ├── Node 1
    └── Node 2

Pod Network
├── Pod 1
├── Pod 2
└── Pod 3
```

Kubenet generally consumes fewer Azure VNet IP addresses because Pod IPs are not individually allocated from the Azure VNet subnet in the same way as traditional Azure CNI.

### Important

Kubenet requires routing between the Pod network and Azure network.

For production environments, networking requirements should be evaluated carefully before choosing it.

---

<a id="6-azure-cni-vs-kubenet"></a>

## 6. Azure CNI vs Kubenet

| Feature | Azure CNI | Kubenet |
|---|---|---|
| Azure VNet integration | Strong | More limited |
| Pod IP model | Azure networking based | Separate Pod network |
| VNet IP consumption | Higher with traditional model | Lower |
| Enterprise integration | Strong | Depends on requirements |
| IP planning | Important | Pod CIDR + node subnet |
| Azure resource connectivity | Strong | Requires appropriate routing |
| Large-scale planning | Requires careful IP design | Can reduce VNet IP consumption |

### Simple Interview Answer

> **Azure CNI provides stronger integration between AKS Pods and Azure networking, while Kubenet uses a separate Pod network and generally consumes fewer Azure VNet IP addresses.**

### Azure CNI Overlay

Do not confuse:

```text
Azure CNI
```

with:

```text
Azure CNI Overlay
```

Overlay provides Azure VNet networking to nodes while using a separate overlay address space for Pods.

<a id="7-kubernetes-service"></a>

## 7. Kubernetes Service

A Kubernetes **Service** provides a stable network endpoint for a group of Pods.

Pods are temporary.

Their IP addresses can change when Pods are recreated.

A Service provides a stable way to reach them.

Flow:

`Client → Service → Pod`

Example:

```text
Service
  │
  ├── Pod 1
  ├── Pod 2
  └── Pod 3
```

The Service selects Pods using labels.

Example:

```yaml
selector:
  app: my-app
```

Pods:

```yaml
labels:
  app: my-app
```

The Service routes traffic to matching Pods.

<a id="9-clusterip"></a>

## 9. ClusterIP

**ClusterIP** is the default Kubernetes Service type.

It provides an internal virtual IP.

Example:

```text
Pod A
  ↓
ClusterIP Service
  ↓
Pod B
```

It is normally used for:

- Internal APIs
- Microservices
- Databases
- Internal applications

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-api
spec:
  type: ClusterIP
  selector:
    app: my-api
  ports:
    - port: 80
      targetPort: 8080
```

Access from inside the cluster:

```text
http://my-api
```

### Memory

`ClusterIP = Internal Service`

---

<a id="10-nodeport"></a>

## 10. NodePort

NodePort exposes a Service through a port on each node.

Flow:

`Client → Node IP:NodePort → Service → Pod`

Example:

```yaml
spec:
  type: NodePort
```

A NodePort normally uses a port from the Kubernetes NodePort range.

### Use Case

Useful for:

- Testing
- Development
- Specific infrastructure scenarios

For modern production AKS applications, direct NodePort exposure is generally less preferred than using an appropriate LoadBalancer or Ingress architecture.

### Memory

`NodePort = Node IP + Port`

---

<a id="11-loadbalancer"></a>

## 11. LoadBalancer

A Kubernetes `LoadBalancer` Service can provision an Azure Load Balancer integration.

Flow:

`Internet → Azure Load Balancer → Service → Pods`

Example:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-app
spec:
  type: LoadBalancer
  selector:
    app: my-app
  ports:
    - port: 80
      targetPort: 8080
```

Check:

```bash
kubectl get service
```

You may see:

```text
NAME     TYPE           EXTERNAL-IP
my-app   LoadBalancer   <public-ip>
```

### Memory

`LoadBalancer = External Network Load Balancing`

<a id="12-ingress"></a>

## 12. Ingress

An **Ingress** provides HTTP/HTTPS routing into Kubernetes applications.

Instead of exposing every application separately, one entry point can route traffic to multiple Services.

Example:

```text
https://example.com/app1 → Service app1
https://example.com/app2 → Service app2
```

Architecture:

```text
Internet
   ↓
Ingress
   ├── /app1 → Service 1 → Pods
   └── /app2 → Service 2 → Pods
```

### Ingress Can Handle

- Host-based routing
- Path-based routing
- TLS termination
- HTTP/HTTPS routing
- Application-level routing

### Host-Based Routing

```text
api.example.com → API Service
web.example.com → Web Service
```

### Path-Based Routing

```text
example.com/api → API Service
example.com/web → Web Service
```

---

<a id="13-ingress-vs-service"></a>

## 13. Ingress vs Service

| Feature | Service | Ingress |
|---|---|---|
| Purpose | Stable Pod endpoint | HTTP/HTTPS routing |
| Layer | Mainly L4/L3 behavior depending on type | L7 |
| Pod discovery | Yes | Uses Services |
| Host routing | No | Yes |
| Path routing | No | Yes |
| TLS | Not its main responsibility | Commonly handled |
| Multiple applications | Can expose individually | One entry point can route many apps |

### Simple Interview Answer

> **A Service provides stable connectivity to Pods, while Ingress provides HTTP/HTTPS routing to one or more Services based on host or path rules.**

<a id="14-aks-dns"></a>

## 14. AKS DNS

DNS allows applications and services to communicate using names instead of IP addresses.

Inside Kubernetes, **CoreDNS** is commonly used for cluster DNS.

Example:

```text
my-api
```

or:

```text
my-api.default.svc.cluster.local
```

The general Kubernetes Service DNS format is:

```text
<service>.<namespace>.svc.cluster.local
```

Example:

```text
my-api.production.svc.cluster.local
```

### Pod-to-Service Flow

```text
Pod
 ↓
DNS Query
 ↓
CoreDNS
 ↓
Service IP
 ↓
Backend Pods
```

### Check CoreDNS

```bash
kubectl get pods -n kube-system
```

Filter:

```bash
kubectl get pods -n kube-system | grep -i coredns
```

Check DNS service:

```bash
kubectl get service -n kube-system
```

---

### External DNS

For external applications:

```text
User
 ↓
DNS
 ↓
Public IP
 ↓
Ingress
 ↓
Service
 ↓
Pod
```

For Azure private networking, **Azure Private DNS** can be used with private endpoints and private DNS zones.

<a id="15-network-policies"></a>

## 15. Network Policies

A Kubernetes **NetworkPolicy** controls network traffic to and from Pods.

Without appropriate policies, workloads may have broader connectivity than required.

Network policies can control:

- Pod-to-Pod traffic
- Namespace traffic
- Ingress traffic
- Egress traffic

### Example

Suppose:

```text
Frontend → API → Database
```

We may want:

```text
Frontend → API       Allowed
API → Database       Allowed
Frontend → Database  Blocked
```

Conceptually:

```text
Frontend
   ↓ Allowed
API
   ↓ Allowed
Database

Frontend ──X──> Database
```

### Why Use Network Policies?

They provide workload-level network segmentation.

Example:

```text
Namespace A
→ Can communicate with Namespace B

Namespace C
→ Cannot communicate with Namespace B
```

### Important

Network policies are not a replacement for:

- NSGs
- Azure Firewall
- WAF
- Application security
- Identity-based authorization

They operate at the Kubernetes workload/network layer.

## 16. AKS Networking Architecture

A typical AKS networking flow:

```text
                         Internet
                            │
                            ▼
                           DNS
                            │
                            ▼
                         Ingress
                            │
                            ▼
                         Service
                            │
                    ┌───────┴───────┐
                    ▼               ▼
                  Pod             Pod
                    │
                    ▼
              Network Policy
```

For internal communication:

`Pod → DNS → Service → Backend Pod`

For external communication:

`User → DNS → Ingress → Service → Pod`

## 17. Production Networking Architecture

A common production pattern is:

```text
Internet
   ↓
Public DNS
   ↓
WAF / Application Gateway / Ingress
   ↓
AKS Service
   ↓
Network Policy
   ↓
Application Pods
   ↓
Internal Services
```

For multiple applications:

```text
Internet
   ↓
DNS
   ↓
Ingress
   ├── example.com/        → Web Service
   ├── example.com/api     → API Service
   └── example.com/admin   → Admin Service
```

### Internal Microservices

```text
Frontend Pod
     ↓
API Service
     ↓
API Pods
     ↓
Database Service
     ↓
Database Pods / Azure Database
```

### Network Segmentation

```text
Internet
   ↓
Ingress
   ↓
Frontend
   ↓
API
   ↓
Database
```

Apply network policies so that only required communication is allowed.

<a id="19-networking-troubleshooting"></a>

## 19. Networking Troubleshooting

Use this sequence:

`Issue → DNS → IP → Service → Endpoints → Ingress → Network Policy → NSG/Firewall → Application`

### Scenario: Application Is Not Reachable

Check:

```bash
kubectl get pods
kubectl get svc
kubectl get endpoints
kubectl get ingress
```

Then:

```bash
kubectl describe ingress <ingress-name>
```

Check:

- DNS
- Public IP
- Ingress
- Service
- Service selector
- Endpoints
- Pod readiness
- Network policies
- NSG
- Firewall
- Application

---

### DNS Failure

Symptom:

```text
Could not resolve host
```

Check:

```bash
kubectl get pods -n kube-system
```

Check CoreDNS:

```bash
kubectl logs -n kube-system <coredns-pod>
```

Test from a Pod:

```bash
nslookup my-api
```

Flow:

`DNS Failure → CoreDNS → Service Name → Namespace → DNS Configuration → Root Cause`

---

### Service Returns No Response

Check:

```bash
kubectl get svc
kubectl get endpoints
kubectl get pods -o wide
```

Common causes:

- Wrong Service selector
- Pod not Ready
- Incorrect `targetPort`
- Application not listening
- Network Policy blocking traffic

---

### Ingress Returns 404

Check:

```bash
kubectl get ingress
kubectl describe ingress <ingress-name>
kubectl get svc
```

Common causes:

- Wrong host
- Wrong path
- Wrong backend Service
- Ingress rule mismatch
- DNS points to wrong endpoint

Flow:

`404 → Host → Path → Ingress Rule → Service → Application`

---

### Ingress Returns 502

Common causes:

- Backend Pod unavailable
- Service has no endpoints
- Wrong Service port
- Wrong targetPort
- Application not listening
- Backend connection failure

Check:

```bash
kubectl get pods
kubectl get svc
kubectl get endpoints
kubectl describe ingress <ingress-name>
```

Flow:

`502 → Ingress → Service → Endpoints → Pod → Application Port`

---

### Ingress Returns 503

Common causes:

- No healthy backend
- Pods not Ready
- Service has no usable endpoints
- Ingress controller cannot reach backend

Check:

```bash
kubectl get pods
kubectl get endpoints
kubectl describe service <service-name>
```

<a id="20-production-scenarios"></a>

## 20. Production Scenarios

### Scenario 1: Pod Can Reach One Service but Not Another

**What will you check?**

```text
Source Pod
→ Destination Service
→ DNS
→ Service IP
→ Endpoints
→ Network Policy
→ Application
```

Commands:

```bash
kubectl get svc
kubectl get endpoints
kubectl get networkpolicy
kubectl describe networkpolicy <policy-name>
```

**Possible Root Cause:**

Network Policy is blocking traffic.

**Fix:**

Allow only the required source-to-destination traffic.

**Interview Answer:**

> I would verify DNS resolution, Service endpoints, Pod readiness, and Network Policies. If DNS and endpoints are correct, I would check whether a NetworkPolicy is blocking the traffic.

---

### Scenario 2: Application Works Inside AKS but Not From Internet

**Check:**

```text
Application
→ Pod
→ Service
→ Ingress
→ Public IP
→ DNS
```

Commands:

```bash
kubectl get pods
kubectl get svc
kubectl get ingress
kubectl describe ingress <ingress-name>
```

Possible causes:

- Ingress misconfiguration
- DNS issue
- Public IP issue
- Load balancer issue
- NSG/firewall
- TLS configuration

---

### Scenario 3: Ingress Returns 502

**Check:**

```bash
kubectl get pods
kubectl get svc
kubectl get endpoints
kubectl describe service <service-name>
kubectl describe ingress <ingress-name>
```

**Root Cause Examples:**

- No endpoints
- Wrong target port
- Application not listening
- Backend Pod unavailable

**Fix:**

Correct Service configuration or application/backend availability.

---

### Scenario 4: DNS Name Does Not Resolve

**Check:**

```bash
kubectl get pods -n kube-system
kubectl get svc -n kube-system
```

From a test Pod:

```bash
nslookup my-api
```

**Root Cause:**

Could be CoreDNS, incorrect Service name, incorrect namespace, or DNS configuration.

**Fix:**

Correct DNS/service configuration and restore healthy DNS components.

---

### Scenario 5: Pod-to-Pod Communication Is Blocked

**Check:**

```bash
kubectl get networkpolicy -A
kubectl describe networkpolicy <policy-name>
```

**Root Cause:**

A NetworkPolicy may deny the traffic.

**Fix:**

Create/update the policy to allow only the required communication.

<a id="21-interview-questions"></a>

## 21. Interview Questions

### Q1. What is Azure CNI?

> Azure CNI is an AKS networking model that integrates Kubernetes networking with Azure networking and provides strong VNet integration.

---

### Q2. What is Kubenet?

> Kubenet is a Kubernetes networking model where nodes use Azure VNet networking while Pods use a separate Pod network. It generally consumes fewer Azure VNet IP addresses.

---

### Q3. Azure CNI vs Kubenet?

> Azure CNI provides stronger Azure VNet integration, while Kubenet uses a separate Pod network and generally requires fewer Azure VNet IP addresses.

---

### Q4. What is Azure CNI Overlay?

> Azure CNI Overlay uses Azure networking for nodes while Pods use a separate overlay address space, reducing the need to allocate Azure VNet IPs directly to every Pod.

---

### Q5. What is a Kubernetes Service?

> A Service provides a stable network endpoint for a group of Pods. It abstracts changing Pod IP addresses and routes traffic to matching Pods.

---

### Q6. ClusterIP vs LoadBalancer?

> ClusterIP provides internal cluster access, while LoadBalancer exposes the Service externally through a cloud load balancer.

---

### Q7. What is Ingress?

> Ingress provides HTTP/HTTPS routing into Kubernetes applications. It can route requests based on hostname or URL path and commonly handles TLS termination.

---

### Q8. Service vs Ingress?

> A Service provides stable connectivity to Pods, while Ingress provides Layer 7 HTTP/HTTPS routing to Services.

---

### Q9. What is CoreDNS?

> CoreDNS provides DNS-based service discovery inside Kubernetes. It allows Pods to communicate with Services using DNS names.

---

### Q10. What is NetworkPolicy?

> NetworkPolicy controls allowed network traffic to and from Pods. It can be used to implement workload-level network segmentation.

---

### Q11. Application is working using ClusterIP but not through Ingress. What will you check?

> I would check DNS, Ingress rules, Ingress controller, public IP, TLS configuration, Service backend, endpoints, and application port.

---

### Q12. Ingress returns 502. What will you check?

> I would check the backend Service, endpoints, targetPort, Pod readiness, application listening port, and Ingress configuration.

---

### Q13. Why is IP planning important with Azure CNI?

> Because traditional Azure CNI uses Azure network IP addresses for Pods, insufficient subnet address space can prevent new Pods or nodes from receiving required IPs.

---

### Q14. How would you troubleshoot Pod-to-Pod connectivity?

> I would check Pod IPs, DNS, Service configuration, endpoints, NetworkPolicies, routes, NSGs/firewalls where applicable, and application ports.

---

<a id="22-best-practices"></a>

## 22. Best Practices

### AKS Networking

- Plan VNet and subnet address ranges before cluster deployment.
- Choose Azure CNI, Azure CNI Overlay, or Kubenet based on requirements.
- Avoid unnecessary public exposure.
- Use ClusterIP for internal services.
- Use Ingress for HTTP/HTTPS application routing.
- Use TLS for external application traffic.
- Use DNS instead of hardcoded Pod IP addresses.
- Use Network Policies for workload segmentation.
- Monitor DNS and networking components.
- Validate Service selectors and endpoints.
- Avoid exposing every application using a separate public LoadBalancer when Ingress is more appropriate.
- Keep network architecture documented.

### Production Flow

`Internet → DNS → WAF/Ingress → Service → Network Policy → Pod`

### Internal Flow

`Pod → CoreDNS → ClusterIP Service → Backend Pod`

### Troubleshooting Flow

`Client → DNS → IP → Ingress → Service → Endpoints → Network Policy → Pod → Application`

### One-Minute Interview Summary

> **AKS networking connects Pods, Nodes, Services, and external users. Azure CNI provides strong Azure VNet integration, while Kubenet uses a separate Pod network. Azure CNI Overlay uses Azure networking for nodes and a separate overlay network for Pods. Kubernetes Services provide stable endpoints, with ClusterIP mainly for internal communication and LoadBalancer for external exposure. Ingress provides HTTP/HTTPS host and path-based routing. CoreDNS provides internal service discovery, and Network Policies control Pod-to-Pod traffic. In production, I would plan IP ranges carefully, use private/internal services where possible, use Ingress for HTTP/HTTPS routing, enable TLS, and apply network policies for workload segmentation.**

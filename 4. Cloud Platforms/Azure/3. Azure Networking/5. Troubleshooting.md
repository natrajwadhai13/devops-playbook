# 1. Network Troubleshooting Overview

When an application cannot connect to another service, do not immediately change NSG or firewall rules.

First identify the complete traffic path.

```text
Client → DNS → Route → NSG → Firewall → Load Balancer/App Gateway → Backend → Application Port
```

### Main Areas to Check

| Area          | What to Check                 |
| ------------- | ----------------------------- |
| DNS           | Name resolves to correct IP   |
| Route         | Traffic has a valid path      |
| NSG           | Traffic is allowed            |
| Firewall      | Traffic is not blocked        |
| Port          | Destination port is listening |
| Application   | Service is running            |
| Load Balancer | Backend is healthy            |
| Network       | Connectivity exists           |
| Logs          | Identify where traffic failed |

### Core Troubleshooting Principle

```text
DNS → IP → Route → Security → Port → Application
```

<a id="3-nsg-rules-troubleshooting"></a>

# 3. NSG Rules Troubleshooting

Network Security Group controls inbound and outbound network traffic.

Rules are based on:

```text
Source
Destination
Port
Protocol
Direction
Priority
Action
```

Example:

```text
Source:      10.0.1.0/24
Destination: 10.0.2.10
Protocol:    TCP
Port:        443
Priority:    100
Action:      Allow
```

### NSG Rule Priority

Lower number = higher priority.

Example:

```text
Priority 100 → Deny TCP 443
Priority 200 → Allow TCP 443
```

The deny rule wins because `100` is evaluated first.

### Troubleshooting Questions

```text
Is NSG attached?
Is traffic inbound or outbound?
What is the source IP?
What is the destination IP?
Which port?
Which protocol?
Which rule matches?
Is there an earlier deny rule?
```

<a id="4-effective-nsg-rules"></a>

# 4. Effective NSG Rules

In Azure, NSGs can exist at:

```text
Subnet
NIC
```

Traffic can therefore be affected by both.

### Example

```text
Subnet NSG → Allow 443
NIC NSG    → Deny 443
```

The effective result is:

```text
TCP 443 → Blocked
```

### Check NSG

```bash
az network nsg rule list \
  --resource-group <resource-group> \
  --nsg-name <nsg-name> \
  --output table
```

### Check NIC

```bash
az network nic show \
  --resource-group <resource-group> \
  --name <nic-name>
```

### Check Effective NSG

```bash
az network nic list-effective-nsg \
  --resource-group <resource-group> \
  --name <nic-name>
```

### Production Interview Answer

> I check both subnet-level and NIC-level NSGs because traffic can be affected by either. I verify the effective NSG rules and identify the exact rule and priority that is allowing or denying the traffic.

# 5. Route Table Troubleshooting

A route determines where network traffic should go.

Azure uses:

- System routes
- User Defined Routes
- BGP routes

### Example

```text
Application VM
     ↓
Route Table
     ↓
10.0.2.0/24
     ↓
Next Hop
     ↓
Database Subnet
```

### Common Route Problems

```text
Missing route
Wrong next hop
Incorrect address prefix
UDR overriding expected route
Traffic forced through firewall
Asymmetric routing
```

### Check Route Table

```bash
az network route-table route list \
  --resource-group <resource-group> \
  --route-table-name <route-table-name> \
  --output table
```

### Show Route Table

```bash
az network route-table show \
  --resource-group <resource-group> \
  --name <route-table-name>
```

<a id="6-effective-routes"></a>

# 6. Effective Routes

When troubleshooting, effective routes are more useful than checking only the route table configuration.

### Check Effective Routes

```bash
az network nic show-effective-route-table \
  --resource-group <resource-group> \
  --name <nic-name>
```

Example output concept:

```text
Address Prefix     Next Hop Type
10.0.0.0/16        VnetLocal
0.0.0.0/0          VirtualAppliance
10.0.2.0/24        VnetLocal
```

### Important

If you see:

```text
0.0.0.0/0 → VirtualAppliance
```

traffic may be forced through a firewall/NVA.

### Route Troubleshooting Flow

```text
Source → Effective Route → Next Hop → Firewall/NVA → Destination
```

<a id="7-dns-troubleshooting"></a>

# 7. DNS Troubleshooting

DNS converts hostnames into IP addresses.

```text
my-api.example.com
        ↓
DNS
        ↓
10.0.2.10
```

If DNS fails, the application may appear to have a network problem even though the network itself is working.

### Common DNS Problems

- Incorrect DNS server
- DNS record missing
- Wrong IP address
- Private DNS zone issue
- DNS forwarding problem
- DNS resolution blocked
- Incorrect hostname
- Cached DNS record

### Check DNS Configuration

Linux:

```bash
cat /etc/resolv.conf
```

Windows:

```powershell
ipconfig /all
```

### Test DNS

```bash
nslookup example.com
```

or:

```bash
nslookup my-api.example.com
```

### Example

```text
nslookup my-api.example.com

Name:    my-api.example.com
Address: 10.0.2.10
```

This confirms that the hostname resolved to an IP.

<a id="8-port-troubleshooting"></a>

# 8. Port Troubleshooting

After DNS and routing are confirmed, check the destination port.

Common ports:

| Port | Protocol / Service |
| ---- | ------------------ |
| 22   | SSH                |
| 53   | DNS                |
| 80   | HTTP               |
| 443  | HTTPS              |
| 3389 | RDP                |
| 1433 | SQL Server         |
| 3306 | MySQL              |
| 5432 | PostgreSQL         |
| 8080 | Application        |
| 8443 | HTTPS/Application  |

### Linux — Check Listening Ports

```bash
ss -lntp
```

Specific port:

```bash
ss -lntp | grep :8080
```

Alternative:

```bash
netstat -lntp
```

### Windows

```powershell
netstat -ano
```

Specific port:

```powershell
netstat -ano | findstr :443
```

### Test TCP Port from Windows

```powershell
Test-NetConnection 10.0.2.10 -Port 443
```

Example:

```text
TcpTestSucceeded : True
```

If:

```text
TcpTestSucceeded : False
```

check:

```text
NSG
Firewall
Route
Service
Port
```

<a id="9-curl-troubleshooting"></a>

# 9. curl Troubleshooting

`curl` is one of the most useful commands for HTTP/HTTPS troubleshooting.

### Basic Request

```bash
curl https://example.com
```

### Show Headers

```bash
curl -I https://example.com
```

### Verbose Mode

```bash
curl -v https://example.com
```

Verbose mode helps identify:

```text
DNS resolution
TCP connection
TLS handshake
HTTP request
HTTP response
```

### Test HTTP

```bash
curl -v http://10.0.2.10:8080
```

### Test HTTPS

```bash
curl -vk https://example.com
```

`-k` skips certificate verification.

Use `-k` mainly for troubleshooting; do not use it as a production security fix.

### Test Specific Host Header

```bash
curl -v \
  -H "Host: my-api.example.com" \
  http://10.0.2.10
```

Useful when troubleshooting:

- Load Balancers
- Application Gateway
- Reverse proxies
- Host-based routing

### Test API

```bash
curl -X GET https://my-api.example.com/api/health
```

### POST Request

```bash
curl -X POST \
  -H "Content-Type: application/json" \
  -d '{"name":"test"}' \
  https://my-api.example.com/api/users
```

### curl Troubleshooting Interpretation

```text
Could not resolve host
→ DNS problem

Connection timed out
→ Network/route/firewall/NSG problem

Connection refused
→ Host reachable but port/service not accepting connection

SSL certificate error
→ TLS/certificate problem

HTTP 404
→ Application/routing/path problem

HTTP 401/403
→ Authentication/authorization problem

HTTP 500
→ Application/server problem
```

<a id="10-nslookup-troubleshooting"></a>

# 10. nslookup Troubleshooting

`nslookup` checks DNS resolution.

### Basic

```bash
nslookup example.com
```

### Query Specific DNS Server

```bash
nslookup example.com 8.8.8.8
```

This helps determine whether the problem is with the configured DNS server.

### Internal DNS

```bash
nslookup my-api.internal
```

### Troubleshooting

```text
Hostname
   ↓
nslookup
   ↓
IP?
   ↓
YES → Continue to network troubleshooting
NO  → Investigate DNS
```

### Common Results

```text
NXDOMAIN
→ DNS record does not exist

Timeout
→ DNS server/network issue

Wrong IP
→ Incorrect DNS record

Correct IP
→ DNS likely working
```

<a id="11-traceroute-and-tracert"></a>

# 11. traceroute and tracert

`traceroute` shows the network path toward a destination.

Linux:

```bash
traceroute example.com
```

Windows:

```cmd
tracert example.com
```

### Example

```text
Source
 ↓
Hop 1
 ↓
Hop 2
 ↓
Hop 3
 ↓
Destination
```

### Useful for

- Routing problems
- Network path analysis
- Identifying where packets stop
- Detecting unexpected routing

### Important Azure Note

A timeout (`* * *`) at a hop does **not automatically mean the network is broken**.

Some routers/firewalls simply do not respond to traceroute probes.

Therefore:

```text
traceroute timeout ≠ automatically network failure
```

Always combine traceroute with:

```text
curl
nslookup
Test-NetConnection
Network Watcher
Application logs
```

### Linux TCP Traceroute

Depending on the environment:

```bash
traceroute -T -p 443 example.com
```

This can be useful when investigating HTTPS connectivity.

Concept:

```text

Port

        ↓

        ↓
Allow / Deny
```

Helps determine where Azure will send traffic.

```text
Source VM
   ↓
Next Hop
   ↓
```

Useful for testing connectivity between:


### Packet Capture

Useful when normal troubleshooting is not enough.

It can help identify:

```text

Retransmissions

Unexpected traffic
```

| ----------------------- | --------------------- | ------------------- |
| DNS name not resolving  | `nslookup`            | DNS                 |
| Timeout                 | Route/NSG/Firewall    | Network/security    |
| Connection refused      | Port/service          | Application         |

| 401                     | HTTP response         | Authentication      |

| 500                     | Application logs      | Application         |

| SSH unavailable         | Port 22               | NSG/firewall/SSH    |

# 16. Interview Questions

### Q1. How do you troubleshoot a network connectivity issue in Azure?

### Interview Answer

> I first identify the source, destination, protocol and port. Then I verify DNS resolution, effective routes, effective NSG rules, firewall rules and the destination port. After network connectivity is confirmed, I test the application using curl and check application logs.

---

### Q2. What is the difference between timeout and connection refused?

```text
Timeout
→ Connection is not completing
→ Check route, NSG, firewall, network path

Connection Refused
→ Destination is reachable
→ No service is accepting the connection or it is actively rejecting it
```


### Q13. How do you troubleshoot an API returning 404?

Use:

```bash

```

Then check:

```text

Host header
Gateway routing
Backend path
Application endpoint
```

---

### Q14. How do you troubleshoot an API returning 500?

Focus on:

```text
Application logs
Backend dependencies
Database
Configuration
Application errors
```

A 500 indicates the HTTP request reached the application/server layer.

---

### Q15. Explain your production network troubleshooting approach.

### Interview Answer

> My approach is to troubleshoot layer by layer. I start with DNS and confirm the destination IP. Then I check effective routes, NSG rules and firewall policies. Next I test the destination port using Test-NetConnection or other TCP tools. For HTTP or HTTPS, I use curl to validate TLS and the HTTP response. Finally, I check application and infrastructure logs to identify the root cause. I avoid changing security rules until I know exactly which layer is blocking the traffic.

<a id="17-best-practices"></a>

# 17. Best Practices

### Network Troubleshooting

- Identify source and destination first.
- Always identify protocol and port.
- Check DNS before assuming a network problem.
- Check effective routes rather than only configured routes.
- Check effective NSG rules.
- Check firewall policies.
- Test the port separately from the application.
- Use `curl -v` for HTTP/HTTPS.
- Use `nslookup` for DNS.
- Use `traceroute` only as supporting evidence.
- Use Azure Network Watcher for Azure-specific diagnosis.
- Check logs before making configuration changes.
- Make the smallest possible security change.
- Verify after every fix.

### Golden Rule

```text
Don't change → Check first → Identify root cause → Fix → Verify
```

## Troubleshooting Decision Tree

```text
Hostname fails?
   ↓ YES
Check DNS

DNS works?
   ↓ YES
Check IP connectivity

Connectivity fails?
   ↓
Check Route → NSG → Firewall

Port fails?
   ↓
Check Service → Listening Port

Port works?
   ↓
Use curl

HTTP error?
   ↓
Check Application / Gateway / Backend

Issue fixed?
   ↓
Verify → Monitor → Document
```

## Most Important Commands

```text
nslookup       → DNS
curl -v        → HTTP/HTTPS
ss -lntp       → Linux listening ports
Test-NetConnection → Windows TCP test
traceroute     → Linux network path
tracert        → Windows network path
show-effective-route-table → Azure routing
list-effective-nsg         → Azure NSG
```

## Interview Memory Trick

```text
DNS      = Where is the server?
Route    = Which path should traffic take?
NSG      = Is traffic allowed?
Firewall = Is centralized security blocking it?
Port     = Is the service listening?
curl     = Does the application respond?
nslookup = Does DNS resolve?
traceroute = What path does traffic take?
Logs     = Why did it fail?
```

## Complete Production Flow

```text
Issue → Source → Destination → DNS → IP → Route → NSG → Firewall → Port → curl → Application Logs → Root Cause → Fix → Verify
```

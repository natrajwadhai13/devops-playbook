# 1. Traffic Management Overview

<a id="1-traffic-management-overview"></a>

Azure provides different services depending on where and how traffic needs to be distributed.

| Service | Layer / Scope | Main Purpose |
|---|---|---|
| **Load Balancer** | Layer 4 | TCP/UDP load balancing |
| **Application Gateway** | Layer 7 | HTTP/HTTPS application routing |
| **WAF** | Layer 7 Security | Protect web applications |
| **Traffic Manager** | DNS | Global traffic distribution |
| **Front Door** | Global Layer 7 | Global HTTP/HTTPS application delivery |

### Memory Trick

```text
Load Balancer  = L4
Application Gateway = L7
WAF            = Web Security
Traffic Manager = DNS Routing
Front Door     = Global Web Delivery
```

### Basic Architecture

```text
Internet
   ↓
Front Door / Traffic Manager
   ↓
Application Gateway + WAF
   ↓
Load Balancer
   ↓
VM / VMSS / Application
```

Not every application needs every service.

# 2. Azure Load Balancer

<a id="2-azure-load-balancer"></a>

## What is Azure Load Balancer?

Azure Load Balancer is a Layer 4 load-balancing service that distributes TCP and UDP traffic across backend resources.

### Main Use Cases

- VM load balancing
- VM Scale Sets
- High availability
- Internal application traffic
- Internet-facing applications
- TCP/UDP workloads

### Traffic Flow

```text
Client
  ↓
Public Load Balancer
  ↓
Health Probe
  ↓
Backend Pool
  ├── VM-1
  ├── VM-2
  └── VM-3
```

---

## Load Balancer Types

| Type | Purpose |
|---|---|
| Public Load Balancer | Internet-facing traffic |
| Internal Load Balancer | Private VNet traffic |

### Public Load Balancer

```text
Internet
   ↓
Public IP
   ↓
Load Balancer
   ↓
VM/VMSS
```

### Internal Load Balancer

```text
Application
   ↓
Private IP
   ↓
Internal Load Balancer
   ↓
Backend VMs
```

## Important Components

| Component | Purpose |

| Backend Pool | Backend VM/NIC/VMSS resources |
| Health Probe | Checks backend health |

```text
        ↓

        ↓
Backend Pool
 ├── VM-1

```

# 4. Load Balancing Rules and Health Probes

<a id="4-load-balancing-rules-and-health-probes"></a>

## Health Probe

A health probe checks whether a backend instance is healthy.

Example:

```text
Probe:
Protocol = TCP
Port = 443
```

or:

```text
Protocol = HTTP
Port = 80
Path = /health
```

### Flow

```text
Load Balancer
     ↓
Health Probe
     ↓
VM-1 → Healthy
VM-2 → Unhealthy
VM-3 → Healthy
```

Traffic is sent only to healthy backend instances.

---

## Important Interview Point

A load balancer being healthy does **not** mean the application is healthy.

A good HTTP health endpoint should validate the application state where appropriate.

Example:

```text
/health
```

---

## Create Load Balancer

Create public IP:

```bash
az network public-ip create \
  --resource-group rg-network \
  --name lb-public-ip \
  --sku Standard
```

Create load balancer:

```bash
az network lb create \
  --resource-group rg-network \
  --name lb-prod \
  --sku Standard \
  --public-ip-address lb-public-ip \
  --frontend-ip-name frontend
```

Create backend pool:

```bash
az network lb address-pool create \
  --resource-group rg-network \
  --lb-name lb-prod \
  --name backend-pool
```

# 5. Application Gateway

<a id="5-application-gateway"></a>

## What is Application Gateway?

Azure Application Gateway is a Layer 7 web traffic load balancer and reverse proxy for HTTP/HTTPS applications.

It can make routing decisions based on application-level information.

### Main Features

- HTTP/HTTPS load balancing
- URL-based routing
- Host-based routing
- TLS termination
- SSL/TLS certificates
- Cookie-based session affinity
- Health probes
- Web Application Firewall integration
- Autoscaling depending on configuration/tier

---

## Basic Flow

```text
Client
  ↓
Application Gateway
  ↓
Routing Rule
  ├── /api → Backend API
  ├── /admin → Admin App
  └── / → Frontend
```

# 7. Application Gateway Routing

<a id="7-application-gateway-routing"></a>

## Path-Based Routing

Different URL paths can go to different backend pools.

```text
example.com/
      ↓
Frontend Backend

example.com/api/
      ↓
API Backend

example.com/admin/
      ↓
Admin Backend
```

### Example

```text
Client
  ↓
Application Gateway
  ├── /api/*    → API Servers
  ├── /admin/*  → Admin Servers
  └── /*        → Web Servers
```

---

## Host-Based Routing

Different hostnames can route to different backends.

```text
www.example.com
      ↓
Frontend Backend

api.example.com
      ↓
API Backend

admin.example.com
      ↓
Admin Backend
```

---

## TLS Termination

Application Gateway can terminate HTTPS at the gateway.

```text
Client
   │ HTTPS
   ↓
Application Gateway
   │ HTTP/HTTPS
   ↓
Backend
```

Benefits:

- Central certificate management
- TLS termination
- Backend architecture simplification
- Centralized HTTPS configuration

# 8. Web Application Firewall WAF

<a id="8-web-application-firewall-waf"></a>

## What is WAF?

Web Application Firewall protects web applications from common application-layer attacks.

It works at Layer 7.

### Common Threats

- SQL Injection
- Cross-Site Scripting XSS
- Malicious HTTP requests
- Common web attack patterns
- Protocol violations

### Flow

```text
Internet
   ↓
WAF
   ↓
Application Gateway / Front Door
   ↓
Application
```

---

## WAF Modes

| Mode | Purpose |
|---|---|
| Detection | Detect and log suspicious requests |
| Prevention | Detect and block suspicious requests |

### Production Approach

Start with:

```text
Detection → Monitor → Tune Rules → Prevention
```

Do not immediately block everything without understanding legitimate application traffic.

---

## WAF Rule Concept

Example:

```text
Request
   ↓
WAF Rules
   ↓
Allowed → Application
Blocked → 403
```

### Important

WAF is not a replacement for:

- NSG
- Azure Firewall
- Identity/access control
- Secure coding
- API authentication
- Endpoint security

WAF protects mainly at the **web application layer**.

# 9. Application Gateway vs Load Balancer

<a id="9-application-gateway-vs-load-balancer"></a>

| Feature | Load Balancer | Application Gateway |
|---|---|---|
| Layer | L4 | L7 |
| Protocol | TCP/UDP | HTTP/HTTPS |
| URL routing | No | Yes |
| Host routing | No | Yes |
| TLS termination | No | Yes |
| WAF | No | Yes |
| Web application routing | Limited | Advanced |
| Non-HTTP workloads | Yes | No |
| Typical use | Network load balancing | Web application delivery |

### Memory Trick

```text
Load Balancer = Port-based
Application Gateway = URL/Host-based
```

# 10. Azure Traffic Manager

<a id="10-azure-traffic-manager"></a>

## What is Traffic Manager?

Azure Traffic Manager is a DNS-based traffic routing service.

It directs users to appropriate application endpoints based on routing rules and endpoint health.

### Important

Traffic Manager does **not** directly proxy application traffic.

It responds to DNS queries and directs clients to an endpoint.

### Flow

```text
User
 ↓
DNS Query
 ↓
Traffic Manager
 ↓
Selected Endpoint
 ↓
Application
```

---

# 11. Traffic Manager Routing Methods

<a id="11-traffic-manager-routing-methods"></a>

## Priority

Used for primary/secondary failover.

```text
Primary
   ↓
If unhealthy
   ↓
Secondary
```

Use case:

`Region-A → Region-B`

---

## Weighted

Distributes traffic based on configured weights.

Example:

```text
Endpoint-A = 80
Endpoint-B = 20
```

Useful for:

- Gradual migration
- Testing
- Traffic distribution

---

## Performance

Routes users to the endpoint with the lowest network latency based on Traffic Manager's performance routing model.

```text
User → Closest/Best-performing endpoint
```

Useful for global applications.

---

## Geographic

Routes users based on geographic location.

```text
India → India Endpoint
US → US Endpoint
Europe → Europe Endpoint
```

Useful when applications need geographic traffic separation.

---

## Multivalue

Returns multiple healthy endpoints in DNS responses.

Useful for improving availability.

---

## Subnet

Routes users based on their source IP subnet.

---

# 12. Azure Front Door

<a id="12-azure-front-door"></a>

## What is Azure Front Door?

Azure Front Door is a global application delivery service for HTTP/HTTPS applications.

It provides global routing, acceleration, health-based failover, TLS termination, and integration with web application security capabilities.

### Basic Flow

```text
User
  ↓
Azure Front Door
  ↓
Global Routing
  ↓
Healthy Backend
  ↓
Application
```

---

## Front Door Features

- Global HTTP/HTTPS routing
- Anycast-based global entry
- TLS termination
- Health probes
- URL-based routing
- Host-based routing
- Backend/origin failover
- Web Application Firewall integration
- Caching/CDN capabilities depending on Front Door configuration
- Global application acceleration

---

## Global Architecture

```text
                    Azure Front Door
                         │
              ┌──────────┴──────────┐
              │                     │
          Region-A               Region-B
              │                     │
          Application           Application
```

If Region-A becomes unhealthy:

```text
User
 ↓
Front Door
 ↓
Region-B
```

---

# 13. Traffic Manager vs Front Door

<a id="13-traffic-manager-vs-front-door"></a>

| Feature | Traffic Manager | Front Door |
|---|---|---|
| Type | DNS-based | Global Layer 7 |
| Traffic proxy | No | Yes |
| HTTP/HTTPS | DNS routing | HTTP/HTTPS delivery |
| Global routing | Yes | Yes |
| URL-based routing | Limited through endpoint design | Yes |
| TLS termination | No | Yes |
| WAF integration | No direct WAF function | Yes |
| Caching/acceleration | No | Yes |
| Failover | DNS-based | Application delivery |
| Best use | DNS-level endpoint selection | Global web application delivery |

### Memory Trick

```text
Traffic Manager = "Which endpoint should DNS return?"
Front Door      = "Which healthy application endpoint should receive the request?"
```

# 16. Traffic Troubleshooting

<a id="16-traffic-troubleshooting"></a>

## Standard Flow

```text
DNS
 ↓
Public IP / Front Door
 ↓
Listener
 ↓
Routing Rule
 ↓
Health Probe
 ↓
Backend Pool
 ↓
NSG / Firewall
 ↓
Application
```

---

## Scenario: Load Balancer Returns 502/Connection Failure

Check:

1. Backend pool
2. Health probe
3. NSG
4. Backend port
5. Application listener
6. VM health
7. Route table

### Linux

```bash
ss -lntp
```

```bash
curl http://localhost:8080/health
```

---

## Scenario: Application Gateway Backend Unhealthy

Check:

```text
Listener
 ↓
Routing Rule
 ↓
Backend Settings
 ↓
Health Probe
 ↓
Backend
```

Common causes:

- Wrong backend port
- Wrong protocol
- Wrong health probe path
- NSG blocking gateway subnet
- Application not listening
- TLS certificate mismatch
- Host header issue

---

## Scenario: WAF Blocks Legitimate Request

### Check

- WAF logs
- Rule ID
- Request URL
- Request body
- Query parameters
- False-positive pattern

### Fix

Do not simply disable WAF.

Instead:

`Identify Rule → Validate Request → Tune Exclusion/Rule → Test → Monitor`

---

## Scenario: Traffic Manager Sends Users to Wrong Region

Check:

- DNS cache
- TTL
- Endpoint health
- Routing method
- Endpoint priority/weight
- Geographic/performance configuration

Remember:

Traffic Manager works through DNS, so changes are affected by DNS caching and TTL.

---

## Scenario: Front Door Sends Traffic to Unhealthy Backend

Check:

- Origin health
- Health probe path
- Probe protocol
- Origin host header
- Origin network access
- WAF rules
- Routing configuration

# 17. Production Scenarios

<a id="17-production-scenarios"></a>

## Scenario 1: Distribute HTTP Traffic Across Multiple VMs

**Requirement:** Three web servers need load balancing.

### Solution

Use:

`Application Gateway` for HTTP/HTTPS Layer 7 traffic.

or:

`Load Balancer` if only Layer 4 distribution is required.

### Interview Answer

"For a web application requiring URL-based routing or TLS termination, I would choose Application Gateway. For TCP/UDP load balancing without Layer 7 routing, I would use Azure Load Balancer."

---

## Scenario 2: Protect Web Application From SQL Injection

**Requirement:** Protect a public web application from common web attacks.

### Solution

Use:

`Application Gateway + WAF`

or:

`Azure Front Door + WAF` for a global application.

### Flow

```text
Internet
 ↓
WAF
 ↓
Application
```

---

## Scenario 3: Global Application With Two Regions

**Requirement:** Application runs in India and Europe.

### Solution

For global HTTP/HTTPS application delivery:

`Azure Front Door → Region-A / Region-B`

Front Door can route requests to healthy origins.

---

## Scenario 4: DNS-Based Global Failover

**Requirement:** Primary application should be used normally, but users should be directed to secondary when primary becomes unavailable.

### Solution

Use:

`Traffic Manager → Priority Routing`

```text
User
 ↓
Traffic Manager
 ↓
Primary
 ↓
If unhealthy
 ↓
Secondary
```

---

## Scenario 5: Different URL Paths Need Different Backend Services

**Requirement:**

```text
/app
/api
/admin
```

must go to different backend services.

### Solution

Use Application Gateway path-based routing.

```text
/api/*    → API
/admin/*  → Admin
/*        → Frontend
```

---

## Scenario 6: Gradual Release

**Requirement:** Send a small percentage of traffic to a new application version.

Possible approach:

`Traffic Manager Weighted Routing`

Example:

```text
Version 1 = 90%
Version 2 = 10%
```

For HTTP application delivery, other deployment mechanisms may also be more appropriate depending on architecture.

# 18. Interview Questions

<a id="18-interview-questions"></a>

### Q1. What is Azure Load Balancer?

Azure Load Balancer is a Layer 4 service that distributes TCP/UDP traffic across healthy backend resources.

### Q2. Load Balancer vs Application Gateway?

**Interview Answer:**

"Load Balancer works at Layer 4 and is suitable for TCP/UDP traffic. Application Gateway works at Layer 7 and supports HTTP/HTTPS features such as URL routing, host-based routing, TLS termination, and WAF integration."

### Q3. What is Application Gateway?

Application Gateway is an Azure Layer 7 web traffic load balancer and reverse proxy for HTTP/HTTPS applications.

### Q4. What is WAF?

WAF is a web application firewall that protects web applications against common Layer 7 attacks such as SQL injection and XSS.

### Q5. Detection vs Prevention mode?

`Detection = Log suspicious traffic`

`Prevention = Block suspicious traffic`

### Q6. What is Traffic Manager?

Traffic Manager is a DNS-based traffic routing service that directs clients to application endpoints based on routing methods and endpoint health.

### Q7. Does Traffic Manager proxy traffic?

No. Traffic Manager provides DNS-based endpoint selection; the client then connects directly to the selected endpoint.

### Q8. What is Azure Front Door?

Azure Front Door is a global Layer 7 application delivery service for HTTP/HTTPS workloads, providing global routing, health-based failover, TLS termination, and security capabilities.

### Q9. Traffic Manager vs Front Door?

**Interview Answer:**

"Traffic Manager is DNS-based and returns an appropriate endpoint to the client. Front Door is a global Layer 7 application delivery service that receives HTTP/HTTPS traffic and routes it to healthy origins."

### Q10. When would you use Load Balancer?

Use it for Layer 4 TCP/UDP load balancing, VM/VMSS workloads, and internal or public network traffic.

### Q11. When would you use Application Gateway?

Use it when HTTP/HTTPS Layer 7 capabilities such as path-based routing, host-based routing, TLS termination, and WAF are required.

### Q12. How does a Load Balancer know whether a backend is healthy?

It uses health probes to determine whether backend instances can receive traffic.

### Q13. Why is my Application Gateway backend marked unhealthy?

Check:

`Health Probe → Backend Port → Protocol → Path → NSG → Route → Application`

### Q14. Why is WAF blocking a valid request?

Possible cause is a WAF rule false positive. Check WAF logs and the triggered rule, then tune the rule/exclusion rather than disabling WAF completely.

### Q15. How would you design a highly available global application?

**Interview Answer:**

"I would deploy the application across multiple Azure regions and use Azure Front Door for global HTTP/HTTPS routing and health-based failover. Depending on the architecture, Application Gateway with WAF can provide regional Layer 7 routing and security, while Load Balancer can distribute traffic across backend instances."

# 19. Best Practices

<a id="19-best-practices"></a>

## Load Balancer

- Use health probes.
- Use Standard SKU for production workloads where applicable.
- Keep backend instances highly available.
- Monitor probe failures.
- Use internal Load Balancer for private applications.

## Application Gateway

- Use HTTPS.
- Manage TLS certificates securely.
- Configure meaningful health probes.
- Use path/host routing where required.
- Use WAF for internet-facing applications.
- Monitor backend health.

## WAF

- Start with Detection mode during tuning.
- Review WAF logs regularly.
- Tune false positives carefully.
- Use Prevention mode after validation.
- Do not rely on WAF as the only security layer.

## Traffic Manager

- Select routing method based on business requirement.
- Configure health checks correctly.
- Understand DNS TTL and caching.
- Use Priority for failover.
- Use Weighted for traffic distribution.
- Use Performance for latency-based global routing.

## Front Door

- Use multiple healthy origins for high availability.
- Configure health probes correctly.
- Use WAF for public applications.
- Use HTTPS/TLS.
- Monitor origin health.
- Design applications to tolerate regional failures.

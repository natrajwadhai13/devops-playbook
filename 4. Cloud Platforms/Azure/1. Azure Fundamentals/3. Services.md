## 1. Azure Core Services Overview

Azure provides different services for compute, networking, storage, databases and containers.

### Main Services

| Service | Category | Main Purpose |
|---|---|---|
| Azure VM | Compute | Virtual servers |
| VMSS | Compute | Multiple managed VMs + autoscaling |
| App Service | PaaS | Host web applications |
| Functions | Serverless | Event-driven code |
| VNet | Networking | Private Azure networking |
| Storage | Storage | Files, objects, queues and data |
| Azure SQL | Database | Managed relational database |
| ACR | Container | Store container images |
| AKS | Containers | Managed Kubernetes |

### Basic Architecture

`Users → Network → Compute → Database / Storage`

### Container Architecture

`Developer → CI/CD → ACR → AKS → Application`

<a id="2-azure-virtual-machines"></a>

## 2. Azure Virtual Machines

Azure VM provides Infrastructure as a Service.

A VM gives you control over:

- Operating system
- CPU
- Memory
- Disks
- Network
- Installed software
- Application runtime

### Architecture

`User → Network → VM → Application`

### Common Use Cases

- Linux applications
- Windows applications
- Legacy applications
- Custom software
- Applications requiring OS-level access
- Custom middleware

### Create VM

```bash
az vm create \
  --resource-group rg-demo \
  --name vm-demo \
  --image Ubuntu2204 \
  --admin-username azureuser \
  --generate-ssh-keys
```

### List VMs

```bash
az vm list \
  --output table
```

### VM Operations

```bash
az vm start \
  --resource-group rg-demo \
  --name vm-demo

az vm stop \
  --resource-group rg-demo \
  --name vm-demo

az vm restart \
  --resource-group rg-demo \
  --name vm-demo
```

### Production

For production applications, avoid depending on a single VM.

`Load Balancer → Multiple VMs → Database`

<a id="3-azure-vm-scale-sets"></a>

## 3. Azure VM Scale Sets

**VMSS = Virtual Machine Scale Sets**

VMSS allows you to deploy and manage multiple VM instances as a group.

### Key Features

- Multiple VM instances
- Autoscaling
- Load balancing integration
- Centralized management
- Health monitoring
- Rolling upgrades

### Architecture

`Users → Load Balancer → VMSS → VM Instances`

### Create VMSS

```bash
az vmss create \
  --resource-group rg-demo \
  --name vmss-demo \
  --image Ubuntu2204 \
  --instance-count 2 \
  --admin-username azureuser \
  --generate-ssh-keys
```

### List Instances

```bash
az vmss list-instances \
  --resource-group rg-demo \
  --name vmss-demo \
  --output table
```

### Scale VMSS

```bash
az vmss scale \
  --resource-group rg-demo \
  --name vmss-demo \
  --new-capacity 4
```

### Production Example

`Low Traffic → 2 Instances`

`High Traffic → 5 Instances`

`Traffic Drops → 2 Instances`

### VM vs VMSS

`VM = Individual Server`

`VMSS = Group of Managed Servers`

<a id="4-azure-app-service"></a>

## 4. Azure App Service

Azure App Service is a PaaS service for hosting web applications and APIs.

It supports application platforms such as:

- .NET
- Java
- Node.js
- Python
- PHP

### Architecture

`Developer → CI/CD → App Service → Users`

### App Service Plan

The App Service Plan provides the compute resources for the application.

`App Service Plan → Compute`

`Web App → Application`

### Scaling

**Scale Up**

Increase the size/tier of the App Service Plan.

`Smaller Plan → Larger Plan`

**Scale Out**

Increase the number of application instances.

`2 Instances → 5 Instances`

### Deployment Slots

Slots provide separate application environments.

Example:

`Production Slot + Staging Slot`

Deployment flow:

`Build → Staging → Test → Swap → Production`

### Create App Service Plan

```bash
az appservice plan create \
  --resource-group rg-demo \
  --name asp-demo \
  --sku B1 \
  --is-linux
```

### Create Web App

```bash
az webapp create \
  --resource-group rg-demo \
  --plan asp-demo \
  --name my-demo-webapp
```

### Enable HTTPS Only

```bash
az webapp update \
  --resource-group rg-demo \
  --name my-demo-webapp \
  --https-only true
```

### Production Use

App Service is a good choice when the team wants to deploy applications without managing servers.

<a id="5-azure-functions"></a>

## 5. Azure Functions

Azure Functions is a serverless compute service used to execute code based on events or triggers.

### Common Triggers

- HTTP
- Timer
- Queue
- Blob
- Event Grid
- Service Bus
- Database events

### Architecture

`Event → Azure Function → Processing → Output`

### Example

`Blob Upload → Function → Process File → Database`

### HTTP Function

`Client → HTTP Trigger → Function → Response`

### Timer Function

`Schedule → Function → Task`

Example:

`Every Day → Function → Cleanup Old Data`

### Advantages

- Serverless
- Event-driven
- Automatic scaling
- Pay based on execution/plan
- Good for short-running workloads

### Use Cases

- Background processing
- Scheduled jobs
- API endpoints
- File processing
- Event processing
- Automation

### Functions vs App Service

| Feature | App Service | Functions |
|---|---|---|
| Type | PaaS | Serverless |
| Main Use | Web applications/APIs | Event-driven code |
| Trigger based | Optional | Core concept |
| Long-running web app | Good | Depends on plan/workload |
| Event processing | Possible | Excellent |

<a id="6-azure-virtual-network"></a>

## 6. Azure Virtual Network

**VNet = Virtual Network**

Azure VNet provides private networking for Azure resources.

### Main Components

- Address Space
- Subnets
- Network Interfaces
- Private IP
- Public IP
- NSG
- Route Tables
- Private Endpoints
- VNet Peering

### Architecture

`VNet → Subnet → NIC → Azure Resource`

### Example

```text
VNet
├── Web Subnet
├── App Subnet
└── Database Subnet
```

### Create VNet

```bash
az network vnet create \
  --resource-group rg-demo \
  --name vnet-demo \
  --address-prefix 10.0.0.0/16 \
  --subnet-name app-subnet \
  --subnet-prefix 10.0.1.0/24
```

### Create NSG

```bash
az network nsg create \
  --resource-group rg-demo \
  --name nsg-app
```

### Production Architecture

`Internet → Load Balancer / Application Gateway → Web Subnet → App Subnet → Database Subnet`

<a id="8-azure-sql"></a>

## 8. Azure SQL

Azure SQL is a managed relational database service based on Microsoft SQL Server technologies.

### Features

- Managed database
- High availability
- Automated backups
- Monitoring
- Security
- Scaling
- Point-in-time recovery

### Architecture

`Application → Private Network → Azure SQL`

### Production Security

Prefer:

`Application → Managed Identity → Azure SQL`

Avoid storing database passwords directly inside application code.

### Common Use Cases

- Web applications
- Enterprise applications
- Transactional workloads
- .NET applications
- Business applications

### Database Troubleshooting Flow

`Application → DNS → Network → Firewall → Authentication → Permissions → Connection → Query → Performance`

<a id="9-azure-container-registry"></a>

## 9. Azure Container Registry

**ACR = Azure Container Registry**

ACR is a private registry for storing and managing container images.

### Architecture

`Developer → Docker Build → ACR → AKS`

### Build Image

```bash
docker build \
  -t my-app:v1 .
```

### Login to ACR

```bash
az acr login \
  --name myregistry
```

### Tag Image

```bash
docker tag \
  my-app:v1 \
  myregistry.azurecr.io/my-app:v1
```

### Push Image

```bash
docker push \
  myregistry.azurecr.io/my-app:v1
```

### List Images

```bash
az acr repository list \
  --name myregistry \
  --output table
```

### Production Flow

`Git → CI/CD → Docker Build → Security Scan → ACR → AKS`

### ACR Security

Prefer:

- Managed Identity
- RBAC
- Private Endpoint
- Image scanning
- Vulnerability management

<a id="10-azure-kubernetes-service"></a>

## 10. Azure Kubernetes Service

**AKS = Azure Kubernetes Service**

AKS is Azure's managed Kubernetes service.

It is used to deploy and manage containerized applications.

### Architecture

`Users → Ingress → AKS → Services → Pods`

### Main Components

- Cluster
- Nodes
- Node Pools
- Pods
- Deployments
- Services
- Ingress
- ConfigMaps
- Secrets
- Persistent Volumes

### Production CI/CD Flow

`Developer → Git → CI/CD → Build → Scan → ACR → AKS → Monitor`

### Example Deployment

```yaml id="5wxj1v"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
        - name: my-app
          image: myregistry.azurecr.io/my-app:v1
          ports:
            - containerPort: 8080
```

### Common AKS Commands

```bash
az aks list --output table

az aks get-credentials \
  --resource-group rg-demo \
  --name aks-demo
```

Then:

```bash
kubectl get nodes
kubectl get pods
kubectl get services
kubectl get deployments
```

### Production Architecture

`Users → Front Door / Application Gateway → Ingress → AKS → Services → Pods → Azure SQL / Storage`

<a id="12-when-to-use-which-service"></a>

## 12. When to Use Which Service

| Requirement | Recommended Service |
|---|---|
| Need full OS control | VM |
| Need multiple VMs with autoscaling | VMSS |
| Host web application without managing servers | App Service |
| Event-driven processing | Functions |
| Private Azure networking | VNet |
| Store files/images/backups | Blob Storage |
| Shared file system | Azure Files |
| Relational SQL database | Azure SQL |
| Store Docker images | ACR |
| Run Kubernetes workloads | AKS |

### Easy Decision Flow

`Need Server Control → VM`

`Need Multiple Managed VMs → VMSS`

`Need Managed Web Hosting → App Service`

`Need Event-Driven Code → Functions`

`Need Private Network → VNet`

`Need Object/File Storage → Storage`

`Need SQL Database → Azure SQL`

`Need Container Registry → ACR`

`Need Kubernetes → AKS`

<a id="17-production-scenarios"></a>

## 17. Production Scenarios

### Scenario 1 — Application Requires OS-Level Changes

**Requirement:** The application requires custom Linux configuration.

**Solution:** Use Azure VM or VMSS.

**Why:** IaaS provides OS-level control.

---

### Scenario 2 — Web Application Has Variable Traffic

**Requirement:** Traffic changes significantly during the day.

**Solution:** Use App Service autoscaling or VMSS autoscaling depending on architecture.

**Interview Answer:**

"I would first identify whether the application needs OS-level control. If not, App Service with autoscaling would reduce infrastructure management."

---

### Scenario 3 — Application Needs Event Processing

**Requirement:** Process a file whenever it is uploaded.

**Solution:**

`Blob Upload → Azure Function → Processing`

---

### Scenario 4 — Company Wants Kubernetes

**Requirement:** Run multiple containerized microservices with Kubernetes.

**Solution:**

`ACR → AKS`

---

### Scenario 5 — Application Cannot Pull Image from ACR

**What will you check?**

- AKS identity
- ACR permissions
- Image name
- Image tag
- Network connectivity
- Private endpoint
- DNS

**Useful Commands:**

```bash
kubectl describe pod <pod-name>
kubectl get events
az aks show \
  --resource-group rg-demo \
  --name aks-demo
```

**Root Cause Examples:**

- Missing `AcrPull`
- Wrong image name
- Wrong tag
- DNS issue
- Network restriction

---

### Scenario 6 — Application Cannot Connect to Azure SQL

**What will you check?**

`DNS → Network → Private Endpoint → Firewall → Port → Authentication → Permissions → Connection String`

**Root Cause Examples:**

- Firewall blocking traffic
- Wrong DNS
- Incorrect credentials
- Private Endpoint issue
- Wrong connection string

---

### Scenario 7 — Storage Access Suddenly Fails

**What will you check?**

- Managed Identity
- RBAC
- SAS expiry
- Storage firewall
- Private Endpoint
- Private DNS
- Application logs

**Root Cause:**

Often an identity, network or access-control issue.

<a id="18-interview-questions"></a>

## 18. Interview Questions

### Q1. VM vs VMSS?

**Answer:**  
A VM is an individual virtual server. VMSS manages multiple VM instances as a group and supports features such as autoscaling and load balancing.

### Q2. VM vs App Service?

**Answer:**  
VM provides OS-level control and is IaaS. App Service is PaaS where Azure manages much of the underlying infrastructure.

### Q3. App Service vs Functions?

**Answer:**  
App Service is mainly used for continuously hosted web applications and APIs. Functions are designed for event-driven and serverless workloads.

### Q4. What is VNet?

**Answer:**  
VNet is Azure's private networking service used to provide network isolation and connectivity for Azure resources.

### Q5. What is ACR?

**Answer:**  
Azure Container Registry is a private registry used to store and manage container images.

### Q6. What is AKS?

**Answer:**  
AKS is Azure's managed Kubernetes service used to run and orchestrate containerized applications.

### Q7. Why do we need ACR with AKS?

**Answer:**  
ACR provides a private registry where container images can be stored. AKS can pull those images and run them as Kubernetes workloads.

### Q8. What is the relationship between ACR and AKS?

**Answer:**

`CI/CD → Build Image → ACR → AKS Pulls Image → Pod`

### Q9. When would you choose App Service instead of AKS?

**Answer:**  
If the application is a standard web application or API and does not require Kubernetes-level orchestration, App Service can reduce operational complexity.

### Q10. When would you choose AKS?

**Answer:**  
When the organization needs Kubernetes features such as container orchestration, microservices, advanced deployment strategies, service discovery, scaling and Kubernetes ecosystem integrations.

### Q11. What is Azure SQL?

**Answer:**  
Azure SQL is a managed relational database service based on Microsoft SQL Server technologies.

### Q12. What is the role of VNet in production?

**Answer:**  
VNet provides network isolation and allows applications to communicate securely with services through private networking, routing, NSGs and private endpoints.

<a id="19-best-practices"></a>

## 19. Best Practices

- Choose the simplest Azure service that meets the requirement.
- Use VM only when OS-level control is required.
- Use VMSS for scalable VM-based workloads.
- Prefer App Service for standard web applications when Kubernetes is unnecessary.
- Use Functions for event-driven workloads.
- Design VNets with proper subnet separation.
- Use private connectivity for sensitive production services.
- Use Managed Identity instead of hardcoded credentials.
- Store container images in ACR.
- Use vulnerability scanning before deploying images.
- Use AKS when Kubernetes capabilities are actually required.
- Monitor all production services.
- Use Infrastructure as Code for repeatable deployments.
- Use CI/CD instead of manual production deployments.

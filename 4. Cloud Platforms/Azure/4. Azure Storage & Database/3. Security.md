## Azure Storage Security

Azure Storage security protects data from **unauthorized access, data exposure, credential leakage, and network-based attacks**.

Core security mechanisms:

```text
Encryption → Protect Data
SAS → Temporary Limited Access
Access Keys → Full Storage Account Access
RBAC → Identity-Based Authorization
Private Endpoint → Private Network Access
```

---

## 1. Encryption

Azure Storage automatically encrypts data **at rest**.

```text
Application → Azure Storage → Encryption → Disk
```

### Encryption at Rest

- Data stored in Blob, File, Queue, and Table Storage is encrypted.
- Azure Storage uses **Microsoft-managed keys by default**.
- You can also use **customer-managed keys** through Azure Key Vault for stronger key-control requirements.

### Encryption in Transit

Use HTTPS/TLS when communicating with Azure Storage.

```text
Application → HTTPS/TLS → Azure Storage
```

For production:

```text
HTTPS Only
TLS
Encryption at Rest
Managed Identity
RBAC
Private Endpoint
```

---

# 2. SAS — Shared Access Signature

SAS provides **temporary and limited access** to Azure Storage resources.

Instead of giving someone the storage account key, you can provide a SAS token with specific permissions.

```text
Application/User
      ↓
   SAS Token
      ↓
Azure Storage
```

### SAS Can Control

- Read
- Write
- Delete
- List
- Create
- Update
- Expiry time
- Resource scope

Example:

```text
Read-only access
Valid for 1 hour
Specific Blob
```

### Example SAS URL

```text
https://mystorage.blob.core.windows.net/images/photo.jpg?<SAS_TOKEN>
```

### Production Example

Suppose an application needs to allow a user to download one private file.

Instead of giving the user:

```text
Storage Account Key ❌
```

Generate:

```text
Short-lived SAS Token ✅
```

Then:

```text
User → SAS URL → Specific Blob
```

### Important

SAS is a **credential**. Treat it like a secret.

Do not:

```text
Commit SAS token to Git ❌
Put SAS token in source code ❌
Share SAS token publicly ❌
```

# 3. Access Keys

Storage accounts have **access keys** that provide broad access to the storage account.

Typically:

```text
Key1
Key2
```

They can be used for applications that authenticate using the storage account key.

Example connection string:

```text
DefaultEndpointsProtocol=https;
AccountName=mystorageaccount;
AccountKey=<SECRET>;
EndpointSuffix=core.windows.net
```

### Advantages

- Simple to configure.
- Useful for legacy applications.
- Supports applications that cannot easily use Entra ID/RBAC.

### Disadvantages

- Very powerful credentials.
- Difficult to manage securely at scale.
- Key leakage can provide broad storage access.
- Requires key rotation.

### Production Recommendation

Prefer:

```text
Managed Identity + RBAC
```

over:

```text
Storage Access Key
```

whenever the application supports Microsoft Entra ID authentication.

# 4. RBAC — Role-Based Access Control

RBAC provides **identity-based authorization**.

```text
User / VM / App Service / AKS
          ↓
   Microsoft Entra ID
          ↓
         RBAC
          ↓
     Azure Storage
```

Instead of sharing storage keys, assign an appropriate Azure role.

### Common Storage Roles

| Role | Purpose |
|---|---|
| Storage Blob Data Reader | Read Blob data |
| Storage Blob Data Contributor | Read/write/delete Blob data |
| Storage Blob Data Owner | Full access to Blob data |
| Storage Queue Data Contributor | Read/write/delete Queue data |

### Example

Application only needs to read Blob files:

```text
Managed Identity
      ↓
Storage Blob Data Reader
      ↓
Blob Storage
```

Application needs to upload files:

```text
Managed Identity
      ↓
Storage Blob Data Contributor
      ↓
Blob Storage
```

### Least Privilege

Give only the permissions required.

```text
Read only → Reader
Read + Write → Contributor
Full control → Owner
```

Avoid giving unnecessary permissions.

# 5. Private Endpoint

A Private Endpoint provides a **private IP address** for accessing Azure Storage through an Azure VNet.

Without Private Endpoint:

```text
Application → Public Network → Azure Storage
```

With Private Endpoint:

```text
Application
     ↓
   VNet
     ↓
Private Endpoint
     ↓
Azure Storage
```

The application can access Storage using a private network path.

### Example Production Architecture

```text
Internet
   ↓
Application
   ↓
Azure VNet
   ↓
Private Endpoint
   ↓
Azure Storage
```

### Private Endpoint + Private DNS

Private Endpoint normally works together with Private DNS so that the Storage hostname resolves to the private IP.

```text
Application
    ↓
DNS
    ↓
Private IP
    ↓
Private Endpoint
    ↓
Storage
```

## Security Troubleshooting

```text
Storage Access Failed
        ↓
Identity
        ↓
RBAC Role
        ↓
SAS Permissions / Expiry
        ↓
Access Key Validity
        ↓
DNS
        ↓
Private Endpoint
        ↓
Storage Firewall
        ↓
Network Connectivity
        ↓
Logs
        ↓
Root Cause → Fix → Verify
```

### Common Errors

| Problem | Likely Cause |
|---|---|
| `403 Forbidden` | RBAC/SAS/ACL/Firewall |
| `AuthenticationFailed` | Invalid/expired credential |
| SAS not working | Expired or insufficient permissions |
| Public access blocked | Storage firewall/network restriction |
| Private Endpoint not working | DNS/private network issue |
| Application cannot access Blob | Missing RBAC role |
| Access key authentication fails | Wrong/rotated key |

## Interview Questions

**Q1. What is the difference between SAS and RBAC?**

**Answer:** SAS provides a temporary, scoped access token with specific permissions and expiry. RBAC provides identity-based authorization using Microsoft Entra ID and Azure roles.

**Q2. Which is preferred for applications: Access Keys or Managed Identity?**

**Answer:** Managed Identity with RBAC is preferred because it avoids storing and managing long-lived storage credentials.

**Q3. How do you secure Azure Storage from public network access?**

**Answer:** Disable unnecessary public access, use Private Endpoint with Private DNS, restrict network access using Storage Firewall/network rules, and use RBAC with Managed Identity.

**Q4. Does encryption protect against unauthorized users?**

**Answer:** Encryption protects the data, but authorization controls such as RBAC, SAS, network restrictions, and identity controls determine who can access it.

### Memory Trick

```text
Encryption → Protect
SAS → Temporary Access
Access Key → Powerful Credential
RBAC → Who Can Do What
Private Endpoint → Private Network
```

# Azure Database

<a id="azure-database"></a>

Azure provides managed database services for **relational, NoSQL, and in-memory caching workloads**.

```text
Application
    ↓
Database Layer
    ├── Azure SQL
    ├── Azure Database for PostgreSQL
    ├── Azure Database for MySQL
    ├── Azure Cosmos DB
    └── Azure Cache for Redis
```

## 1. Database Service Selection

<a id="database-service-selection"></a>

| Service | Type | Best For |
|---|---|---|
| **Azure SQL Database** | Relational | SQL Server applications |
| **Azure Database for PostgreSQL** | Relational | PostgreSQL applications |
| **Azure Database for MySQL** | Relational | MySQL applications |
| **Azure Cosmos DB** | NoSQL | Globally distributed applications |
| **Azure Cache for Redis** | In-Memory Cache | High-speed caching |

### Simple Memory

```text
SQL Server      → Azure SQL
PostgreSQL      → Azure PostgreSQL
MySQL           → Azure MySQL
NoSQL / Global  → Cosmos DB
Cache           → Redis
```

# 6. Cosmos DB Partitioning

<a id="cosmos-partitioning"></a>

Partitioning distributes data across multiple logical/physical partitions.

```text
Application
     ↓
Cosmos DB
     ↓
Partition Key
 ┌────┼────┐
 P1   P2   P3
```

A good partition key helps distribute workload evenly.

### Example

Suppose an application stores customer orders.

```text
/customerId
```

can be used as a partition key when access patterns are customer-oriented.

### Interview Point

A poor partition key can create a **hot partition**, where too much traffic goes to one partition.

# 8. Azure Cache for Redis

<a id="azure-cache-redis"></a>

Azure Cache for Redis is a **managed in-memory data store** used primarily for caching.

```text
Application
    ↓
Redis Cache
    ↓
Fast Data Access

Application
    ↓
Database
    ↓
Slower than Cache
```

Instead of querying the database repeatedly:

```text
Application
    ↓
Check Redis
    ↓
Data exists?
 ├── Yes → Return Data
 └── No  → Database → Store in Redis → Return Data
```

This is called the **cache-aside pattern**.

### Common Use Cases

- Session storage
- Frequently accessed data
- API response caching
- Product/catalog caching
- Reducing database load
- Improving application response time
- Distributed application caching

# 9. Database vs Cache

<a id="database-vs-cache"></a>

| Feature | Database | Redis Cache |
|---|---|---|
| Purpose | Persistent data | Fast temporary access |
| Storage | Persistent | Primarily memory |
| Speed | Normal | Very fast |
| Main Use | Source of truth | Cached data |
| Example | Azure SQL | Azure Cache for Redis |

### Important

Redis should generally **not be treated as the primary database** for normal application data.

```text
Database = Source of Truth
Redis    = Performance Layer
```

# 16. Hands-on — Azure SQL

<a id="hands-on-sql"></a>

### Login

```bash
az login
```

### Create Resource Group

```bash
az group create \
  --name rg-database \
  --location centralindia
```

### Create SQL Server

```bash
az sql server create \
  --name my-sql-server-123 \
  --resource-group rg-database \
  --location centralindia \
  --admin-user sqladmin \
  --admin-password '<StrongPassword>'
```

### Create Database

```bash
az sql db create \
  --resource-group rg-database \
  --server my-sql-server-123 \
  --name mydatabase \
  --service-objective S0
```

> In production, avoid putting database passwords directly in scripts or source control.

# 21. Production Troubleshooting Scenarios

<a id="database-scenarios"></a>

### Scenario 1 — Application Cannot Connect to Azure SQL

**What will you check?**

```text
DNS
→ Private Endpoint
→ Network
→ Firewall
→ Port
→ Authentication
→ Database permissions
→ Application connection string
→ Database status
```

**Commands:**

```bash
nslookup <sql-server-hostname>
```

```bash
Test-NetConnection <sql-server-hostname> -Port 1433
```

**Root Cause:** Firewall or network access was blocking the connection.

**Fix:** Correct the network/firewall configuration and verify database permissions.

**Interview Answer:**  
"I first verify DNS resolution and connectivity to port 1433, then check Private Endpoint, firewall rules, authentication, database permissions, and application configuration. Once the connectivity issue is fixed, I validate the application connection and database logs."

# 22. Interview Questions

<a id="database-interview"></a>

### Q1. Azure SQL vs PostgreSQL?

**Answer:** Azure SQL is based on the SQL Server ecosystem, while Azure Database for PostgreSQL provides managed PostgreSQL. The choice depends mainly on application compatibility, existing database technology, and workload requirements.

### Q2. Azure SQL vs Cosmos DB?

**Answer:** Azure SQL is a relational database using structured tables and SQL. Cosmos DB is a NoSQL database designed for distributed, highly scalable applications and global low-latency access.

### Q3. Why use Redis?

**Answer:** Redis stores frequently accessed data in memory, reducing database calls and improving application response time.

### Q4. Is Redis a replacement for a database?

**Answer:** Normally no. The database remains the source of truth, while Redis is primarily used as a caching and performance layer.

### Q5. What is a Cosmos DB partition key?

**Answer:** A partition key determines how Cosmos DB distributes data across partitions. A good partition key provides even distribution and prevents hot partitions.

### Q6. How do you secure Azure databases?

**Answer:** I use encryption, Microsoft Entra authentication, RBAC, Private Endpoint, firewall/network restrictions, managed identities, Key Vault for required secrets, and monitoring/auditing.

### Q7. Database connection is timing out. What do you check?

**Answer:**

```text
DNS
→ Private Endpoint
→ Route
→ NSG
→ Firewall
→ Port
→ Database Status
→ Authentication
→ Application Configuration
```

### Q8. What is the difference between HA and backup?

**Answer:** HA keeps the database service available during certain failures, while backup allows recovery of data after deletion, corruption, or other recovery scenarios.

# 23. Best Practices

<a id="database-best-practices"></a>

- Use managed database services where possible.
- Prefer Microsoft Entra ID and Managed Identity.
- Use Private Endpoint for production workloads where appropriate.
- Avoid hardcoded credentials.
- Store required secrets in Key Vault.
- Enable encryption.
- Restrict public network access.
- Configure backups and retention.
- Define RPO and RTO.
- Monitor CPU, storage, connections, latency, and errors.
- Optimize database queries and indexes.
- Use Redis for appropriate caching workloads.
- Design Cosmos DB partition keys carefully.
- Test backup restoration regularly.
- Implement HA/DR according to business requirements.

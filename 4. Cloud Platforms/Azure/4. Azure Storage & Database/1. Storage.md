<a id="1-azure-storage-overview"></a>

# 1. Azure Storage Overview

Azure Storage provides managed cloud storage services for applications, backups, files, messages and structured NoSQL data.

Main services:

| Service | Purpose | Typical Use |
|---|---|---|
| Blob Storage | Object storage | Images, videos, backups, logs |
| Azure Files | Managed file shares | Shared application files |
| Queue Storage | Message storage | Async processing |
| Table Storage | NoSQL key-value storage | Simple structured data |
| Storage Account | Storage service container | Hosts storage services |

### Memory Trick

```text
Blob  = Objects
File  = Shared Files
Queue = Messages
Table = NoSQL
Account = Container for Storage Services
```

<a id="2-storage-account"></a>

# 2. Storage Account

A Storage Account is the top-level Azure resource that provides access to Azure Storage services.

Typical structure:

```text
Storage Account
├── Blob Containers
├── File Shares
├── Queues
└── Tables
```

Example:

```text
Storage Account
      ↓
Application
      ↓
Blob Container
      ↓
Images / Backups / Documents
```

### Important Storage Account Settings

| Setting | Purpose |
|---|---|
| Performance | Standard / Premium |
| Redundancy | LRS / ZRS / GRS / GZRS |
| Access Tier | Hot / Cool / Cold / Archive |
| Secure Transfer | HTTPS |
| Public Access | Control public exposure |
| Encryption | Protect stored data |
| Networking | Firewall / Private Endpoint |
| Access Keys | Authentication |
| Shared Access Signature | Limited delegated access |

### Create Storage Account

```bash
az storage account create \
  --resource-group rg-storage \
  --name mystorageaccount123 \
  --location centralindia \
  --sku Standard_LRS \
  --kind StorageV2
```

`StorageV2` is the general-purpose v2 storage account type commonly used for modern Azure Storage workloads.

<a id="5-blob-types"></a>

# 5. Blob Types

Azure Blob Storage supports three blob types.

| Blob Type | Purpose |
|---|---|
| Block Blob | General object/file storage |
| Append Blob | Append operations, commonly logs |
| Page Blob | Random-access storage, used by some VM disk scenarios |

### Block Blob

Most common type.

Use for:

```text
Images
Documents
Videos
Application files
Backups
```

### Append Blob

Designed for append operations.

Example:

```text
Application
   ↓
Append Log
   ↓
Append Blob
```

### Page Blob

Optimized for random read/write operations and historically used for VHD scenarios.

### Memory Trick

```text
Block  = General Files
Append = Logs / Append
Page   = Random Access
```

<a id="7-storage-access-tiers"></a>

# 7. Storage Access Tiers

Blob Storage provides access tiers that help optimize storage cost based on how frequently data is accessed.

| Tier | Access Pattern | Cost Concept |
|---|---|---|
| Hot | Frequently accessed | Higher storage, lower access cost |
| Cool | Infrequently accessed | Lower storage, higher access cost |
| Cold | Rarely accessed | Lower storage, higher access cost |
| Archive | Very rarely accessed | Lowest storage, retrieval takes longer |

### Memory Trick

```text
Hot     → Frequently used
Cool    → Less frequently used
Cold    → Rarely used
Archive → Long-term storage
```

### Example

```text
Application Data
      ↓
Hot

Old Data
      ↓
Cool

Long-term Data
      ↓
Cold / Archive
```

### Important

Choosing an access tier is a **cost + access-frequency decision**.

Do not automatically put everything in Archive.

Consider:

- Access frequency
- Retrieval latency
- Transaction costs
- Data retention
- Business requirements

<a id="9-azure-queue-storage"></a>

# 9. Azure Queue Storage

Azure Queue Storage provides asynchronous message storage.

Instead of one application directly waiting for another:

```text
Application → Queue → Worker
```

### Example

```text
Web Application
      ↓
Queue
      ↓
Background Worker
      ↓
Database
```

The web application can place a message into the queue and continue processing.

### Use Cases

- Background jobs
- Async processing
- Order processing
- Image processing
- Email processing
- Decoupling applications

### Memory Trick

```text
Queue = Decouple Producer and Consumer
```

### Create Queue

```bash
az storage queue create \
  --account-name mystorageaccount123 \
  --name processing \
  --auth-mode login
```

<a id="10-azure-table-storage"></a>

# 10. Azure Table Storage

Azure Table Storage is a NoSQL key-value store for structured data.

It is useful when you need simple, scalable NoSQL storage without a relational database model.

Basic structure:

```text
Table
 ├── PartitionKey
 ├── RowKey
 └── Properties
```

### PartitionKey

Groups related entities.

### RowKey

Uniquely identifies an entity within a partition.

Example:

```text
PartitionKey = India
RowKey       = 1001
Name         = User1
Status       = Active
```

### Use Cases

- Metadata
- Device information
- User profiles
- Simple NoSQL workloads
- Large-scale key-value data

### Memory Trick

```text
Table = Key-Value / NoSQL
```

<a id="11-storage-redundancy"></a>

# 11. Storage Redundancy

Azure Storage provides multiple redundancy options.

| Option | Meaning | Use |
|---|---|---|
| LRS | Locally Redundant Storage | Local resilience |
| ZRS | Zone-Redundant Storage | Zone failure protection |
| GRS | Geo-Redundant Storage | Regional disaster protection |
| GZRS | Geo-Zone-Redundant Storage | Zone + regional protection |

### LRS

Data is replicated within the same region.

```text
Region
└── Multiple Storage Copies
```

### ZRS

Data is replicated across availability zones in the region.

```text
Zone 1 ─┐
Zone 2 ─┼→ Storage
Zone 3 ─┘
```

### GRS

Data is replicated to a secondary region.

```text
Primary Region
      ↓
Secondary Region
```

### GZRS

Combines zone redundancy in the primary region with geo-redundancy.

### Production Selection

```text
Single-region resilience
→ LRS / ZRS

Regional disaster protection
→ GRS / GZRS
```

Choose based on:

- RPO
- RTO
- Business criticality
- Cost
- Regional DR requirements

<a id="12-lifecycle-management"></a>

# 12. Lifecycle Management

Azure Blob lifecycle management automatically moves or deletes blobs based on conditions.

Example:

```text
Hot
 ↓
Cool
 ↓
Cold
 ↓
Archive
 ↓
Delete
```

### Example Policy

```text
After 30 days
→ Move Hot → Cool

After 90 days
→ Move Cool → Cold

After 180 days
→ Move Cold → Archive

After 365 days
→ Delete
```

### Why Use Lifecycle Management?

- Reduce storage cost
- Automate data retention
- Remove obsolete data
- Reduce manual operations

### Example Lifecycle Policy

```json
{
  "rules": [
    {
      "enabled": true,
      "name": "archive-old-data",
      "type": "Lifecycle",
      "definition": {
        "filters": {
          "blobTypes": [
            "blockBlob"
          ],
          "prefixMatch": [
            "backups/"
          ]
        },
        "actions": {
          "baseBlob": {
            "tierToCool": {
              "daysAfterModificationGreaterThan": 30
            },
            "tierToArchive": {
              "daysAfterModificationGreaterThan": 180
            },
            "delete": {
              "daysAfterModificationGreaterThan": 365
            }
          }
        }
      }
    }
  ]
}
```

### Production Example

```text
Application Backups
       ↓
Hot
       ↓ 30 Days
Cool
       ↓ 180 Days
Archive
       ↓ 365 Days
Delete
```

<a id="13-storage-security"></a>

# 13. Storage Security

Storage security should follow defense in depth.

### Important Controls

```text
RBAC
Managed Identity
SAS
Encryption
HTTPS
Private Endpoint
Storage Firewall
Network Rules
Public Access Control
Microsoft Defender for Storage
```

### Avoid

```text
Hardcoded Storage Keys
Public Containers
Anonymous Access
Broad SAS Permissions
Long-lived Credentials
```

### Preferred Architecture

```text
Application
   ↓
Managed Identity
   ↓
Microsoft Entra ID
   ↓
RBAC
   ↓
Private Endpoint
   ↓
Storage Account
```

### Private Endpoint

A private endpoint provides private network access to supported Azure Storage services.

```text
VNet
 ↓
Private Endpoint
 ↓
Private IP
 ↓
Storage Account
```

This avoids depending on public internet connectivity for application-to-storage access.

## Problem 2 — Authorization Failed

Typical causes:

```text

Expired SAS
Invalid SAS permissions
Wrong storage account
Wrong container
Access key issue
```

Check current identity:

```bash
az account show
```

Check role assignments:

```bash
az role assignment list \
  --assignee <principal-id> \
  --scope <storage-resource-id>
```

## Problem 3 — Storage Is Not Reachable

Check:

```text
DNS
 ↓
Private Endpoint
 ↓
Private DNS
 ↓
Route
 ↓
NSG
 ↓
Storage Firewall
```

For private endpoint issues:

```text
Application
 ↓
Storage FQDN
 ↓
DNS
 ↓
Private IP?
```

If DNS resolves to a public IP when private connectivity is expected, investigate Private DNS configuration.

---

## Problem 4 — Application Cannot Mount Azure Files

Check:

```text
Storage Account
 ↓
File Share
 ↓
SMB/NFS
 ↓
DNS
 ↓
Network
 ↓
Port
 ↓
Authentication
```

For SMB, commonly verify TCP 445 connectivity where applicable.

## Problem 5 — Storage Cost Increased

Check:

```text
Data Growth
 ↓
Access Tier
 ↓
Transactions
 ↓
Data Retrieval
 ↓
Replication
 ↓
Egress
 ↓
Lifecycle Policy
```

Possible fix:

```text
Frequently used → Hot
Less used → Cool/Cold
Long-term → Archive
```

<a id="20-best-practices"></a>

# 20. Best Practices

## Storage Account

- Use `StorageV2`.
- Use HTTPS.
- Disable unnecessary public access.
- Select redundancy based on business requirements.
- Monitor capacity and transactions.
- Use private endpoints for sensitive workloads.

## Blob Storage

- Select access tiers based on access patterns.
- Use lifecycle policies.
- Avoid public containers.
- Use RBAC/Managed Identity.
- Use SAS only when delegated temporary access is required.
- Separate data by logical containers.

## Azure Files

- Use private connectivity where required.
- Control share permissions.
- Monitor capacity.
- Use appropriate protocol and authentication.

## Queue

- Design consumers to handle retries.
- Make processing idempotent.
- Monitor queue depth.
- Handle failed messages appropriately.

## Security

```text
Managed Identity > Hardcoded Credentials
Private Endpoint > Public Exposure
RBAC > Shared Credentials
Least Privilege > Broad Access
```

## Cost

```text
Access Pattern → Tier → Lifecycle → Retention → Cost Optimization
```

# Azure Database — DevOps

<a id="database-devops"></a>

Database DevOps covers **backup, restore, migration, connection configuration, and secure secret management**.

```text
Application → Connection Configuration → Database
                         ↓
              Secret Management
                         ↓
          Backup → Restore → DR
                         ↓
                    Migration
```

---

# 1. Database Backup

<a id="database-backup"></a>

A database backup creates a recoverable copy of database data.

```text
Database
   ↓
Backup
   ↓
Storage
   ↓
Restore when required
```

### Why Backup Is Required

- Accidental data deletion
- Data corruption
- Application errors
- Failed deployment
- Database failure
- Disaster recovery
- Compliance requirements

### Backup Strategy

```text
Full Backup
    ↓
Retention
    ↓
Point-in-Time Recovery
    ↓
Geo-Redundant Backup / DR
```

### Important Terms

| Term | Meaning |
|---|---|
| **Backup** | Copy of database data for recovery |
| **Retention** | How long backups are kept |
| **PITR** | Restore database to a previous point in time |
| **RPO** | Maximum acceptable data loss |
| **RTO** | Maximum acceptable recovery time |

### Example

If:

```text
RPO = 15 minutes
```

The business should not lose more than approximately 15 minutes of data.

If:

```text
RTO = 1 hour
```

The service should be restored within approximately one hour.

# 4. Database Restore

<a id="database-restore"></a>

Restore means creating a usable database from a backup or recovery point.

```text
Backup
   ↓
Restore
   ↓
New / Recovered Database
   ↓
Application Validation
```

### Restore Process

```text
Identify Recovery Point
        ↓
Restore Database
        ↓
Validate Schema
        ↓
Validate Data
        ↓
Test Application
        ↓
Switch Application
```

### Production Rule

Never assume that a backup works simply because the backup job is successful.

**Test restoration regularly.**

```text
Backup Success ≠ Recovery Guaranteed
```

---

# 5. Point-in-Time Restore

<a id="point-in-time-restore"></a>

Point-in-time restore allows recovery to a specific time within the supported backup retention period.

Example:

```text
10:00 → Normal
10:30 → Data accidentally deleted
10:45 → Issue discovered

Restore → 10:29
```

This minimizes data loss.

### Production Scenario

An engineer accidentally executes:

```sql
DELETE FROM orders;
```

Instead of restoring the entire environment blindly:

```text
Incident
   ↓
Identify Time
   ↓
Point-in-Time Restore
   ↓
Validate Data
   ↓
Recover Required Data
```

# 6. Database Migration

<a id="database-migration"></a>

Database migration means moving database data/schema from one database environment to another.

Common migrations:

```text
On-Premises → Azure
VM Database → Managed Database
MySQL → Azure MySQL
PostgreSQL → Azure PostgreSQL
SQL Server → Azure SQL
Development → Production
```

### Migration Flow

```text
Source Database
      ↓
Assessment
      ↓
Schema / Compatibility Check
      ↓
Migration
      ↓
Data Validation
      ↓
Application Testing
      ↓
Cutover
      ↓
Monitoring
```

---

# 7. Database Migration Strategies

<a id="migration-strategies"></a>

| Strategy | Meaning | Downtime |
|---|---|---|
| **Backup & Restore** | Backup source and restore target | Medium |
| **Offline Migration** | Stop application, migrate, start application | High |
| **Online Migration** | Replicate changes while source remains active | Low |
| **Replication** | Keep source and target synchronized | Low |
| **Dual Write** | Application writes to both systems | Complex |
| **Dump & Import** | Export data and import into target | Depends on size |

### Production Preference

For critical production systems:

```text
Source DB
   ↓
Continuous / Online Migration
   ↓
Target Azure DB
   ↓
Validation
   ↓
Cutover
   ↓
Monitor
```

# 9. Connection Strings

<a id="connection-strings"></a>

A connection string contains information required by an application to connect to a database.

### Example — SQL

```text
Server=tcp:<server>.database.windows.net,1433;
Database=mydatabase;
User ID=<username>;
Password=<password>;
Encrypt=True;
```

### PostgreSQL Example

```text
Host=<server>;
Port=5432;
Database=mydatabase;
Username=<username>;
Password=<password>;
SSL Mode=require;
```

### MySQL Example

```text
Server=<server>;
Port=3306;
Database=mydatabase;
User=<username>;
Password=<password>;
SslMode=Required;
```

### Important

Connection strings often contain **credentials**.

Therefore:

```text
Connection String in Git ❌
Connection String in Dockerfile ❌
Connection String in Public Config ❌
```

Prefer:

```text
Application
    ↓
Environment / Secret Store
    ↓
Connection String
    ↓
Database
```

# 10. Environment-Specific Connection Strings

<a id="environment-connection"></a>

Do not use the same database configuration for every environment.

```text
Development → Dev Database
Testing     → Test Database
Staging     → Staging Database
Production  → Production Database
```

Example:

```text
Development
DB_HOST=dev-db.example.com

Production
DB_HOST=prod-db.example.com
```

The application should receive configuration from the deployment environment rather than hardcoding it.

<a id="secret-rotation"></a>

Secrets should be rotated periodically.

```text
Old Secret
    ↓
Create New Secret
    ↓
Update Key Vault
    ↓

    ↓
Validate
    ↓
```

### Production Considerations

- Avoid application downtime
- Maintain controlled rotation
- Test new credentials
- Monitor authentication failures
- Have rollback capability

# 16. Database Rollback

<a id="database-rollback"></a>

Database rollback requires more planning than application rollback.

```text
Application Rollback
        ≠
Database Rollback
```

Example:

```text
Application v2
     ↓
Database Schema v2
```

If application v2 fails:

```text
Application → v1
```

the database may already have schema changes.

Therefore use:

```text
Backward-Compatible DB Changes
        ↓
Deploy Application
        ↓
Validate
        ↓
Remove Old Schema Later
```

This is often called the **expand-and-contract** approach.

# 18. Hands-on — Key Vault Secret

<a id="hands-on-key-vault"></a>

Create Key Vault:

```bash
az keyvault create \
  --resource-group rg-database \
  --name my-keyvault-123 \
  --location centralindia
```

Store a secret:

```bash
az keyvault secret set \
  --vault-name my-keyvault-123 \
  --name DatabasePassword \
  --value '<StrongPassword>'
```

Retrieve:

```bash
az keyvault secret show \
  --vault-name my-keyvault-123 \
  --name DatabasePassword
```

> Do not expose secrets in terminal history, scripts, CI/CD logs, or source control in a real production environment.

**What will you check?**

```text
Environment Variables
        ↓
Connection String
        ↓
Secret / Key Vault
        ↓
Managed Identity
        ↓
RBAC
        ↓
DNS
        ↓
Private Endpoint
        ↓
Firewall
        ↓

```

**Commands:**

```bash
nslookup <database-host>
```

```bash
Test-NetConnection <database-host> -Port 1433
```

For PostgreSQL:

```powershell
Test-NetConnection <database-host> -Port 5432
```

For MySQL:

```powershell
Test-NetConnection <database-host> -Port 3306
```

**Root Cause:** Application was using an outdated connection string or could not retrieve the database secret.

**Fix:** Correct the secret/configuration and validate Managed Identity/RBAC access.

**Interview Answer:**  
"I first verify the application's environment configuration and connection string, then check Key Vault access, Managed Identity, RBAC, DNS, Private Endpoint, firewall, and database connectivity. Finally, I validate the connection from the application and review logs."

# 23. Interview Questions

<a id="database-devops-interview"></a>

### Q1. What is RPO?

**Answer:** Recovery Point Objective defines the maximum acceptable amount of data loss measured in time.

```text
RPO = How much data can we afford to lose?
```

### Q2. What is RTO?

**Answer:** Recovery Time Objective defines how quickly the service must be restored.

```text
RTO = How quickly must we recover?
```

### Q3. Why should database backups be tested?

**Answer:** A successful backup job does not guarantee that the backup can actually be restored successfully. Regular restore testing validates the recovery process.

### Q4. Where should database passwords be stored?

**Answer:** In a secure secret-management system such as Azure Key Vault rather than source code, Git repositories, Dockerfiles, or plain-text configuration files.

### Q5. How do you secure connection strings?

**Answer:** Store sensitive connection information in Key Vault or another approved secret store, use Managed Identity where supported, inject configuration at runtime, and prevent secrets from appearing in CI/CD logs.

### Q6. What is database migration?

**Answer:** Database migration is the controlled movement or transformation of database schema and data from one environment or database platform to another.

### Q7. How do you perform production database migration?

**Answer:**

```text
Assessment
→ Backup
→ Compatibility Check
→ Migration Plan
→ Test
→ Data Validation
→ Production Migration
→ Cutover
→ Smoke Test
→ Monitoring
→ Rollback/Recovery Plan
```

### Q8. Why is database rollback difficult?

**Answer:** Application rollback and database rollback are not always independent. A newer application may introduce schema changes that an older application cannot understand. Therefore database changes should be backward-compatible where possible.

### Q9. What is Managed Identity?

**Answer:** Managed Identity provides an Azure-managed identity that applications can use to authenticate to supported Azure services without storing credentials in application code.

### Q10. How do you troubleshoot a database connection failure?

**Answer:**

```text
Application Config
→ Connection String
→ Secret
→ Identity
→ RBAC
→ DNS
→ Network
→ Private Endpoint
→ Firewall
→ Port
→ Database
→ Logs
→ Root Cause
```

# 24. Best Practices

<a id="database-devops-best-practices"></a>

- Enable and monitor database backups.
- Define RPO and RTO.
- Test database restoration regularly.
- Maintain a documented migration plan.
- Version-control database migration scripts.
- Test migrations in lower environments.
- Use CI/CD for controlled database changes.
- Never commit passwords or connection strings to Git.
- Use Azure Key Vault for secrets.
- Prefer Managed Identity where supported.
- Use Private Endpoint for production database connectivity where appropriate.
- Rotate credentials regularly.
- Monitor database connections, performance, errors, and storage.
- Maintain a rollback/recovery plan.
- Validate data after every migration.
- Keep application and database changes backward-compatible where possible.

<a id="121-azure-functions"></a>

### 🔹 Why Azure Functions?

Azure Functions is best for event-driven or short-to-medium background workloads where the team wants Azure to handle infrastructure and scaling. The main DevOps responsibility shifts from server management to deployment, configuration, identity, observability, reliability and cost control.

**Production decision:** Choose Functions when the workload can be triggered by an event, schedule, HTTP request or message and does not require a continuously managed server.

# 12.1 Azure Functions

## Concept / Definition

\***\*Azure Functions\*\*** is a serverless compute service used to run code without managing servers directly.

You deploy a function and Azure manages:

- Compute infrastructure

- Scaling

- Runtime

- Availability

- Execution environment

You mainly focus on:

```text

Code  → Trigger  → Configuration  →  Dependencies

```

## Simple Architecture

```text

Event → Azure Function → Business Logic → Azure Service / Database / API

```

Example:

```text

Blob Upload → Azure Function → Process File → Storage / Database

```

## Supported Languages

Common runtimes include:

- C# , Java, JavaScript, TypeScript, Python, PowerShell

Choose the runtime based on application and team requirements.

<a id="122-architecture"></a>

### 🔹 Architecture Theory

A Function App is the deployment and hosting boundary. Functions inside the same app share the hosting environment, configuration and operational settings. In production, group functions that have similar runtime, scaling, security and deployment requirements; avoid putting unrelated high-load workloads into one Function App.

# 12.2 Architecture

## Important Components

### Function App

A \***\*Function App\*\*** is the Azure resource that hosts one or more functions.

```text

Function App

 ├── Function 1

 ├── Function 2

 └── Function 3

```

Functions inside an app normally share the same hosting environment and configuration.

### Function

A single unit of executable business logic.

### Trigger

Defines \***\*what starts the function\*\***.

### Binding

Provides an easy connection between the function and another service.

```text

Trigger → Function → Binding → Azure Service

```

### Hosting Plan

Important hosting choices include:

- Flex Consumption

- Consumption

- Premium

- Dedicated/App Service

For production, select the plan based on:

- Execution time

- Scaling requirement

- Cold-start sensitivity

- Networking requirement

- Cost

- Performance

<a id="123-triggers"></a>

### 🔹 Trigger Selection Theory

The trigger determines the event that starts execution. Choose the trigger based on how the business event arrives:

- HTTP for synchronous API/webhook requests
- Timer for scheduled work
- Queue for simple asynchronous background processing
- Event Grid for event notification and reactive processing
- Service Bus for enterprise messaging, retries and decoupled workflows
- Blob for file-oriented processing

**Interview point:** A Function has one trigger, but it can use multiple input/output bindings.

# 12.3 Triggers

A Function can have \***\*one trigger\*\***, which starts its execution.

## HTTP Trigger

Runs when an HTTP request arrives.

```text

Client → HTTP → Function → Response

```

Example use:

```text

POST /api/order

```

Typical use:

- API endpoint

- Webhook

- Lightweight backend logic

## Timer Trigger

Runs according to a schedule.

Example:

```text

Every day at 02:00

       ↓

Azure Function

       ↓

Cleanup Job

```

Typical use:

- Scheduled cleanup

- Report generation

- Health checks

- Batch processing

## Blob Trigger

Runs when Blob Storage activity occurs according to the trigger model used.

```text

Blob uploaded

     ↓

Function

     ↓

Process file

```

Use cases:

- Image processing

- CSV processing

- Document processing

- File validation

## Queue Trigger

Runs when a message is available in Azure Storage Queue.

```text

Producer

   ↓

Queue

   ↓

Function

   ↓

Process Message

```

Useful for asynchronous processing.

## Event Grid Trigger

Useful for event-driven architectures.

```text

Azure Resource

     ↓

Event Grid

     ↓

Function

```

Example:

```text

Blob Created

     ↓

Event Grid

     ↓

Function

```

## Service Bus Trigger

Useful when enterprise messaging features are required.

Typical use:

- Order processing

- Payment events

- Reliable asynchronous communication

<a id="124-bindings"></a>

### 🔹 Binding Theory

Bindings reduce boilerplate integration code, but they do not remove the need to understand authentication, permissions, retries, failures and service limits. In production, treat binding configuration as application configuration and secure its connection settings.

# 12.4 Bindings

## Concept

Bindings reduce the amount of infrastructure-specific code required inside a Function.

They can connect a function with Azure services for input/output.

### Input Binding

Reads data from another service.

```text

Function

   ↓

Input Binding

   ↓

Storage / Database

```

### Output Binding

Writes data to another service.

```text

Function

   ↓

Output Binding

   ↓

Queue / Blob / Service

```

## Example Concept

```text

HTTP Trigger

     ↓

Function

     ↓

Queue Output Binding

     ↓

Storage Queue

```

Instead of writing all connection/client handling manually, the binding configuration can handle the integration.

## Important Interview Point

\***\*Trigger starts the Function. Binding connects the Function to other services.\*\***

```text

Trigger = Why function runs

Binding = How function connects to data/service

```

<a id="125-durable-functions"></a>

### 🔹 Durable Functions Theory

Durable Functions are useful when a workflow must remember progress across multiple activities. The orchestrator coordinates the workflow while activity functions perform individual tasks.

**Production point:** Keep activities small and retry-safe. Design workflows so duplicate execution does not create duplicate payments, orders or notifications.

# 12.5 Durable Functions

## Concept

Durable Functions extend Azure Functions for \***\*stateful workflows and long-running orchestration\*\***.

Normal Function:

```text

Request

 ↓

Function

 ↓

Response

```

Durable Function:

```text

Orchestrator

 ↓

Activity 1

 ↓

Activity 2

 ↓

Activity 3

 ↓

Final Result

```

Useful when multiple steps must be coordinated.

## Important Components

### Orchestrator

Controls workflow execution.

### Activity

Performs actual business work.

### Entity

Used for stateful operations where supported.

## Example

NexCart order workflow:

```text

Order Created

      ↓

Validate Order

      ↓

Process Payment

      ↓

Update Inventory

      ↓

Send Notification

      ↓

Order Completed

```

If payment temporarily fails, the workflow can use retry/orchestration patterns instead of implementing everything as one large function.

## When to Use Durable Functions

Use when you need:

- Multi-step workflows

- Long-running operations

- Retry logic

- Fan-out/fan-in

- Stateful orchestration

- Scheduled workflow continuation

Do not use Durable Functions for every simple Function.

<a id="126-configuration"></a>

### 🔹 Configuration Theory

Treat configuration as environment-specific data, not application code. Dev, QA, UAT and Production should use separate settings. Non-secret settings can use application settings, while secrets should be retrieved securely through Key Vault and Managed Identity.

# 12.6 Configuration

## Application Settings

Store environment-specific configuration outside the code.

Example:

```text

APP_ENV=production

API_URL=https\://api.example.com

LOG_LEVEL=Information

```

Access them from Function configuration/environment variables.

## Environment Separation

Use:

```text

Development

QA

UAT

Production

```

Avoid putting production values directly into source code.

## Secrets

Do not store:

```text

Password

API Key

Connection String

Client Secret

```

inside Git repository.

Preferred pattern:

```text

Function

   ↓

Managed Identity

   ↓

Key Vault

   ↓

Secret

```

<a id="127-security"></a>

### 🔹 Security Theory

The preferred production model is passwordless access using Microsoft Entra ID and Managed Identity. Give the Function only the permissions it needs, protect secrets with Key Vault and restrict network exposure where the workload requires private access.

# 12.7 Security

## Managed Identity

Managed Identity allows a Function App to access Azure resources without storing credentials in application code.

```text

Function App

     ↓

Managed Identity

     ↓

Microsoft Entra ID

     ↓

Azure Resource

```

Example:

```text

Function

   ↓

Managed Identity

   ↓

Key Vault

```

## Key Vault

Use Key Vault for:

- Secrets

- Certificates

- Keys

Do not hardcode secrets in:

- Python

- JavaScript

- C#

- YAML

- Git

- Dockerfile

## Least Privilege

Function should receive only required permissions.

Example:

```text

Function

  ↓

Storage Reader

```

instead of:

```text

Function

  ↓

Subscription Owner

```

## Network Security

For sensitive workloads consider:

- Private Endpoint

- VNet integration

- Restricted inbound access

- Firewall rules

- Authentication/authorization

Do not expose internal Functions publicly without a requirement.

<a id="128-cicd"></a>

### 🔹 CI/CD Theory

A production Function deployment should be repeatable and traceable. Source code is built and tested in CI, security checks are performed, an immutable deployable package is produced, and CD deploys it to the intended environment with validation and rollback capability.

# 12.8 CI/CD

## Production Flow

```text

Developer

   ↓

GitLab

   ↓

CI Pipeline

   ↓

Build

   ↓

Unit Tests

   ↓

Security Scan

   ↓

Package

   ↓

Deploy

   ↓

Azure Function

   ↓

Health Verification

```

## Example Azure CLI Deployment

```bash

az functionapp deployment source config-zip \\

  --resource-group rg-nexcart \\

  --name func-nexcart \\

  --src function.zip

```

## Configuration Through CLI

```bash

az functionapp config appsettings set \\

  --resource-group rg-nexcart \\

  --name func-nexcart \\

  --settings APP_ENV=production

```

For secrets, prefer Key Vault/managed identity rather than passing secret values through pipeline variables whenever possible.

## Pipeline Stages

Recommended:

```text

Build

 ↓

Test

 ↓

Security Scan

 ↓

Package

 ↓

Deploy Dev

 ↓

Validation

 ↓

Deploy QA

 ↓

Approval

 ↓

Deploy Production

```

## Rollback

Keep previous deployable versions.

Possible rollback approaches depend on hosting/deployment model:

```text

Previous Package

      ↓

Redeploy

```

or use deployment slots where supported and appropriate.

<a id="129-monitoring"></a>

### 🔹 Monitoring Theory

Function monitoring should answer four questions: Is it available? Is it succeeding? Is it fast enough? Are dependencies healthy? Use Azure Monitor/Application Insights for metrics, logs, exceptions, requests and dependency visibility, then create alerts only for actionable conditions.

# 12.9 Monitoring

## What to Monitor

Monitor:

- Function execution count

- Success/failure

- Execution duration

- Exceptions

- Dependency failures

- Memory

- HTTP response codes

- Queue backlog

- Retry behavior

## Application Insights

Common production observability path:

```text

Function

   ↓

Application Insights

   ↓

Logs + Requests + Exceptions + Dependencies

```

Useful for:

- Request tracing

- Exceptions

- Dependency calls

- Performance

- Application logs

## Alerts

Useful alerts:

```text

Function failures ↑

Execution duration ↑

HTTP 5xx ↑

Queue messages ↑

Dependency failures ↑

```

## Production Dashboard

Example:

```text

Function Health

├── Requests

├── Success %

├── Failure %

├── Avg Duration

├── P95/P99 Duration

├── Exceptions

└── Dependency Failures

```

<a id="1211-troubleshooting"></a>

### 🔹 Troubleshooting Method

Use the same production method used for other Azure workloads:

**Alert → Scope → Metrics → Logs → Configuration → Identity → Dependency → Network → Root Cause → Fix → Verify → Prevent**

Do not start with a restart. First collect enough evidence to understand the failure.

# 12.11 Troubleshooting

## Function Not Triggering

Check:

```bash

az functionapp show \\

  -g \<resource-group> \\

  -n \<function-app>

```

Check:

- Trigger configuration

- Connection configuration

- Function enabled state

- Runtime version

- Application logs

- Event source

- Permissions

## HTTP Function Returns 500

Check:

```text

Request

 ↓

Function Logs

 ↓

Exception

 ↓

Dependency

 ↓

Configuration

```

Look for:

- Application exception

- Missing environment variable

- Key Vault access issue

- Database failure

- Invalid input

- Dependency timeout

## Function Is Slow

Check:

- Cold start

- External API latency

- Database latency

- Dependency calls

- Large payload

- Function execution time

- Hosting plan

Do not immediately increase compute without finding the bottleneck.

## Queue Messages Are Increasing

```text

Producer

   ↓

Queue

   ↓

Function

   ↓

Processing

```

If queue backlog continuously increases:

Check:

- Function failures

- Function concurrency

- Processing time

- Downstream dependency

- Scaling behavior

- Poison messages

## Key Vault Access Failure

Check:

```text

Function Identity

      ↓

Role / Permission

      ↓

Key Vault Access

      ↓

Network

      ↓

Secret

```

Common causes:

- Managed Identity disabled

- Wrong identity

- Missing permission

- Wrong Key Vault

- Secret name incorrect

- Private networking issue

## Deployment Successful but Old Code Runs

Check:

- Correct Function App

- Correct environment

- Deployment package

- Deployment slot

- Pipeline target

- Application version

- Configuration

<a id="1213-interview-questions"></a>

# 12.13 Interview Questions

### Q1. What is Azure Functions?

\***\*Answer:\*\*** Azure Functions is a serverless compute service where we run event-driven code without directly managing servers.

### Q2. What is a Function App?

\***\*Answer:\*\*** A Function App is the Azure resource that hosts one or more Functions and provides the runtime, configuration and hosting environment.

### Q3. Trigger vs Binding?

\***\*Answer:\*\***

```text

Trigger

→ starts the Function

Binding

→ connects the Function with input/output data or services

```

### Q4. What is a Timer Trigger?

\***\*Answer:\*\*** It executes a Function according to a configured schedule. It is useful for scheduled jobs such as cleanup, reports and maintenance.

### Q5. When would you use Durable Functions?

\***\*Answer:\*\*** For stateful, multi-step or long-running workflows where orchestration, retries, fan-out/fan-in or workflow state is required.

### Q6. How do you secure secrets in Azure Functions?

\***\*Answer:\*\*** I avoid hardcoding secrets and use Managed Identity with Azure Key Vault wherever possible.

### Q7. How do you deploy Functions?

\***\*Answer:\*\***

```text

Git

 ↓

CI

 ↓

Build/Test

 ↓

Package

 ↓

Deploy

 ↓

Validate

```

Deployment can be automated through Azure DevOps, GitHub Actions, GitLab CI/CD or other supported deployment methods.

### Q8. How do you monitor Azure Functions?

\***\*Answer:\*\*** I use Application Insights and Azure Monitor to track executions, failures, exceptions, duration and dependencies, and configure alerts for production issues.

### Q9. Function is returning 500. What will you check?

\***\*Answer:\*\***

```text

Application Insights

 ↓

Exception

 ↓

Application logs

 ↓

Configuration

 ↓

Dependencies

 ↓

Authentication

```

### Q10. Queue backlog is increasing. What will you check?

\***\*Answer:\*\*** I check Function failures, processing duration, concurrency/scaling, poison messages and downstream dependencies.

### Q11. Function cannot access Key Vault. What will you check?

\***\*Answer:\*\*** I check Managed Identity, required RBAC/permissions, Key Vault name/secret, networking and application configuration.

### Q12. When should you NOT use Azure Functions?

\***\*Answer:\*\*** Avoid Functions when the workload requires long-running dedicated compute, complex always-on application servers, highly specialized runtime requirements or predictable workloads where another hosting model is more suitable.

### Q13. Consumption vs Premium?

\***\*Answer:\*\*** Consumption is designed for serverless workloads with automatic scaling and usage-based characteristics. Premium provides features such as pre-warmed instances and better control for workloads with stronger performance/networking requirements. The exact available plans and features depend on the current Azure Functions hosting model.

### Q14. How would you design a production event-driven application?

\***\*Answer:\*\***

```text

Application

 ↓

Event / Queue

 ↓

Function

 ↓

Business Logic

 ↓

Database / Service

 ↓

Monitoring + Alerting

```

I would also add authentication, retry handling, dead-letter handling where applicable, least-privilege identity and observability.

<a id="1214-best-practices"></a>

### 🔹 Production Principles

The most important production principles are idempotency, least privilege, externalized configuration, secure identity, controlled retries, dead-letter handling, observability and safe deployment/rollback.

# 12.14 Best Practices

## Application

- Keep Functions small and focused

- Avoid unnecessary long-running operations

- Make event processing idempotent

- Handle retries safely

- Use asynchronous processing for suitable workloads

## Configuration

- Keep configuration outside code

- Separate Dev/QA/Prod settings

- Never commit secrets

- Use Key Vault for sensitive values

## Security

- Prefer Managed Identity

- Use least privilege

- Restrict public access when unnecessary

- Use private networking for sensitive workloads where required

## CI/CD

```text

Build

→ Test

→ Scan

→ Package

→ Deploy

→ Validate

```

- Use automated deployment

- Keep version history

- Protect production deployment

- Use approvals where required

## Reliability

- Implement retry strategy carefully

- Handle duplicate events

- Design idempotent processing

- Handle poison/dead-letter messages

- Monitor dependency failures

- Test failure scenarios

## Monitoring

- Monitor success/failure rate

- Monitor duration

- Monitor exceptions

- Monitor dependencies

- Configure actionable alerts

- Keep production dashboards

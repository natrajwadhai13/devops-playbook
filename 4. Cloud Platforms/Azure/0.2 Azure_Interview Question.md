## Q1. GitLab pipeline fails during the build stage. How will you troubleshoot it?

### 1. What will you check?

- Check the **GitLab job logs** and identify the exact error.
- Check whether the **GitLab Runner** is available and healthy.
- Check the required runtime/tool versions — Java, Node.js, Python, Maven, npm, Docker, etc.
- Check the source code and build files such as `pom.xml`, `package.json`, `Dockerfile`, etc.
- Check required **CI/CD variables**.
- Check dependency download or network issues.
- Identify whether the failure is during **compile, dependency installation, testing, or Docker build**.

### 2. Commands

```bash
# Check Runner
gitlab-runner status

# Check Java
java -version

# Check Maven
mvn -version

# Check Node.js
node -v
npm -v

# Check Docker
docker version

# Check environment variables
env

# Test Maven build
mvn clean package

# Test Node.js build
npm install
npm run build

# Test Docker build
docker build -t myapp:latest .
```

### 3. Root Cause

Common causes:

- Compilation error
- Missing dependency
- Incorrect runtime version
- Missing CI/CD variable
- Runner environment issue
- Network/repository issue
- Docker build failure
- Permission issue

### 4. Fix

First identify the exact failing stage from the GitLab logs.

Then fix the corresponding issue:

- Correct the code/build configuration.
- Install or configure the required runtime.
- Add missing CI/CD variables.
- Fix dependency or network issues.
- Correct the Dockerfile.
- Fix Runner configuration.

Then rerun the pipeline and verify the complete build.

### 5. Interview Answer

> "If the GitLab pipeline fails during the build stage, first I check the GitLab job logs and identify the exact error and failing command. Then I verify the Runner, runtime versions, dependencies, environment variables, and build configuration. If required, I reproduce the same build locally. Based on the root cause, I fix the issue and rerun the pipeline."

**Keywords:** `Job Logs → Runner → Runtime → Dependencies → Variables → Build → Root Cause → Fix → Rerun`

## Q2. GitLab Runner is unable to connect to Azure. What will you check?

### 1. What will you check?

I will check:

- Whether Azure CLI is installed on the Runner.
- Whether the Runner has internet connectivity.
- Whether the Azure endpoint is reachable.
- Whether Azure credentials are configured correctly.
- Whether the Service Principal is valid.
- Check `Tenant ID`, `Client ID`, and `Client Secret`.
- Check whether the Service Principal has required Azure RBAC permissions.
- Check whether the subscription is correct.
- Check proxy/firewall restrictions if applicable.

### 2. Commands

```bash
# Check Azure CLI
az version

# Check Azure CLI login
az login

# Check current account
az account show

# List subscriptions
az account list

# Set subscription
az account set --subscription "<subscription-id>"

# Test Azure resource access
az group list
```

For Service Principal authentication:

```bash
az login \
  --service-principal \
  --username "$AZURE_CLIENT_ID" \
  --password "$AZURE_CLIENT_SECRET" \
  --tenant "$AZURE_TENANT_ID"
```

### 3. Root Cause

Possible causes:

- Azure CLI not installed.
- Runner has no internet access.
- Incorrect Azure credentials.
- Expired Service Principal secret.
- Wrong Tenant ID or Subscription ID.
- Missing RBAC permissions.
- Firewall/proxy/network restrictions.

### 4. Fix

- Install/configure Azure CLI on the Runner.
- Fix network/proxy connectivity.
- Correct Azure credentials.
- Rotate an expired Service Principal secret if required.
- Assign the required Azure RBAC role.
- Verify the correct subscription and tenant.

Then test Azure authentication again.

### 5. Interview Answer

> "If the GitLab Runner cannot connect to Azure, first I check Azure CLI installation and network connectivity. Then I verify the Tenant ID, Client ID, credentials, subscription, and Service Principal permissions. I also check whether the credentials are expired and whether any firewall or proxy is blocking the connection. After fixing the issue, I test `az login` and verify Azure resource access."

**Keywords:** `Runner → Azure CLI → Network → Credentials → Service Principal → Tenant → Subscription → RBAC`

## Q3. `az login` fails inside the GitLab Runner. How will you troubleshoot it?

### 1. What will you check?

- Check whether Azure CLI is installed.
- Check the Azure CLI version.
- Check the authentication method.
- Verify `Client ID`.
- Verify `Client Secret`.
- Verify `Tenant ID`.
- Check whether the secret has expired.
- Check Runner network connectivity.
- Check whether the Service Principal is disabled.
- Check Azure permissions.

### 2. Commands

```bash
# Check Azure CLI
az version

# Service Principal login
az login \
  --service-principal \
  --username "$AZURE_CLIENT_ID" \
  --password "$AZURE_CLIENT_SECRET" \
  --tenant "$AZURE_TENANT_ID"

az account show

# Check subscription
az account list
```

You can also check variables without exposing secret values:

```bash
echo "$AZURE_CLIENT_ID"
echo "$AZURE_TENANT_ID"
```

### 3. Root Cause

Common causes:

- Wrong Client ID.
- Wrong Tenant ID.
- Invalid or expired Client Secret.
- Service Principal disabled.
- Azure CLI issue.
- Network connectivity problem.
- Incorrect authentication configuration.

### 4. Fix

- Correct the GitLab CI/CD variables.
- Rotate an expired secret.
- Verify the Service Principal.
- Verify the Tenant ID.
- Ensure the Runner can reach Azure.
- Make sure the required permissions are assigned.

### 5. Interview Answer

> "If `az login` fails inside the GitLab Runner, I first check the Azure CLI and authentication method. Then I verify the Client ID, Tenant ID, and Client Secret stored in GitLab CI/CD variables. I also check whether the secret is expired, whether the Service Principal is active, and whether the Runner has network connectivity. I fix the root cause and verify the login using `az account show`."

**Keywords:** `Azure CLI → Service Principal → Client ID → Tenant ID → Secret → Network → RBAC`

## Q4. How will you securely authenticate GitLab with Azure?

### 1. What will you check?

The main requirement is to avoid storing credentials directly in the GitLab repository.

I will check:

- GitLab CI/CD Variables.
- Service Principal or preferably **Workload Identity Federation / OIDC**, where supported.
- Secret protection and masking.
- Least-privilege Azure RBAC.
- Separate credentials for different environments.

### 2. Commands

For Service Principal authentication:

```bash
az login \
  --service-principal \
  --username "$AZURE_CLIENT_ID" \
  --password "$AZURE_CLIENT_SECRET" \
  --tenant "$AZURE_TENANT_ID"

az account set --subscription "$AZURE_SUBSCRIPTION_ID"
```

Verify:

```bash
az account show
```

### 3. Root Cause

A common security problem is:

- Azure credentials hardcoded in `.gitlab-ci.yml`.
- Secrets committed to Git.
- Excessive Azure permissions.
- Credentials not protected or masked.

### 4. Fix

Store sensitive values in **GitLab CI/CD Variables** and mark them as:

- Masked
- Protected

Use least-privilege Azure RBAC.

Where possible, use **OIDC/workload identity federation** instead of long-lived client secrets.

### 5. Interview Answer

> "I would never hardcode Azure credentials in the GitLab repository. I would store required credentials as protected and masked GitLab CI/CD variables. I would use a Service Principal with least-privilege RBAC, or preferably workload identity federation using OIDC where supported, to avoid long-lived secrets."

**Keywords:** `CI/CD Variables → Masked → Protected → Service Principal → OIDC → Least Privilege → RBAC`

## Q6. The Docker image is not being pushed to Azure Container Registry (ACR). How will you troubleshoot it?

### 1. What will you check?

- Check whether Docker is running.
- Check whether the image was built successfully.
- Check ACR login.
- Check ACR name and login server.

### 2. Commands

```bash
# Check Docker

# Check ACR
az acr show --name <acr-name>

az acr repository list --name <acr-name>

docker build -t myapp:latest .

# Tag image
docker tag myapp:latest <acr-name>.azurecr.io/myapp:latest

docker push <acr-name>.azurecr.io/myapp:latest
```

### 3. Root Cause

Common causes:

- ACR authentication failure.
- Incorrect ACR name.
- Incorrect image tag.
- Missing `AcrPush` permission.

### 4. Fix

- Correct ACR authentication.
- Verify the image name and tag.
- Assign required `AcrPush` permission.
- Fix Docker configuration.
- Correct the pipeline variables.

Then push the image again.

### 5. Interview Answer

> "If the Docker image is not pushed to ACR, I first check the GitLab logs and verify that the Docker build completed successfully. Then I check ACR login, image tagging, ACR name, network connectivity, and the Service Principal's AcrPush permission. After fixing the issue, I push the image again and verify it in ACR."

## Q7. GitLab pipeline deploys the wrong Docker image tag to AKS. What will you check?

### 1. What will you check?

I will check:

- Docker image tag generated during the pipeline.
- Git commit SHA/tag used for the image.
- GitLab CI/CD variables.
- Kubernetes Deployment YAML.
- Image name and tag in the Deployment.
- Whether the correct image was pushed to ACR.
- Whether AKS is using an old cached image.
- Pipeline variables passed between stages.

### 2. Commands

```bash
# Check images in ACR
az acr repository show-tags \
  --name <acr-name> \
  --repository <repo-name>

# Check deployment
kubectl get deployment <deployment-name> -o yaml

# Check current image
kubectl get deployment <deployment-name> \
  -o jsonpath='{.spec.template.spec.containers[*].image}'

# Check pods
kubectl get pods

# Check pod image
kubectl describe pod <pod-name>
```

### 3. Root Cause

Possible causes:

- Wrong CI/CD variable.
- Incorrect image tag.
- Deployment YAML contains an old tag.
- Pipeline passes the wrong tag between stages.
- Same `latest` tag is being reused.
- Kubernetes is using a previously pulled image.

### 4. Fix

Use a **unique immutable image tag**, preferably based on the Git commit SHA.

For example:

```text
myapp:8f3a21c
```

Update the Kubernetes deployment with the correct image:

```bash
kubectl set image deployment/myapp \
  myapp=<acr-name>.azurecr.io/myapp:<correct-tag>
```

Then verify:

```bash
kubectl rollout status deployment/myapp
```

### 5. Interview Answer

> "If AKS receives the wrong Docker image tag, I first compare the image tag generated by GitLab with the tag available in ACR and the tag configured in the Kubernetes Deployment. I check the pipeline variables and deployment YAML. I prefer immutable tags such as the Git commit SHA instead of repeatedly using `latest`. After correcting the tag, I redeploy and verify the running pod image."

**Keywords:** `Git Commit SHA → Image Tag → ACR → Deployment YAML → kubectl → Immutable Tag`

I will compare the manual environment with the GitLab Runner environment.

- `kubectl` version.

### 3. Root Cause

Common reasons:

- GitLab Runner is not authenticated with AKS.
- Different Kubernetes context.
- Wrong namespace.
- Missing RBAC permissions.
- Missing CI/CD variables.

- Different Kubernetes configuration.

### 4. Fix

- Authenticate the Runner correctly.
- Configure the correct AKS context.
- Use the correct namespace.
- Assign required Kubernetes RBAC permissions.
- Configure required GitLab variables.
- Verify Runner-to-AKS network connectivity.

### 5. Interview Answer

> "If manual `kubectl` deployment works but GitLab deployment fails, I compare the manual environment with the GitLab Runner environment. I check Azure authentication, AKS credentials, Kubernetes context, namespace, RBAC permissions, CI/CD variables, and network connectivity. **Keywords:** `Runner → AKS Credentials → Context → Namespace → RBAC → Variables → Network`

**Keywords:** `Pipeline → ACR → Image Tag → Deployment → Pod → Rollout → Application Version`

## Q10. How will you implement automatic rollback when a GitLab deployment fails?

### 1. What will you check?

Before implementing rollback, I will check:

- Kubernetes Deployment strategy.
- Readiness and liveness probes.
- Deployment rollout status.
- Previous successful ReplicaSet.
- Health checks.
- GitLab pipeline stages.
- Failure conditions.

### 2. Commands

Check rollout:

```bash
kubectl rollout status deployment/myapp
```

Check history:

```bash
kubectl rollout history deployment/myapp
```

Rollback:

```bash
kubectl rollout undo deployment/myapp
```

Verify:

```bash
kubectl rollout status deployment/myapp
```

### 3. Root Cause

A deployment may fail because:

- New application version crashes.
- Container fails health checks.
- Image is incorrect.
- Configuration is wrong.
- Application cannot connect to dependencies.
- New version does not become Ready.

### 4. Fix

Implement deployment validation in GitLab.

Example flow:

```text
Build
   ↓
Test
   ↓
Docker Build
   ↓
Push to ACR
   ↓
Deploy to AKS
   ↓
Check Rollout
   ↓
Health Check
   ↓
Success → Continue
Failure → Rollback
```

Example:

```bash
kubectl apply -f deployment.yaml

kubectl rollout status deployment/myapp --timeout=120s

if [ $? -ne 0 ]; then
    kubectl rollout undo deployment/myapp
    exit 1
fi
```

### 5. Interview Answer

> "I would implement automatic rollback by validating the Kubernetes rollout after deployment. GitLab first deploys the new version and waits for `kubectl rollout status`. If the rollout or health check fails, the pipeline executes `kubectl rollout undo` to return to the previous stable ReplicaSet. I would also use proper readiness and liveness probes so that unhealthy pods are detected automatically."

**Keywords:** `Deploy → Rollout Status → Health Check → Failure → Rollout Undo → Previous Stable Version`

## Q14. A new image was pushed using the same Docker tag, but AKS is still running the old image. Why?

### 1. What will you check?

The main thing I will check is whether we are **reusing the same mutable tag**, such as `latest`.

I will check:

- Current image tag in the Deployment.
- Image pull policy.
- Pod creation time.
- Image digest.
- Whether the new image was actually pushed.
- Whether the Deployment triggered a new rollout.

### 2. Commands

Check the Deployment:

```bash
kubectl get deployment myapp -o yaml
```

Check image:

```bash
kubectl get deployment myapp \
  -o jsonpath='{.spec.template.spec.containers[*].image}'
```

Check image pull policy:

```bash
kubectl get deployment myapp \
  -o jsonpath='{.spec.template.spec.containers[*].imagePullPolicy}'
```

Check pod:

```bash
kubectl describe pod <pod-name>
```

Restart deployment if required:

```bash
kubectl rollout restart deployment/myapp
```

### 3. Root Cause

The common issue is **reusing the same tag**.

For example:

```text
myapp:latest
```

First deployment:

```text
myapp:latest → Version 1
```

Later:

```text
myapp:latest → Version 2
```

Kubernetes may continue running the previously pulled image depending on the rollout and `imagePullPolicy`.

### 4. Fix

The best approach is to use **unique immutable tags**, such as:

```text
myapp:1.0.1
myapp:1.0.2
```

or preferably a Git commit SHA:

```text
myapp:8f3a21c
```

Then update the Deployment with the new tag.

```bash
kubectl set image deployment/myapp \
  myapp=<acr-name>.azurecr.io/myapp:8f3a21c

kubectl rollout status deployment/myapp
```

### 5. Interview Answer

> "If a new image is pushed using the same tag but AKS is still running the old version, the likely reason is that the tag is mutable, for example `latest`. I would check the image pull policy and deployment rollout. My preferred approach is to use unique immutable image tags such as the Git commit SHA. This makes every deployment traceable and avoids image caching and version confusion."

**Keywords:** `Mutable Tag → latest → ImagePullPolicy → Rollout → Immutable Tag → Git SHA`

**Keywords:** `RBAC → Least Privilege → AcrPush → AcrPull → Managed Identity → Image Scan → Immutable Tags → Private Access`

## Q22. A deployment is successful, but old pods are still running. Why?

### 1. What will you check?

I will check:

- Deployment rollout status.
- ReplicaSets.
- Pod creation time.
- Deployment strategy.
- Whether the new ReplicaSet is Ready.
- Whether the old ReplicaSet is still scaling down.

### 2. Commands

```bash
# Deployment
kubectl get deployment <deployment-name>

# ReplicaSets
kubectl get rs

# Pods
kubectl get pods -o wide

# Rollout status
kubectl rollout status deployment/<deployment-name>

# Rollout history
kubectl rollout history deployment/<deployment-name>
```

### 3. Root Cause

During a Kubernetes **RollingUpdate**, Kubernetes does not immediately delete all old pods.

It gradually:

```text
Old Pods
   ↓
Create New Pods
   ↓
Wait for New Pods to become Ready
   ↓
Scale Down Old Pods
```

Old pods may temporarily remain during the rollout.

Other possible reasons:

- New pods are not Ready.
- `maxSurge` / `maxUnavailable` configuration.
- Rollout is still in progress.
- Deployment is stuck.

### 4. Fix

If the rollout is healthy, wait for completion.

If it is stuck:

```bash
kubectl describe deployment <deployment-name>
kubectl get rs
kubectl describe pod <pod-name>
```

Then fix the underlying issue.

### 5. Interview Answer

> "During a Kubernetes RollingUpdate, old pods can temporarily remain because Kubernetes gradually creates new pods and removes old ones. I check the rollout status and ReplicaSets to confirm whether the rollout is still in progress. If the old pods remain after the rollout should be complete, I investigate readiness, deployment strategy, and ReplicaSet status."

**Keywords:** `RollingUpdate → New Pods → Ready → Old Pods → ReplicaSet → maxSurge → maxUnavailable`

## Q24. How will you implement zero-downtime deployment in AKS?

### 1. What will you check?

- Readiness probes are missing or incorrect.
- `maxUnavailable` is too high.
- Application takes time to start.
- Not enough replicas are running.

### 4. Fix

Use:

- Multiple replicas.
- RollingUpdate strategy.
- `maxUnavailable: 0`.
- Appropriate `maxSurge`.
- Proper readiness probes.
- Proper liveness probes.
- Sufficient cluster resources.

Example:

```text
Old Pods:  3
     ↓
Create New Pod
     ↓
New Pod becomes Ready
     ↓
Remove Old Pod
     ↓
Repeat
```

### 5. Interview Answer

> "For zero-downtime deployment, I use a Kubernetes RollingUpdate strategy with multiple replicas. I configure `maxUnavailable` to zero so that existing healthy pods remain available while new pods are created. I also use proper readiness probes so Kubernetes sends traffic only to healthy new pods. After deployment, I verify the rollout status."

**Keywords:** `Multiple Replicas → RollingUpdate → maxUnavailable 0 → maxSurge → Readiness Probe`

### 1. What will you check?

I will check:

- Two versions of the application: **Blue** and **Green**.

- Kubernetes Service.
- Labels/selectors.
- Health of the new version.
- Traffic switching strategy.
- Rollback plan.

### 2. Commands

Check deployments:

```bash

```

Check services:

```bash

```

Check pods:

```bash

```

Example:

```yaml id="u0f0pn"

  app: myapp
  version: blue
```

```yaml id="xk9bby"
# Green
labels:
  app: myapp
  version: green
```

Service initially points to Blue:

```yaml id="mml7t6"

  app: myapp
  version: blue
```

After testing Green, change the Service selector:

```yaml id="t5ijqv"

  app: myapp
  version: green
```

The **Green** environment contains the new version.

### 4. Fix / Deployment Flow

```text
Production Traffic
       ↓
     Service
       ↓
   Blue Version
       │
       │ New Version
       ↓
  Green Version
       ↓
   Test Green
       ↓
Switch Service
       ↓
Production Traffic
       ↓
  Green Version
```

### 5. Interview Answer

> "For Blue/Green deployment, I maintain two versions of the application, Blue and Green. Blue is the current production version, while Green contains the new version. I deploy and test Green separately. Once it passes health checks and validation, I switch the Kubernetes Service selector from Blue to Green. If there is an issue, I can quickly switch the Service back to Blue."

**Keywords:** `Blue → Green → Separate Deployment → Service Selector → Test → Traffic Switch → Rollback`


```bash
kubectl get svc
```

```yaml
                port:
                  number: 80
```

```yaml
          - path: /
            pathType: Prefix

              service:
                name: app2-service

                  number: 80
```

```text
                  Internet
                     |
              AKS Ingress
               /         \
              /           \
     app1.example.com   app2.example.com
           |                   |

           |                   |
        App 1              App 2
```

### 5. Interview Answer

> "I can expose multiple applications through the same AKS Ingress by using host-based or path-based routing. **Keywords:** `Ingress Controller → Host-Based Routing → Path-Based Routing → Service → DNS`

## 37. How will you configure the AKS Cluster Autoscaler?

### 1. What will you check?

Cluster Autoscaler works at the **node level**.

It automatically:

- Adds nodes when pods cannot be scheduled because of insufficient resources.
- Removes underutilized nodes when they are no longer required.

I first check:

- AKS cluster.
- Node pool name.
- Minimum node count.
- Maximum node count.
- Current node count.

### 2. Commands

List node pools:

```bash

  --cluster-name <aks-cluster> \
  -o table
```

```bash
az aks nodepool update \
  --resource-group <resource-group> \
  --cluster-name <aks-cluster> \
  --name <nodepool-name> \
  --enable-cluster-autoscaler \
  --min-count 2 \
  --max-count 5
```

Check configuration:

```bash
az aks nodepool show \
  --resource-group <resource-group> \
  --cluster-name <aks-cluster> \
  --name <nodepool-name> \
```

### 4. Fix / Configuration

Typical architecture:

```text
High Application Load
        ↓
       HPA
        ↓
More Pods Required
        ↓
Insufficient Node Resources
        ↓
Cluster Autoscaler
        ↓
New AKS Node
        ↓
Pods Scheduled
```

Configure suitable:

- `min-count`
- `max-count`
- Node pool size
- Resource requests

### 5. Interview Answer

> **“I configure Cluster Autoscaler on the AKS node pool with minimum and maximum node counts. When pods cannot be scheduled because of insufficient node resources, Cluster Autoscaler adds nodes. When capacity is no longer required, it can scale down nodes. I also make sure pod resource requests are configured correctly.”**

**Keywords:** HPA = Pod scaling → Cluster Autoscaler = Node scaling

## 43. How will you create separate system and user node pools in AKS?

- **User node pool** → runs application workloads.

- Existing node pools.
- VM size.
- Minimum/maximum node count.
- Availability requirements.
- Application workload requirements.

```bash
az aks nodepool add \
  --resource-group <resource-group> \

  --mode System \
  --node-vm-size Standard_D4s_v5
```

Create a user node pool:

```bash
az aks nodepool add \
  --resource-group <resource-group> \
  --cluster-name <aks-cluster> \
  --name userpool \

  --mode User \
  --node-vm-size Standard_D4s_v5
```

Verify:

```bash
az aks nodepool list \
  --resource-group <resource-group> \
  --cluster-name <aks-cluster> \
  -o table
```

```text
AKS Cluster
     |
     +-- System Node Pool
     |      └── AKS system components
     |
     +-- User Node Pool
            └── Application Pods
```

This helps prevent application workloads from consuming all resources needed by system components.

### 4. Fix / Configuration

For production, I would typically:

- Keep at least the required healthy capacity in the system pool.
- Use user pools for application workloads.
- Configure autoscaling as required.
- Use labels/taints when workload isolation is needed.

Check node labels:

```bash
kubectl get nodes --show-labels
```

### 5. Interview Answer

> **“In AKS, I can create separate system and user node pools. The system node pool is used for critical AKS system workloads, while the user node pool is used for application workloads. I create the pools using az aks nodepool add with the appropriate mode, System or User. This provides better workload isolation and resource management.”**

**Keywords:** System Pool → User Pool → Workload Isolation → Resource Management → Autoscaling

## 51. An AKS application needs to access Azure Key Vault. How will you implement this securely?

### 1. What will you check?

For AKS, I would use:

- **Microsoft Entra Workload Identity**
- **Azure Key Vault**
- **Azure Key Vault CSI Driver**

- Kubernetes ServiceAccount

```text
AKS Pod
   ↓
Kubernetes ServiceAccount
   ↓
Workload Identity
   ↓
Microsoft Entra ID
   ↓
Azure Key Vault
   ↓
Secret

```


```text

     ↓
```

### 5. Interview Answer

> **“For an AKS application accessing Key Vault, I would use Microsoft Entra Workload Identity instead of storing credentials in the application. I create a managed identity, associate it with a Kubernetes ServiceAccount and provide only the required Key Vault RBAC permissions. **Keywords:** Workload Identity → Managed Identity → ServiceAccount → Key Vault → RBAC → CSI Driver

## 53. A secret was accidentally committed to the GitLab repository. What will you do?

### 1. What will you check?

I treat the secret as **compromised** immediately.

I check:

- What type of secret was exposed?
- Is it still valid?
- Where was it committed?
- Was it pushed to remote?
- Is it present in Git history?
- Who could access the repository?

### 2. Commands

Find the commit:

```bash
git log --all --oneline
```

Search repository history:

```bash
git log --all -S"SECRET_VALUE" --oneline
```

Check repository status:

```bash
git status
```

### 3. Root Cause

The secret was stored directly in source control.

For example:

```text
password=MyPassword123
```

Even if we delete it from the latest file, it may still exist in **Git history**.

### 4. Fix

I would:

1. Immediately revoke/rotate the exposed secret.
2. Remove the secret from the repository.
3. Clean Git history if required.
4. Update the application with the new secret.
5. Store future secrets in Key Vault/GitLab protected variables.
6. Enable secret scanning to prevent recurrence.
7. Review audit logs for possible misuse.

**Important:** Removing the secret from Git does **not** make the old secret safe. Rotation/revocation is the first priority.

### 5. Interview Answer

> **“If a secret is accidentally committed, I consider it compromised and immediately rotate or revoke it. Then I remove it from the repository and Git history if required. I update the application with the new secret and move secret management to Key Vault or protected CI/CD variables. I would also enable secret scanning to prevent the same issue in the future.”**

**Keywords:** Revoke → Rotate → Remove → Git History → Key Vault → Secret Scanning

- Pod restarts.
- Node CPU and memory.
- Service/endpoints.
- Ingress/Load Balancer latency.
- DNS and network connectivity.
- Database/external API response time.
- Recent deployments or configuration changes.

## 68. Terraform state is locked. How will you troubleshoot it?

### What is state locking?

State locking prevents multiple Terraform operations from modifying the same state simultaneously.

For example:

```text
Engineer A → terraform apply
                    ↓
               State Locked
                    ↓
Engineer B → terraform apply
                    ↓
               Blocked
```

### What will you check?

I will check:

1. Is another Terraform pipeline running?
2. Is another engineer running Terraform?
3. Did a previous pipeline fail/crash?
4. What backend is being used?
5. Is the lock still valid?

### Commands

```bash
terraform plan
terraform state list
```

If Terraform provides a lock ID, I will inspect the situation before removing it.

For a stale lock, Terraform provides:

```bash
terraform force-unlock <LOCK_ID>
```

### ⚠️ Important

I will **not immediately use `force-unlock`**.

First I verify that no Terraform process or CI/CD pipeline is currently running.

Otherwise, two Terraform processes could modify the same state.

### Root Cause

- Another Terraform operation is running
- GitLab pipeline is still executing
- Previous pipeline crashed
- Stale state lock

### Interview Answer

> **“If Terraform state is locked, first I check whether another Terraform operation or GitLab pipeline is currently running. I don't immediately force-unlock because that can cause state corruption if another process is active. If I confirm that the lock is stale and no Terraform operation is running, then I can use terraform force-unlock with the lock ID.”**

## 72. How would you rollback a failed production deployment?

### What will you check?

First I check:

```bash
kubectl rollout history deployment/<deployment-name>
```

Then:

```bash
kubectl rollout status deployment/<deployment-name>
```

If the latest revision is the problem:

```bash
kubectl rollout undo deployment/<deployment-name>
```

Verify:

```bash
kubectl get pods
kubectl rollout status deployment/<deployment-name>
```

### Root Cause

Usually:

- Bad application code
- Incorrect image
- Configuration issue
- Secret/configuration mismatch
- Dependency issue

### Fix

Rollback first:

```bash
kubectl rollout undo deployment/<deployment-name>
```

Then investigate the failed version separately.

### Interview Answer

> **“For a failed production deployment, I first confirm the failed revision using rollout history and application logs. If the latest version is causing the problem, I use kubectl rollout undo to return to the previous stable revision. I verify pod health and application availability, and then investigate the failed release before deploying it again.”**

## 79. How would you implement Blue/Green deployment for a production AKS application?

### Concept

We maintain **two environments**:

```text
             Ingress
                |
        ┌───────┴───────┐
        ↓               ↓
      BLUE            GREEN
   Current             New
  Production          Version
```

For example:

```text
Blue  → v1
Green → v2
```

### Process

1. Blue is currently serving production.
2. Deploy v2 to Green.
3. Test Green.
4. Perform health/smoke tests.
5. Switch traffic from Blue → Green.
6. Monitor.
7. Keep Blue available for quick rollback.

### Kubernetes Example

Separate deployments:

```text
deployment-blue
deployment-green
```

Services can select the active version using labels.

Example:

```yaml
selector:
  app: myapp
  version: green
```

When Green is validated, update the Service selector to Green.

### Rollback

If Green fails:

```text
Green ❌
   ↓
Service → Blue
   ↓
Production restored
```

### Interview Answer

> **“For Blue/Green deployment, I maintain two versions of the application. Blue is the current production version and Green contains the new version. I deploy and test Green separately, including health and smoke tests. Once Green is validated, I switch the Service or traffic to Green. If there is an issue, I can quickly switch traffic back to Blue.”**

## 80. How would you design high availability and disaster recovery for an AKS application?

### High Availability

I would design multiple layers of redundancy:

```text
                    Users
                      ↓
              Azure Load Balancer
                      ↓
                   Ingress
                      ↓
              ┌───────┴───────┐
              ↓               ↓
            Pod             Pod
              ↓               ↓
             AKS Nodes / Availability Zones
                      ↓
              Azure Database
```

### AKS

I would consider:

- Multiple replicas
- Multiple nodes
- Multiple availability zones where supported
- Pod anti-affinity/topology spread
- PodDisruptionBudget
- HPA
- Cluster Autoscaler
- Separate system/user node pools

### Disaster Recovery

I would consider:

- Azure region redundancy where required
- Backup of databases
- Backup/replication of important data
- Terraform/Infrastructure as Code
- Container images stored in ACR
- Kubernetes manifests/Helm stored in Git
- Key Vault/secret recovery strategy
- Documented DR procedure
- Regular DR testing

### Important Concepts

**HA = minimize downtime**

**DR = recover after a major failure**

### Interview Answer

> **“For AKS high availability, I use multiple replicas, multiple nodes and availability zones where appropriate. I use HPA and Cluster Autoscaler for workload and infrastructure scaling, and configure pod disruption and scheduling rules to avoid concentrating workloads on one node. For disaster recovery, I maintain infrastructure as code, back up critical data, protect container images and secrets, and define a recovery strategy for a regional or major infrastructure failure. I also regularly test the DR process.”**

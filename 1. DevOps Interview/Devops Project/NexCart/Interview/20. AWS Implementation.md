# 6. Public vs Private Subnet

### Public Subnet

Has a route to an Internet Gateway.

Typical resources:

```text
ALB
NAT Gateway
Public-facing components
```

### Private Application Subnet

No direct inbound Internet access.

Typical resources:

```text
EKS Nodes
Application workloads
Internal services
```

### Private Database Subnet

Database should normally remain private.

```text
Application
    |
    v
Private Database
```

Do not expose RDS directly to the Internet unless there is an exceptional, reviewed requirement.

---

# 7. Internet Gateway vs NAT Gateway

### Internet Gateway

Provides Internet connectivity for resources in public subnets.

```text
Public Subnet
     |
Internet Gateway
     |
  Internet
```

### NAT Gateway

Allows private resources to initiate outbound Internet connections without allowing unsolicited inbound connections.

```text
Private Subnet
     |
NAT Gateway
     |
Internet Gateway
     |
Internet
```

Example requirement:

```text
EKS Node
   |
   +--> Download package/image/update
   |
NAT Gateway
```

# 8. Security Groups

Security Groups are stateful virtual firewalls.

Example:

```text
ALB SG
  443 from Internet

EKS Node SG
  Application traffic from ALB

RDS SG
  5432 only from application SG
```

Prefer security-group references instead of broad CIDRs where possible.

Avoid:

```text
0.0.0.0/0
```

for database ports.

# 21. ALB vs NLB

| ALB | NLB |
|---|---|
| Layer 7 | Layer 4 |
| HTTP/HTTPS | TCP/UDP/TLS |
| Path routing | High-performance network traffic |
| Host routing | Static IP support/use cases |
| Web applications | TCP/UDP workloads |

Choose based on traffic requirements, not simply because one is newer.

# 45. EKS Resource Management

Every production workload should have appropriate:

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"
```

Requests influence scheduling.

Limits constrain container resource usage.

Do not copy the same values blindly for every service. Size based on observed workload.

# 60. Production Incident Example

### Scenario

Payment API returns 500 after deployment.

### Investigation

```text
Check deployment
      ↓
Check error rate
      ↓
Check Payment Pod logs
      ↓
Check traces
      ↓
Check environment variables
      ↓
Check database
      ↓
Check recent configuration
```

Suppose the deployment changed:

```text
order_id
```

to:

```text
orderId
```

but the API contract expects `order_id`.

Root cause:

```text
Application contract mismatch
```

Fix:

```text
Correct request/DTO mapping
Add automated API contract test
Deploy immutable image
Smoke test payment API
```

# 3. IAM

### Q9. IAM User vs IAM Role?

> A User generally represents a long-term identity, while a Role provides temporary, assumable permissions. For workloads and modern human access, I prefer role-based and federated access rather than long-lived access keys.

### Q10. What is an IAM policy?

# 4. AWS Networking

### Q13. What is a VPC?

> VPC is a logically isolated network in AWS where we define IP ranges, subnets, routes and network security.

### Q14. Public vs private subnet?

> A public subnet has a route to an Internet Gateway. A private subnet does not provide direct inbound Internet access and can use NAT for outbound connectivity.

### Q15. Why should EKS nodes be private?

> It reduces direct Internet exposure. Public traffic terminates at the load balancer while application nodes remain private.

### Q16. Internet Gateway vs NAT Gateway?

> Internet Gateway provides Internet connectivity for resources with appropriate public routing. NAT Gateway allows private resources to initiate outbound Internet connections without allowing unsolicited inbound connections.

### Q17. Security Group vs NACL?

| Security Group | NACL |
|---|---|
| Resource-level | Subnet-level |
| Stateful | Stateless |
| Allow rules | Allow and deny rules |
| Common workload firewall | Additional subnet control |

### Q119. Why OIDC?

> Temporary federated authentication without storing long-lived cloud credentials.

### Q120. What is the biggest DevOps mistake?

> Treating successful deployment as the definition of success. Production success means the business transaction works reliably, securely and observably.

# 26. Senior Scenario Answer Framework

For almost every troubleshooting question:

```text
1. Understand impact
2. Establish timeline
3. Check recent changes
4. Determine blast radius
5. Collect evidence
6. Form hypothesis
7. Validate hypothesis
8. Apply safest mitigation
9. Validate recovery
10. Identify root cause
11. Implement permanent fix
12. Add prevention
```

Do not answer:

> "I will restart the Pod."

Instead:

> "First I establish impact and determine whether the issue is isolated or systemic. Then I check recent changes, Pod health, logs, events, metrics and dependencies. If a recent deployment is responsible and rollback is safe, I roll back. After recovery I validate the business transaction and perform RCA."

# 29. Two-Minute AWS Project Answer

> **NexCart is an e-commerce microservices application that I designed for an end-to-end AWS DevOps implementation. The application consists of Product, Order, Payment and Notification services. Each service is containerized using Docker.**
>
> **The source code is maintained in GitLab, and the CI/CD pipeline performs validation, testing, quality checks, security scanning and Docker image creation. Images are stored in Amazon ECR using immutable Git-based tags.**
>
> **For the runtime platform, I use Amazon EKS across multiple Availability Zones. Kubernetes Deployments manage the Pods, Services provide service discovery, and Ingress with the AWS Load Balancer Controller integrates the application with an ALB. Helm is used to package and deploy the application.**
>
> **AWS networking is based on VPC, public and private subnets, route tables, NAT and security groups. Application nodes and databases are kept private wherever possible.**
>
> **For security, I use IAM least privilege and workload identity rather than static AWS credentials. Secrets are managed through Secrets Manager and encryption is handled through KMS.**
>
> **Terraform manages the AWS infrastructure layer, while Helm manages Kubernetes application resources.**
>
> **For observability, I monitor AWS infrastructure and application behavior using CloudWatch along with metrics, logs and distributed traces.**
>
> **From a production perspective, I focus on HA across Availability Zones, HPA and node scaling, database protection, certificate and secret rotation, backup and DR, security, cost optimization and Day-2 operations.**
>
> **My approach is not just to deploy the application. I design it so that it can be monitored, secured, scaled, rolled back and recovered when something fails.**

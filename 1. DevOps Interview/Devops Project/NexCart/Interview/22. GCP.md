# ☁️ NexCart — GCP Implementation Notes & Interview Guide

## 1. GCP Architecture for NexCart

NexCart is an e-commerce microservices application consisting of **Product, Order, Payment and Notification** services.

The recommended GCP production architecture is:

```text
Developer
   │
   ▼
GitLab Repository
   │
   ▼
GitLab CI/CD
   │
   ├── Validate
   ├── Test
   ├── SonarQube / Quality
   ├── SAST / Dependency Scan
   ├── Trivy Image Scan
   └── Docker Build
           │
           ▼
     Artifact Registry
           │
           ▼
       GKE Cluster
     ┌─────┴─────┐
     │           │
 Product      Order
 Payment      Notification
     │           │
     └─────┬─────┘
           │
      Internal Services
           │
     Ingress / Load Balancer
           │
        Internet
```

Supporting GCP services:

| Area | GCP Service |
|---|---|
| Kubernetes | GKE |
| Container Registry | Artifact Registry |
| Compute | Compute Engine / GKE Nodes |
| Networking | VPC |
| Load Balancing | Cloud Load Balancing |
| DNS | Cloud DNS |
| TLS | Google-managed certificates / Certificate Manager |
| Database | Cloud SQL |
| Cache | Memorystore |
| Object Storage | Cloud Storage |
| Secrets | Secret Manager |
| Encryption | Cloud KMS |
| Identity | IAM / Workload Identity Federation |
| Monitoring | Cloud Monitoring |
| Logging | Cloud Logging |
| Audit | Cloud Audit Logs |
| IaC | Terraform |
| CI/CD | GitLab CI/CD |
| Kubernetes Packaging | Helm |

# 2. GCP Project Structure

A production environment should not depend on a single unmanaged GCP project.

Recommended structure:

```text
GCP Organization
│
├── Folder: Production
│   └── Project: nexcart-prod
│
├── Folder: Non-Production
│   ├── Project: nexcart-dev
│   └── Project: nexcart-test
│
└── Folder: Shared Services
    └── Project: nexcart-shared
```

For smaller environments:

```text
nexcart-dev
nexcart-test
nexcart-prod
```

Keep production isolation as a priority.

# 3. GCP Regions and Zones

GCP resources are either:

- Global
- Regional
- Zonal

Example:

```text
Region
│
├── Zone A
├── Zone B
└── Zone C
```

For production GKE:

```text
GKE Cluster
│
├── Zone A → Nodes
├── Zone B → Nodes
└── Zone C → Nodes
```

This protects the application from a single-zone failure.

Senior principle:

> High availability is not achieved by simply running multiple pods. Workloads must be distributed across failure domains.

# 4. GCP IAM

GCP IAM controls:

```text
Who
  ↓
Can perform what action
  ↓
On which resource
```

Main concepts:

- Principal
- Role
- Permission
- Resource
- Policy

Roles:

### Basic roles

- Owner
- Editor
- Viewer

Avoid these for production where possible.

### Predefined roles

Examples:

```text
roles/container.developer
roles/container.admin
roles/storage.objectViewer
roles/secretmanager.secretAccessor
roles/artifactregistry.reader
```

### Custom roles

Use custom roles when predefined roles provide excessive permissions.

# 5. Service Accounts

A GCP Service Account represents a workload identity.

Example:

```text
GitLab CI
   ↓
GCP Service Account

GKE Workload
   ↓
Kubernetes ServiceAccount
   ↓
GCP IAM identity
```

Do not put service-account JSON keys inside:

```text
GitLab repository
Docker image
Kubernetes Secret
Helm values
application source code
```

Prefer:

```text
OIDC / Workload Identity Federation
```

over long-lived service-account keys.

# 6. Workload Identity

GKE Workload Identity allows Kubernetes workloads to access Google Cloud services without storing long-lived credentials inside pods.

Example:

```text
Pod
 │
 ▼
Kubernetes ServiceAccount
 │
 ▼
Workload Identity
 │
 ▼
GCP Service Account
 │
 ▼
Secret Manager / Cloud Storage / Pub/Sub / etc.
```

Example Kubernetes ServiceAccount:

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: payment-service
  namespace: nexcart
  annotations:
    iam.gke.io/gcp-service-account: payment@nexcart-prod.iam.gserviceaccount.com
```

Grant only required permissions.

Example:

```bash
gcloud projects add-iam-policy-binding nexcart-prod \
  --member="serviceAccount:payment@nexcart-prod.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor"
```

```text

├── Secondary Pod Range
│
├── Secondary Service Range

│
```

GKE VPC-native networking uses:

```text
Primary subnet range
        +
Pod secondary range

Service secondary range
```

Check subnet:

```bash
gcloud compute networks subnets list
```

Describe subnet:

```bash
gcloud compute networks subnets describe <subnet> \
  --region=<region>
```

# 8. Private GKE Architecture

Production GKE should normally minimize public exposure.

Recommended:

```text
Internet
   │
   ▼
Cloud Load Balancer
   │
   ▼
Ingress
   │
   ▼
GKE
   │
   ├── Product
   ├── Order
   ├── Payment
   └── Notification
```

Nodes can use private IP addresses.

For outbound Internet access:

```text
Private GKE Nodes
       │
       ▼
Cloud NAT
       │
       ▼
Internet
```

Cloud NAT provides outbound connectivity without assigning public IPs to nodes.

# 9. GKE

GKE = Google Kubernetes Engine.

Two major operating modes:

### Autopilot

Google manages much of the underlying infrastructure.

### Standard

You have more control over:

- Node pools
- Machine types
- Autoscaling
- OS configuration
- Networking
- Node-level settings

For senior interviews:

> I choose Autopilot when I want reduced operational overhead and Standard when I need deeper control over node pools, workloads, networking or specialized infrastructure requirements.

# 12. Artifact Registry

Artifact Registry replaces the older Container Registry approach for modern implementations.

Repository:

```text
asia-south1-docker.pkg.dev/
    nexcart-prod/
    nexcart/
    product-service
```

Create repository:

```bash
gcloud artifacts repositories create nexcart \
  --repository-format=docker \
  --location=asia-south1
```

Configure Docker:

```bash
gcloud auth configure-docker asia-south1-docker.pkg.dev
```

Build:

```bash
docker build \
  -t asia-south1-docker.pkg.dev/nexcart-prod/nexcart/product-service:<git-sha> .
```

Push:

```bash
docker push \
  asia-south1-docker.pkg.dev/nexcart-prod/nexcart/product-service:<git-sha>
```

List images:

```bash
gcloud artifacts docker images list \
  asia-south1-docker.pkg.dev/nexcart-prod/nexcart
```

# 14. GKE → Artifact Registry

GKE nodes need permission to pull images.

Grant the required Artifact Registry access to the node identity/service account.

Typical role:

```text
roles/artifactregistry.reader
```

Troubleshooting:

```bash
kubectl describe pod <pod> -n nexcart
```

Look for:

```text
ErrImagePull
ImagePullBackOff
401 Unauthorized
403 Forbidden
manifest unknown
```

Senior troubleshooting flow:

```text
ImagePullBackOff
   ↓
Check image name
   ↓
Check image tag/digest
   ↓
Check repository
   ↓
Check node/service identity
   ↓
Check Artifact Registry IAM
   ↓
Check network/private access
```

# 26. KMS

Cloud KMS provides cryptographic key management.

Use cases:

- Encryption
- Customer-managed encryption keys
- Key rotation
- Compliance
- Controlled key access

Architecture:

```text
Application
   ↓
GCP Service
   ↓
KMS
   ↓
Encryption Key
```

Do not confuse:

```text
Secret Manager
```

with:

```text
KMS
```

Secret Manager stores secrets.

KMS manages cryptographic keys and encryption operations.

# 33. HPA

Horizontal Pod Autoscaler scales pods.

Example:

```text
CPU > target
   ↓
Increase replicas
```

Check:

```bash
kubectl get hpa -n nexcart
```

Describe:

```bash
kubectl describe hpa <name> -n nexcart
```

Example:

```yaml
minReplicas: 3
maxReplicas: 10
targetCPUUtilizationPercentage: 70
```

CPU alone may not represent application load.

Consider:

- Request rate
- Queue depth
- Latency
- Concurrent requests
- Business metrics

# 34. GKE Cluster Autoscaler

HPA:

```text
Pod scaling
```

Cluster Autoscaler:

```text
Node scaling
```

Example:

```text
Traffic increases
     ↓
HPA increases pods
     ↓
No node capacity
     ↓
Pods remain Pending
     ↓
Cluster Autoscaler adds nodes
     ↓
Pods become Running
```

This distinction is a common interview question.

```text
Alerts
Dashboards
```

should exist before production incidents occur.

```text

 ↓

 ↓

 ↓

 ↓
```

### 10. Senior DevOps mindset

The objective is not simply:

> "How do I deploy the application?"

The senior-level objective is:

> "How do I design, deploy, operate, secure, scale, troubleshoot and recover the application reliably while controlling cost and reducing operational risk?"

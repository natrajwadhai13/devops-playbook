# 🚀 10. GitLab CI/CD

## 1. Overview

GitLab CI/CD automates the NexCart software delivery lifecycle:

```text
Developer
   ↓
Git
   ↓
GitLab Repository
   ↓
GitLab CI/CD
   ↓
Build + Test + Security Scan
   ↓
Docker Image
   ↓
Azure Container Registry
   ↓
AKS
   ↓
Helm
   ↓
Smoke Test
   ↓
Production
```

The goal is:

```text
Build once → Scan once → Push once → Deploy the same artifact
```

# 3. `.gitlab-ci.yml`

GitLab uses `.gitlab-ci.yml` to define pipeline configuration.

Basic example:

```yaml
stages:
  - validate
  - test
  - build
  - security
  - deploy

validate:
  stage: validate
  script:
    - echo "Validating application"

test:
  stage: test
  script:
    - npm ci
    - npm test

build:
  stage: build
  script:
    - docker build -t product-service:$CI_COMMIT_SHA .

security:
  stage: security
  script:
    - echo "Running security scan"

deploy:
  stage: deploy
  script:
    - echo "Deploying application"
```

# 4. GitLab Pipeline Terminology

| Term | Meaning |
|---|---|
| Pipeline | Complete CI/CD workflow |
| Stage | Logical pipeline phase |
| Job | Individual task |
| Runner | Machine executing jobs |
| Artifact | Output generated by a job |
| Cache | Reusable dependency data |
| Variable | Configuration/secret value |
| Environment | Deployment target |
| Rule | Controls when a job executes |
| Trigger | Starts another pipeline/job |

# 5. GitLab Runner

GitLab Runner executes CI/CD jobs.

```text
GitLab
   |
   | Job
   v
GitLab Runner
   |
   +-- Shell
   +-- Docker
   +-- Kubernetes
```

Runner can be:

- Shared
- Group-level
- Project-specific

For production environments, dedicated runners can provide better isolation and control.

# 7. GitLab CI Variables

Variables store configuration and sensitive information.

Example:

```yaml
variables:
  ACR_NAME: "nexcartacr"
  AKS_NAMESPACE: "nexcart"
```

Sensitive variables should be configured in:

```text
Project
  ↓
Settings
  ↓
CI/CD
  ↓
Variables
```

Sensitive variables should be:

```text
Masked
Protected
Environment-scoped
```

when appropriate.

---

# 8. Never Store Secrets in `.gitlab-ci.yml`

Bad:

```yaml
variables:
  DB_PASSWORD: "Password123"
  AZURE_CLIENT_SECRET: "secret-value"
```

Also avoid:

```yaml
script:
  - echo "$DB_PASSWORD"
```

because secrets can accidentally appear in logs.

Better:

```text
GitLab
   |
OIDC / Federated Identity
   |
Azure
   |
Key Vault
```

For application secrets:

```text
AKS
 ↓
Workload Identity
 ↓
Key Vault
```

---

# 9. GitLab CI/CD Variables vs Key Vault

| GitLab Variable | Azure Key Vault |
|---|---|
| Useful for CI configuration | Centralized secret management |
| Available to pipeline jobs | Available to Azure workloads |
| Can be masked/protected | Azure RBAC |
| Good for non-sensitive configuration | Better for sensitive application secrets |
| Rotation must be managed | Centralized secret lifecycle |

Do not use GitLab variables as a replacement for enterprise secret management.

# 10. Pipeline Rules

Rules control when a job runs.

Example:

```yaml
deploy-prod:
  stage: deploy
  script:
    - echo "Deploying production"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
```

Merge request example:

```yaml
unit-test:
  stage: test
  script:
    - npm test
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
```

# 13. Build Once, Deploy Many

Bad approach:

```text
DEV → Build image
TEST → Build image again
PROD → Build image again
```

This can produce different artifacts.

Preferred:

```text
Source
  ↓
Build
  ↓
Image SHA
  ↓
ACR
  |
  +--> DEV
  |
  +--> TEST
  |
  +--> PROD
```

Example image:

```text
nexcartacr.azurecr.io/product-service:9f3a71c
```

The same immutable image should move through environments.

```text

    |

    v
```

```text
    |
    | Federated Identity
    v
```

- Reduced credential leakage risk
- Short-lived authentication
- Better auditability
- Easier credential lifecycle

# 17. ACR Authentication

For AKS image pulling, normally use the AKS kubelet/managed identity with:

```text
AcrPull
```

Do not confuse:

```text
AKS → ACR
```

with:

```text
Pod → Key Vault
```

They are different identity flows.

```text
AKS node identity
      ↓
ACR
      ↓
Pull image
```

Whereas:

```text
Pod
 ↓
Workload Identity
 ↓
Key Vault
```

# 20. Dependency Caching

Example Node.js:

```yaml

  key:
    files:
      - package-lock.json
  paths:
    - .npm/
```

Then:

```bash
npm ci --cache .npm --prefer-offline
```

Cache can reduce pipeline execution time.

Do not cache generated build outputs blindly.

# 21. Artifacts

Artifacts are files produced by jobs and passed/downloaded later.

Example:

```yaml
build:
  stage: build
  script:
    - npm run build
  artifacts:
    paths:
      - dist/
```

Artifacts are useful for:

- Test reports
- Coverage
- Build packages
- Scan reports
- Generated manifests

---

# 22. Artifact vs Cache

| Artifact | Cache |
|---|---|
| Pipeline output | Performance optimization |
| Used by later jobs | Reuses dependencies |
| Usually intentional output | May be regenerated |
| Can be downloaded | Usually reused automatically |

Senior principle:

```text
Artifact = deliverable
Cache = optimization
```

# 27. Helm Validation in CI

Before deployment:

```bash

```

Render templates:

```bash
helm template nexcart ./helm/nexcart \
  -f ./helm/nexcart/values-prod.yaml
```

Dry run:

```bash

  -n nexcart \
  --create-namespace \
  -f ./helm/nexcart/values-prod.yaml \
  --dry-run
```

This catches many manifest/template errors before they reach AKS.

# 28. Deploy to AKS

Typical GitLab job:

```yaml
deploy-dev:
  stage: deploy
  script:
    - az aks get-credentials
        --resource-group "$AKS_RESOURCE_GROUP"
        --name "$AKS_NAME"
    - helm upgrade --install nexcart ./helm/nexcart
        --namespace nexcart
        --create-namespace
        -f ./helm/nexcart/values-dev.yaml
```

Production:

```yaml
deploy-prod:
  stage: deploy
  script:
    - az aks get-credentials
        --resource-group "$AKS_RESOURCE_GROUP"
        --name "$AKS_NAME"
    - helm upgrade --install nexcart ./helm/nexcart
        --namespace nexcart
        -f ./helm/nexcart/values-prod.yaml
        --wait
        --atomic
  when: manual
```

---

# 29. `--wait` and `--atomic`

Useful production deployment:

```bash
helm upgrade --install nexcart ./helm/nexcart \
  -n nexcart \
  -f values-prod.yaml \
  --wait \
  --atomic
```

### `--wait`

Waits for Kubernetes resources to become ready.

### `--atomic`

If deployment fails, Helm attempts to roll back the release.

This reduces the risk of leaving production in a partially deployed state.

# 35. Deployment Strategy

## Rolling Deployment

Default Kubernetes strategy.

```text
Old Pods
   ↓
New Pods
   ↓
Readiness checks
   ↓
Traffic gradually moves
```

Useful for normal releases.

---

## Blue-Green

```text
Blue = Current
Green = New
```

Test Green before switching traffic.

Useful for higher-risk releases but requires additional infrastructure and traffic-control design.

---

## Canary

```text
95% → Old version
5%  → New version
```

Increase traffic gradually after observing metrics.

Useful for high-risk production releases.

# 44. Pipeline Optimization

Senior-level optimization:

```text
1. Parallelize independent jobs
2. Use dependency caching
3. Use Docker layer caching where appropriate
4. Avoid rebuilding unchanged services
5. Use immutable image tags
6. Build only changed services where practical
7. Reuse CI templates
8. Use purpose-built runner images
9. Fail fast on critical checks
10. Avoid unnecessary environment setup
```

Example:

```text
                 ┌─ Product Build ─┐
                 ├─ Order Build ───┤
Source ──────────┼─ Payment Build ──┼──→ Push
                 └─ Notify Build ───┘
```

---

# 45. Monorepo Consideration

NexCart contains multiple services.

A monorepo can trigger unnecessary builds.

Example:

```text
product-service changed
```

There is no reason to rebuild:

```text
payment-service
notification-service
```

Use GitLab rules/changes to optimize pipelines.

Concept:

```yaml
rules:
  - changes:
      - product-service/**/*
```

# 46. Reusable GitLab Templates

Large organizations should avoid copying the same pipeline logic into every project.

Example:

```text
.gitlab/
  ci/
    build.yml
    test.yml
    security.yml
    deploy.yml
```

Then use:

```yaml
include:
  - local: '.gitlab/ci/build.yml'
  - local: '.gitlab/ci/security.yml'
  - local: '.gitlab/ci/deploy.yml'
```

Benefits:

- Standardization
- Easier maintenance
- Central security controls
- Less duplication

# 52. Example Production Pipeline

```yaml
stages:
  - validate
  - test
  - quality
  - security
  - build
  - push
  - deploy-dev
  - smoke
  - deploy-prod

  stage: validate

    - echo "Run unit tests"

sonarqube:
  stage: quality
  script:
    - echo "Run SonarQube analysis"

  stage: security
  script:
    - echo "Run SAST and dependency scanning"

build:
  stage: build
  script:
    - docker build -t "$ACR_LOGIN_SERVER/product-service:$CI_COMMIT_SHA" ./product-service

trivy:
  stage: security

push:
  stage: push
  script:
    - docker push "$ACR_LOGIN_SERVER/product-service:$CI_COMMIT_SHA"

deploy-dev:

      -n nexcart-dev

      -f ./helm/nexcart/values-dev.yaml

smoke:
  stage: smoke
  script:
    - echo "Run application smoke tests"

deploy-prod:
  stage: deploy-prod
  script:
    - helm upgrade --install nexcart ./helm/nexcart
      -n nexcart-prod
      -f ./helm/nexcart/values-prod.yaml
      --wait
```

# 56. Senior Interview Questions

### Q1. Explain your GitLab CI/CD pipeline.

> Our pipeline follows a controlled flow from validation and testing through quality and security scanning, Docker image creation, ACR publishing, Helm deployment to AKS, smoke testing, and controlled production deployment. We use immutable commit-based image tags and promote the same artifact across environments.

---

### Q2. How do you deploy the same image across DEV, TEST and PROD?

> I build the image once using the Git commit SHA as the immutable tag, push it to ACR, and use environment-specific Helm values to deploy that same image reference to each environment. I don't rebuild the image for every environment.

---

### Q3. How do you secure Azure authentication from GitLab?

> My preferred approach is GitLab OIDC with Microsoft Entra federated identity instead of storing a long-lived Azure client secret. The pipeline receives short-lived identity credentials and gets only the Azure permissions required for the deployment.

---

### Q4. How do you prevent a developer from deploying directly to production?

> I use protected branches, protected environments, merge-request approvals, successful pipeline requirements, and manual production deployment gates. Production credentials and deployment jobs are restricted to trusted branches and runners.

---

### Q5. What happens if Trivy detects a critical vulnerability?

> The security stage fails and the image is not promoted to the production deployment stage. I would investigate whether the vulnerability comes from the application dependency or base image, upgrade the affected component, rebuild, rescan, and only then continue the release.

---

### Q6. Why use Git commit SHA for Docker tags?

> It provides a deterministic relationship between source code and the deployed artifact. If production is running image `9f3a71c`, I can trace that exact image back to the Git commit that produced it.

---

### Q7. How do you troubleshoot a failed GitLab deployment?

> I first identify the failing stage. If it is build-related, I reproduce the Docker build. If it is authentication, I verify Azure identity and permissions. If Helm fails, I render the templates and inspect Helm status and Kubernetes events. If the deployment succeeds but the application is unhealthy, I troubleshoot pods, logs, probes, services, dependencies, and configuration.

---

### Q8. How do you reduce pipeline execution time?

> I parallelize independent service builds and tests, use dependency caching, avoid rebuilding unchanged services, use reusable CI templates, optimize Docker layers, and maintain purpose-built runner images. I measure pipeline duration before and after optimization instead of blindly adding caching.

---

### Q9. What is the difference between CI and CD?

**CI:**

```text
Code
 ↓
Build
 ↓
Test
 ↓
Quality
 ↓
Security
```

**CD:**

```text
Artifact
 ↓
Environment
 ↓
Deployment
 ↓
Validation
 ↓
Promotion
```

---

### Q10. How do you handle production rollback?

> I first stop further rollout, determine whether the issue is application or infrastructure related, and if necessary roll back to the last known-good Helm revision or image. After confirming application health, I investigate the root cause and add a preventive control to the pipeline.
